# Unit 3 — 수의 표현 & 산술

> 핵심 질문: 음수·소수를 0과 1로 어떻게 표현하고, 왜 `0.1+0.2≠0.3`인가?

## 0. 큰 그림

가산기는 비트를 더할 뿐, **그 비트가 무슨 수인지**는 따로 정해야 한다. 같은 `1111_1111`이 **255**(unsigned)일 수도 **−1**(signed)일 수도 있다. **비트 자체엔 의미가 없고, 해석 규칙이 수를 결정한다.**

## 1. 부호 없는 정수 (Unsigned)

```text
1011₂ = 1×8 + 0×4 + 1×2 + 1×1 = 11
```

n비트 → 0 ~ 2ⁿ−1 (8비트 = 0~255). 직관적. 문제는 음수.

## 2. 음수 — 2의 보수 (Two's Complement)

**순진한 시도 (sign-magnitude, "맨 앞=부호"):**

```text
0_0000101 = +5 / 1_0000101 = -5
```

문제: ① 0이 둘(+0,−0) ② 덧셈 시 부호 보고 분기 → 회로 복잡.

**해법: 2의 보수 = "비트 반전 + 1":**

```text
+5 = 0000_0101
-5 = 반전(1111_1010) + 1 = 1111_1011
```

> **장점: 뺄셈을 그냥 덧셈으로** 처리 → 가산기 하나로 덧셈·뺄셈 통합.

```text
5 + (-5):  0000_0101 + 1111_1011 = 1_0000_0000 → 맨위 올림 버림 → 0 ✅
```

- 0이 하나뿐. 맨 앞 비트 1이면 음수.
- 8비트 범위: **−128 ~ +127** (음수가 하나 더 많음).

## 3. Overflow — 같은 비트, 다른 사건

가산기는 signed/unsigned를 모름 → overflow가 **두 종류**:

```text
8비트:  0111_1111 (127) + 0000_0001 (1) = 1000_0000
  unsigned 해석: 128 ✅ (정상, carry 없음)
  signed 해석:  -128 ❌ (127+1이 음수?! signed overflow)
```

- **Carry flag**: unsigned overflow (맨 위 올림 넘침).
- **Overflow flag**: signed overflow (부호 이상하게 뒤집힘 — 부호비트로 들어가는 carry ≠ 나가는 carry).

→ 같은 가산기, 두 개의 다른 "넘침". 혼동이 버그 단골.

## 4. 부동소수점 (Floating Point)

```text
값 = (−1)^부호 × 1.가수 × 2^(지수−127)
32비트: [부호 1][지수 8][가수 23]
```

"부동(floating)" = 소수점 위치가 지수 따라 떠다님 → 넓은 범위를 같은 비트 수로.

**★ 왜 `0.1+0.2≠0.3`:** 2진 부동소수점으로 **0.1을 정확히 표현 못 함**:

```text
0.1 = 0.0001100110011...₂ (무한 반복)  ← 1/3=0.333...이 무한인 것과 같은 현상
```

가수 23비트에서 잘라 반올림 → 저장값이 0.1이 아니라 "0.1에 가까운 값". 0.2도 마찬가지 → 합 ≈ 0.30000000447 ≠ 0.3. **버그 아니라 표현 한계(반올림 오차).**

특수값: `+0/−0`, `NaN`, `±∞`, `denormal`.

## 핵심 정리

- 비트는 의미 없음 — **해석 규칙(표현)이 수를 결정.**
- **2의 보수**: 음수=반전+1 → 뺄셈을 덧셈으로(가산기 통합), 0 하나.
- **Overflow 2종**: carry(unsigned) ≠ overflow(signed). 같은 비트도 해석 따라 정상/넘침.
- **부동소수점**: 2진 과학표기. 0.1을 못 담아 반올림 오차 → `0.1+0.2≠0.3`.
- **Golden rule:** 같은 비트도 해석에 따라 다른 수다 — 표현 규칙을 모르면 산술을 예측할 수 없다.

---

## 🔌 검증 관점

- **signed vs unsigned 혼동 = reference model 버그 1순위.** SystemVerilog `logic`은 기본 unsigned → signed 비교는 `$signed()` 명시 안 하면 조용히 틀림. `0x80`을 한쪽은 +128, 한쪽은 −128로 봐서 mismatch.
- **Overflow 코너:** `MAX+1`, `MIN−1`, `0−1`, 부호 경계(`0x7F→0x80`)는 필수 코너. carry/overflow 플래그를 **각각** 검증.
- **FP 비교는 `==` 금지:** bit-exact 요구할지 tolerance(ULP) 둘지 결정. DUT와 모델의 **반올림 모드**가 다르면 마지막 비트 어긋나 mismatch — "틀린 게 아니라 반올림 차이"(Unit 1 "정당한데 달라 보이는 것"의 FP 버전).
- **특수값:** NaN·∞·denormal 입력 동작 별도 검증 (정상 범위만 테스트하면 놓침).

## 📎 부록 — 이 단원에서 나온 질문들

### Q. 부동소수점을 그래서 어떻게 표현한다는 거야?

2진수 버전의 과학적 표기법으로, 수를 세 칸(부호/지수/가수)에 나눠 담는다.

```text
값 = (−1)^부호 × 1.가수 × 2^(지수−127)
32비트: [부호 1] [지수 8] [가수 23]
```

**예제 1 — 6.25 인코딩 (깔끔히 떨어지는 수):**

```text
① 10진→2진:  6=110, 0.25=0.01 → 6.25 = 110.01₂
② 정규화:    110.01 = 1.1001 × 2²   (소수점 왼쪽 2칸 → ×2²; 항상 1.xxx 꼴)
③ 세 칸 채우기:
   부호 = 0
   지수 = 2 + 127 = 129 = 1000_0001
   가수 = "1." 뒤 부분 = 1001 → 23비트로: 100_1000_0000_0000_0000_0000
완성: 0 1000_0001 100_1000_0000_0000_0000_0000
검산: 1.1001₂ = 1+0.5+0.0625 = 1.5625, ×2² = 6.25 ✅
```

**핵심 트릭 — "숨은 1"(implicit leading 1):** 정규화하면 항상 `1.xxx`라 맨 앞 1은 저장 안 함(하드웨어가 붙임) → 23비트로 실질 24비트 정밀도.

**왜 지수에 +127 (bias):** 지수는 음수도 돼야 함. 항상 127을 더해 저장하면 저장값이 늘 양수(0~255)라 음수 지수 처리·대소 비교가 단순. 읽을 땐 −127로 복원.

```text
실제지수 -5 → 저장 122 / 0 → 127 / +2 → 129
```

**예제 2 — 0.1은 왜 깨지나:**

```text
① 0.1 = 0.00011001100110011...₂ (무한 반복! 2진수로 안 떨어짐)
② 정규화: 1.10011001100... × 2^-4 (무한)
③ 가수 23비트에서 잘라 반올림 → 저장값 ≈ 0.100000001490... (정확한 0.1 아님)
```

→ `0.1+0.2`는 약간씩 어긋난 값끼리 더해져 ≈ 0.300000004 ≠ 0.3. **유한 비트로 무한 소수를 담는 반올림 오차**(버그 아님).

**요약 3단계:** ① 2진수로 변환 → ② `1.xxx × 2^n` 정규화 → ③ 부호·(지수+127)·(소수부 23비트)에 나눠 담기(앞의 1은 숨김). 무한 소수는 잘려서 반올림 오차 발생.
