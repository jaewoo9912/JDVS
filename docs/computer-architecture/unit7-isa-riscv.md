# Unit 7 — ISA & RISC-V (명령어 집합 구조)

> 핵심 질문: 하드웨어와 소프트웨어의 계약(ISA)이란? 왜 RISC-V가 깔끔한가? (ISA = HW/SW 계약 · RISC vs CISC · RISC-V)

## 0. 한 문장으로 시작 — ISA란 무엇인가

> **ISA(Instruction Set Architecture, 명령어 집합 구조)** = 소프트웨어가 하드웨어에게 시킬 수 있는 **모든 명령어의 목록과 그 규칙**. 하드웨어와 소프트웨어 사이의 **계약(contract)** 이자 **추상화 경계(abstraction boundary)**.

ISA는 **식당 메뉴판**이다:

- 손님(소프트웨어/컴파일러)은 메뉴판에 있는 것만 주문할 수 있다.
- 주방(하드웨어)이 그걸 어떻게 만드는지(가스불? 인덕션? 전자레인지?)는 손님이 알 필요 없다.
- 메뉴판만 똑같으면, 주방을 통째로 바꿔도 손님은 **같은 주문**을 할 수 있다.

핵심 가치 — **"인터페이스를 고정하면, 양쪽이 독립적으로 진화할 수 있다."**

## 1. ISA는 "경계선"이다 — 무엇을 가르나

```text
   ┌─────────────────────────────────┐
   │  응용 프로그램 (앱)               │  ← 소프트웨어
   │  컴파일러 / OS                   │
   ├─────────────────────────────────┤
   │  ★ ISA (명령어 집합) ★           │  ← 계약서 (이 줄이 경계!)
   ├─────────────────────────────────┤
   │  마이크로아키텍처                  │  ← 하드웨어
   │  (pipeline, 캐시, 분기예측...)     │     "ISA를 어떻게 구현하나"
   │  회로 / 트랜지스터                 │
   └─────────────────────────────────┘
```

| | **Architecture (ISA)** | **Microarchitecture (마이크로아키텍처)** |
|---|---|---|
| 무엇 | 소프트웨어가 **보는** 것 (명령어, 레지스터, 메모리 모델) | ISA를 **구현하는** 방법 (pipeline 깊이, 캐시 크기...) |
| 비유 | 메뉴판 (무엇을) | 주방 (어떻게) |
| 예 | "add 명령어가 있다", "레지스터 32개" | "5단계 pipeline", "L1 32KB" |
| 바뀌면 | SW 다시 짜야 함 (호환성 깨짐) | SW는 그대로 (성능만 달라짐) |

> **결정적 통찰**: **같은 ISA를 여러 마이크로아키텍처로 구현할 수 있다.** Intel i3와 i9는 마이크로아키텍처가 완전히 다르지만 **같은 x86 ISA** → 같은 프로그램이 둘 다에서 돈다. Unit 6의 Pentium4(31단계)와 Core(14단계)도 같은 x86 ISA였다 — 메뉴판은 같고 주방만 바꾼 것.

> **DV 메모**: 이 경계가 **검증 레벨을 가른다.** ISA 레벨 검증(아키텍처 검증)은 "명령어가 스펙대로 정확한 결과를 내나"(architectural state 비교, Unit 5의 PC/RegFile/Memory). 마이크로아키텍처 검증은 "pipeline forwarding, 캐시 일관성, 분기예측이 정확하나"(내부 동작). RDMA로 치면 — IB spec 준수 검증(아키텍처) vs 내부 큐/파이프 동작 검증(마이크로아키텍처)의 구분과 똑같다.

## 2. ISA가 정의하는 것들 — 계약서의 조항

1. **명령어 집합** — 어떤 연산이 가능한가 (add, load, branch...)
2. **명령어 인코딩** — 각 명령어가 비트로 어떻게 표현되나 (Unit 5의 R/I/S/B/U/J 포맷)
3. **레지스터** — 몇 개, 몇 비트, 용도 (RISC-V: 32개 × 32/64비트)
4. **데이터 타입** — 다룰 수 있는 데이터 (정수 8/16/32/64비트, 부동소수점...)
5. **메모리 모델** — 주소 지정 방식, 정렬(alignment), 바이트 순서(endianness), 메모리 일관성 규칙(Unit 13)
6. **예외/인터럽트** — illegal instruction, page fault 등을 어떻게 처리하나

> **DV 메모**: 이 6개가 그대로 **검증 coverage 항목**이 된다. ISA 매뉴얼이 곧 verification plan의 뼈대다.

## 3. ⭐ RISC vs CISC — 두 철학의 전쟁

### CISC (Complex Instruction Set Computer) — "명령어를 강력하게"

**철학**: "명령어 하나가 많은 일을 하게 하자." 대표: **x86** (Intel, AMD)

```text
x86 예: add [메모리주소], 5    ← 메모리 직접 연산 (load+add+store가 한 명령어)
```

- 명령어 종류가 **많고 복잡** (수백~수천 개), **길이 가변** (1~15바이트)
- **IC ↓** (명령어 적게 씀), 하지만 **CPI ↑, T ↑** (Iron Law!)

### RISC (Reduced Instruction Set Computer) — "명령어를 단순하게"

**철학**: "명령어를 단순하게 유지하고, 복잡한 건 여러 명령어 조합으로." 대표: **RISC-V, ARM, MIPS**

```text
RISC 예:
   lw  x5, 0(x10)    ← 메모리에서 읽기
   addi x5, x5, 5    ← 더하기
   sw  x5, 0(x10)    ← 메모리에 쓰기
```

- 명령어 종류가 **적고 단순**, **길이 고정** (RISC-V: 32비트) → 디코드 쉬움
- **Load/Store만 메모리 접근** (load-store 구조)
- **IC ↑** (명령어 많이 씀), 하지만 **CPI ↓, T ↓**

| | **CISC (x86)** | **RISC (RISC-V, ARM)** |
|---|---|---|
| 철학 | 명령어 하나가 많은 일 | 명령어 단순, 조합으로 해결 |
| 명령어 수 | 많음(복잡) | 적음(단순) |
| 명령어 길이 | 가변 (1~15B) | 고정 (4B) |
| 메모리 접근 | 어느 명령어든 가능 | load/store만 |
| 디코드 | 복잡(어려움) | 단순(쉬움) → pipeline 유리 |
| Iron Law | IC↓ CPI↑ T↑ | IC↑ CPI↓ T↓ |

### 누가 이겼나? — "사실 둘 다, 그리고 RISC가"

- **결론적으로 RISC 철학이 이겼다.** 모바일(ARM)·임베디드·서버(ARM)·새 설계(RISC-V) 전부 RISC.
- **그런데 x86(CISC)도 살아남았다** — 현대 x86 CPU는 **속으로는 RISC처럼 동작**한다. x86의 복잡한 명령어를 칩 내부에서 **micro-op(μop)이라는 단순한 RISC식 명령어로 쪼개서** 실행한다. 즉 겉(ISA)은 CISC, 속(마이크로아키텍처)은 RISC.

> **ISA(메뉴판)는 호환성 때문에 x86 CISC로 유지하면서, 주방(마이크로아키텍처)은 RISC로 바꾼 것.** "인터페이스 고정, 구현 진화"의 완벽한 사례.

## 4. 왜 RISC-V인가

- **오픈소스/무료** — x86(Intel/AMD 독점), ARM(라이선스 비쌈)과 달리 **누구나 무료로** 칩을 만들 수 있다. ISA계의 리눅스.
- **모듈식 설계** — 기본(RV32I, 정수 47개 명령어)에 필요한 확장만 골라 붙임:

  ```text
  RV32I  : 기본 정수 (32비트)
  + M    : 곱셈/나눗셈
  + A    : 원자적 연산 (멀티코어용)
  + F/D  : 부동소수점 (single/double)
  + C    : 압축 명령어 (16비트, 코드 크기↓)
  → RV32IMAFDC = "RV32G" (general)
  ```

- **깨끗한 설계** — 40년 ISA 연구의 교훈을 처음부터 반영. legacy 짐이 없어 배우기 좋다.
- **교육·연구·산업 표준**.

### RISC-V 기본 명령어 카테고리

| 카테고리 | 예 | 하는 일 |
|---|---|---|
| 산술/논리 | `add, sub, and, or, xor, slt` | 레지스터끼리 계산 (R-type) |
| 즉치 산술 | `addi, andi, ori` | 레지스터 + 상수 (I-type) |
| 메모리 | `lw, sw, lb, sb` | load/store (메모리 접근은 이것만) |
| 분기 | `beq, bne, blt, bge` | 조건 분기 (B-type) |
| 점프 | `jal, jalr` | 함수 호출/점프 (J-type) |
| 상위 즉치 | `lui, auipc` | 큰 상수 만들기 (U-type) |

> **DV 메모**: RISC-V는 검증 생태계가 강력하다. **표준 자체에 compliance/ACT test suite가 있고**, 오픈소스 reference model(Spike, Sail 등 ISA simulator)이 있어 — DUT의 실행 결과를 golden ISA simulator와 **lock-step**으로 비교하는 게 표준 검증 방법이다. 정확히 Unit 5의 instruction-level scoreboard고, RISC-V는 그 golden model이 공짜로 주어진다. (RDMA에 IB spec compliance test가 있는 것과 같은 구조)

## 5. ISA 검증의 핵심 — DV 관점 종합

1. **명령어별 정확성** — golden ISA model과 lock-step 비교 (PC/RegFile/Memory).
2. **인코딩 coverage** — 모든 포맷, 모든 funct 조합, **illegal encoding은 trap 나나**.
3. **레지스터 corner** — `x0` 특수성, 같은 레지스터 read/write.
4. **메모리 모델** — alignment, endianness, 비정렬 접근 예외.
5. **예외/인터럽트** — illegal instruction, misaligned, page fault 등 모든 trap path.
6. **데이터 corner** — 오버플로우, 부호/무부호, 최대/최소값 (Unit 3 연결).

> **ISA 매뉴얼이 곧 검증 스펙이다.** 모호한 스펙 = 검증 불가능한 스펙.

## 핵심 정리

> 이 유닛의 진짜 메시지 — 꼭 기억할 3가지.

1. **ISA = 하드웨어와 소프트웨어의 계약(메뉴판).** architecture(무엇)와 microarchitecture(어떻게)를 가르는 경계. 인터페이스를 고정하면 양쪽이 독립 진화한다.
2. **RISC vs CISC** = "단순하고 많이"(RISC, IC↑CPI↓) vs "복잡하고 적게"(CISC, IC↓CPI↑). RISC 철학이 이겼고, x86조차 속은 RISC(μop).
3. **RISC-V = 오픈·모듈식·깨끗한 RISC ISA.** golden ISA model로 lock-step 검증 가능. **ISA 매뉴얼이 곧 검증 스펙이다.**

## 🔌 검증 관점

- **경계가 검증 레벨을 가른다:** ISA(아키텍처) 검증 = 명령어가 스펙대로 결과를 내나(architectural state). 마이크로아키텍처 검증 = forwarding·캐시·분기예측 등 내부 동작.
- **golden ISA model lock-step:** RISC-V는 Spike/Sail 등 오픈소스 reference model + 표준 compliance/ACT test가 공짜 → DUT vs golden을 명령어 단위로 비교(Unit 5의 instruction-level scoreboard).
- **ISA 6개 조항 = coverage 항목:** 명령어/인코딩/레지스터/데이터타입/메모리모델/예외. ISA 매뉴얼이 곧 verification plan의 뼈대.
- **인코딩 coverage:** 모든 포맷·funct 조합 + **illegal encoding은 반드시 trap.** immediate 재조립(B/J 셔플+부호확장)이 단골 버그.
- **레지스터/메모리 corner:** `x0`(읽으면 0/쓰면 무시), 같은 레지스터 read/write, alignment·endianness·비정렬 예외.
- **negative/security가 functional만큼 중요:** 특권 레벨(U/S/M) — "권한 없는 접근이 정말 막히나"는 negative test가 핵심. 특권 명령어 × 낮은 권한 exhaustive, CSR 권한 매트릭스, trap 전이.
- **hardwired control은 formal 친화적:** 조합 논리라 입력 공간 유한 → formal verification 강력. RISC-V가 검증하기 쉬운 이유 중 하나.

## 📎 부록 — 이 단원에서 나온 질문들

### Q1. "hardwired에 대해 설명해줘"

Unit 5의 **Control Unit**과 Unit 7의 **RISC vs CISC**를 잇는 다리다. "control 신호를 **어떻게 만들어내느냐**"에 대한 두 방식 중 하나가 hardwired다.

#### 0. 맥락 — Control Unit이 하는 일

decode 단계의 Control Unit이 명령어(opcode)를 보고 **control 신호 뭉치**(`ALUOp`, `RegWrite`, `MemRead`, `ALUSrc`...)를 뿜어낸다. 질문은: **"opcode가 들어오면 → 어떤 control 신호를 켤지"를 결정하는 그 장치를 실제로 어떻게 만드나?**

답이 두 가지: ① **Hardwired control** ② **Microprogrammed control**

#### 1. Hardwired Control — "논리 회로로 직접 박아넣기"

> opcode → control 신호의 대응 관계를 **순수 조합 논리 회로(AND/OR 게이트)** 로 직접 구현한 것.

"이 opcode면 이 신호들을 켠다"는 규칙을 **게이트와 배선으로 물리적으로 굳혀(hardwire)** 놓는 것.

```text
opcode 비트 ──►┌──────────────────────┐──► RegWrite
funct  비트 ──►│   조합 논리 회로        │──► ALUSrc
              │  (AND/OR 게이트 다발)   │──► MemRead
              │  = 진리표를 회로로 구현   │──► ALUOp
              └──────────────────────┘──► ... (모든 control 신호)
```

예시 — "RegWrite는 언제 1이 되나?":

```text
RegWrite = 1  ←  명령어가 R-type 이거나, I-type(addi)이거나, load 일 때
→ 회로로: RegWrite = (opcode==R-type) OR (opcode==addi) OR (opcode==load)
          이걸 OR 게이트 하나로 배선!
```

control 신호 하나하나를 불 논리식으로 적은 다음 게이트로 합성. 일종의 **거대한 진리표를 회로로 만든 것**.

| 장점 | 단점 |
|---|---|
| **빠르다** — 게이트 한두 단계만 통과 (클럭 1번) | **수정이 어렵다** — 명령어 추가/변경 시 회로 재설계 |
| 단순한 ISA에 최적 → **RISC에 딱 맞음** | 명령어가 복잡하면 회로가 거대·복잡 |

#### 2. 대조군 — Microprogrammed Control

> control 신호를 회로로 박는 대신, **작은 메모리(control store)에 "신호 패턴"을 표처럼 저장**해두고 opcode로 lookup.

- **Hardwired** = 요리법을 **손에 외워서 반사적으로** (빠르지만 새 요리 배우려면 훈련 다시)
- **Microprogrammed** = **요리책(메모리)을 펼쳐 한 줄씩 읽으며** (느리지만 페이지만 바꾸면 새 요리)

| | **Hardwired** | **Microprogrammed** |
|---|---|---|
| 구현 | 조합 논리 회로 (게이트) | 메모리(control store)의 마이크로코드 |
| 속도 | 빠름 | 느림 (메모리 읽기 필요) |
| 유연성 | 낮음 (회로 재설계) | 높음 (마이크로코드만 수정) |
| 적합 | **RISC** (단순 명령어) | **CISC** (복잡 명령어) |

#### 3. ⭐ 왜 RISC vs CISC와 직결되나

- **CISC(x86)**: 명령어가 복잡·다양 → 회로로 박기엔 너무 큼 → **microprogrammed**가 자연스러움.
- **RISC(RISC-V)**: 명령어가 단순·고정길이 → control 신호가 단순 → **hardwired로 빠르게**. RISC가 빠른 이유 중 하나 — decode/control이 hardwired라 클럭 1번에 끝나서 **CPI가 작고 pipeline에 유리**.

> RISC가 "명령어를 단순하게 유지하자"고 한 진짜 이유 중 하나가 **"그래야 control을 hardwired로 빠르게 만들 수 있다"** 다.

**현대의 반전**: 현대 x86은 **하이브리드** — 자주 쓰는 단순 명령어는 **hardwired**, 드물고 복잡한 명령어는 **microcode**. microcode가 메모리(고칠 수 있는 저장소)에 있어서 **출하 후 패치 가능**(Spectre 같은 버그를 마이크로코드 업데이트로 수정).

#### 🔌 DV 메모

1. **Hardwired control 검증** = 본질적으로 **조합 논리 검증**. 입력 공간이 유한해서 **formal verification이 특히 강력**.
2. **Microprogrammed control 검증** = control store 내용(데이터) + 시퀀싱 검증.
3. hardwired는 상태가 적어 검증 공간이 작고 formal 친화적. RISC-V가 검증하기 쉬운 이유 중 하나.
4. **RDMA 비유**: hardwired ↔ fixed-function 하드웨어 파이프라인(빠르지만 고정), microcode ↔ 펌웨어/프로그래머블 엔진(느리지만 유연·패치 가능).

**한 줄 요약**: **Hardwired control** = Control Unit을 **조합 논리 회로(게이트)로 직접 박아넣은 방식**. **빠르지만 수정 어려움** → 단순한 **RISC에 최적**. 반대는 microprogrammed(메모리에 마이크로코드, 느리지만 유연 → CISC). 현대 CPU는 둘을 섞어 씀.

### Q2. "RISC와 RISC-V의 차이는 뭐야?"

> **RISC는 "철학/분류"이고, RISC-V는 그 철학을 따르는 "구체적인 제품(ISA) 하나"다.**

"포유류 vs 강아지" 관계와 똑같다. RISC가 포유류(큰 범주), RISC-V는 그중 한 종(강아지).

#### 1. RISC = 설계 철학 (카테고리)

**RISC** = **R**educed **I**nstruction **S**et **C**omputer. 특정 제품이 아니라 ISA를 설계하는 **방침/사상**(명령어 단순, 고정 길이, load/store만 메모리 접근, 레지스터 多...).

이 철학을 따르는 ISA는 여러 개:

```text
├── MIPS      (1980년대, 학계 유명)
├── ARM       (스마트폰/태블릿, 애플 M칩)
├── SPARC     (Sun/Oracle 서버)
├── POWER     (IBM 서버)
├── RISC-V    ← 막내, 오픈소스    ★
```

#### 2. RISC-V = 구체적인 ISA 하나 (제품)

RISC 철학을 따르는 **실제 명령어 집합 표준 하나**. 2010년 UC Berkeley 시작. **"V(5)"** 는 Berkeley의 **5번째 RISC 설계**(RISC-I~IV에 이은 다섯 번째)라는 뜻. 명령어 비트 인코딩, 레지스터 32개, R/I/S/B/U/J 포맷이 **명세서에 박혀 있다**. 반면 그냥 "RISC"는 구체적 비트를 정의하지 않음(철학이니까).

#### 3. RISC-V만의 특별한 점 (다른 RISC 형제들과의 차이)

| | **ARM, MIPS** | **RISC-V** |
|---|---|---|
| 소유 | 회사 소유 (ARM은 ARM社, 라이선스비) | **오픈소스, 무료** |
| 사용료 | 칩 만들려면 돈 | **공짜** |
| 설계 방식 | 한 회사가 통제 | **개방형 표준 (RISC-V International)** |
| legacy 부담 | 수십 년 누적 호환성 짐 | **2010년 시작, 깨끗** |
| 모듈성 | 비교적 고정 | **모듈식** (RV32I + 확장 골라 붙임) |

> RISC-V = "RISC 철학 + 오픈소스 + 현대적 설계". **ISA계의 리눅스**.

#### 4. 핵심 관계 그림

```text
        RISC (철학/분류 — "단순한 명령어로 만들자")
       ╱      │       │        │         ╲
    MIPS    ARM    SPARC    POWER    RISC-V
   (제품)  (제품)  (제품)   (제품)   (제품, 오픈소스)
```

#### 5. 흔한 오해

- ❌ "RISC-V는 RISC의 5번째 버전" → RISC는 버전 없는 철학. "V"는 Berkeley의 5번째 *설계 프로젝트*.
- ❌ "RISC-V가 RISC를 대체" → 카테고리와 제품은 대체 관계 아님. RISC-V는 RISC 안에 있음.
- ✅ "RISC-V는 RISC 철학을 따르는 여러 ISA 중 하나이고, 오픈소스라는 점이 특별하다."

#### 🔌 DV 메모

- **검증 스펙(golden)은 "RISC"가 아니라 "RISC-V 명세서"여야 한다.** RISC는 철학이라 "정답"을 정의 안 함.
- **RISC-V가 검증 친화적인 이유**: 오픈소스라서 **golden ISA simulator(Spike, Sail)가 공짜로 공개**, **표준 compliance test suite(RISC-V ACT)** 존재 → "DUT vs golden model lock-step 비교"를 누구나 바로 사용.
- RDMA 비유: "RISC" = "RDMA라는 개념", "RISC-V" = "IB spec / RoCEv2 spec처럼 비트까지 확정된 구체 표준".

**한 줄 요약**: **RISC = 설계 철학(범주)**, **RISC-V = 그 철학을 따르는 구체적 오픈소스 ISA 하나**. ARM·MIPS도 같은 RISC 형제지만 RISC-V만 무료·오픈·현대적이라 교육·검증 표준이 됐다.

### Q3. "근데 오픈소스다?"

여기 **중요한 뉘앙스**가 있다. "오픈소스"가 소프트웨어에서 익숙한 의미랑 살짝 다르다.

#### 1. 오픈된 건 "ISA 명세서(설계도/규칙)"지 "칩"이 아니다

> RISC-V에서 무료·공개인 것은 **ISA 사양(명령어 목록과 인코딩 규칙 = 메뉴판)** 이다. 그걸로 **실제 만든 칩(주방)은 비공개·유료여도 된다.**

요리법(레시피)은 누구나 무료로 쓰는데, 그 레시피로 만든 음식을 파는 식당은 각자 사업.

```text
┌─────────────────────────────────────┐
│  RISC-V ISA 명세서 (메뉴판/레시피)     │  ← 무료, 공개, 누구나 사용 ✅
└─────────────────────────────────────┘
              ↓ 이걸 보고 각자 칩 설계
┌──────────┬──────────┬───────────────┐
│ SiFive칩  │ 알리바바칩 │  네가 만든 칩   │  ← 각자 비공개/유료 가능 ✅
└──────────┴──────────┴───────────────┘
```

#### 2. "오픈소스 SW"와 뭐가 다른가

| | **오픈소스 SW (리눅스)** | **오픈 ISA (RISC-V)** |
|---|---|---|
| 공개되는 것 | 소스 코드 (실제 구현물) | **사양/규칙** (구현물 아님) |
| 만든 결과물 | 그 코드 자체가 결과물 | 사양은 "설계 기준", 칩은 따로 만듦 |
| 만든 걸 비공개로? | 라이선스 제약(GPL 등) | **칩 구현은 완전히 비공개 가능** |

그래서 엄밀히는 "오픈소스"보다 **"오픈 스탠다드(개방형 표준)"** 또는 **"로열티 프리(royalty-free) ISA"** 가 더 정확. 상용 RISC-V 칩의 고성능 코어 RTL은 비공개다.

#### 3. "무료"가 정확히 뭐가 무료냐 — ARM과 비교

**ARM 칩:** ① ARM社 라이선스 비용(선불) ② 칩 팔 때마다 로열티 ③ ARM 규칙만 따라야 함
**RISC-V 칩:** ① 라이선스 = 0원 ② 로열티 = 0원 ③ 커스텀 명령어 추가 가능

→ 스타트업, 대학, 빅테크(구글·엔비디아)가 자체 칩에 RISC-V 채택. **"ISA 사용료라는 진입장벽이 사라졌다"** 가 핵심.

#### 4. 누가 관리하나

- **RISC-V International** 비영리 재단(스위스 소재)이 표준 관리.
- 회원사(인텔, 구글, 엔비디아, 알리바바, 삼성 등)들이 "기본 명령어 표준"을 합의·고정.
- **기본(base + 표준 확장)은 고정** → 호환성 보장. 그 위 **커스텀 영역은 자유** → 유연성.

#### 5. 왜 혁명적인가

CPU의 "언어(ISA)"는 지금까지 항상 누군가의 사유재산(x86=Intel/AMD, ARM=ARM社)이었다. RISC-V는 **"CPU의 언어를 공공재로 만들자"** 는 시도. 그래서 "ISA계의 리눅스".

#### 🔌 DV 메모

1. **Golden reference가 공짜로 열려 있다** — Spike, Sail 같은 ISA simulator가 오픈소스. ARM/x86은 정확한 동작 모델이 비공개/NDA.
2. **표준 compliance test(RISC-V ACT)가 공개** — "내 칩이 표준 지키나"를 표준 테스트로 검증.
3. **사양이 투명 = 모호함이 적다** — 단, 커스텀 확장을 붙이면 그 부분은 *네가* 스펙을 써야 하고 곧 *네가* 검증 스펙의 저자가 됨.
4. **RDMA 비유**: IBTA가 IB spec을 공개 관리하는 것과 RISC-V International이 같은 역할. "공개 표준 + 비공개 구현 + 표준 compliance 검증" 구도 그대로.

**한 줄 요약**: RISC-V가 오픈소스라는 건 **"ISA 명세서(메뉴판/규칙)가 무료·공개"** 라는 뜻이지 칩까지 공개·무료라는 게 아니다. ARM처럼 라이선스비·로열티 없이 누구나 CPU의 "언어"를 쓰게 한 **개방형 표준(royalty-free ISA)**. DV 입장에선 golden model·compliance test가 공짜로 열려 있다는 게 큰 이득.

### Q4. "특권레벨 관련해서도 간단하게 설명해줘"

ISA의 **"누가 무엇을 할 수 있나"** 를 정하는 부분.

#### 0. 왜 필요한가

> CPU의 모든 명령어/자원을 **아무 코드나 다 건드리면 안 된다.** 그래서 "권한 등급"을 나눠서, **높은 등급만 위험한 일(메모리 설정, 하드웨어 제어, 다른 프로그램 중단)을 할 수 있게** 제한.

비유: **회사 출입증 등급**. 일반 직원증(내 자리만) < 관리자증(서버실도) < 마스터키(모든 문 + 보안 설정). 직원이 마스터키 일을 하려면 관리자에게 "요청"해야 한다.

#### 1. RISC-V의 3가지 특권 레벨

```text
   권한 높음 ▲
   M-mode (Machine)   ★최고 권한   ← 펌웨어, 부트로더 (가장 먼저 실행)
   S-mode (Supervisor) 중간 권한   ← OS 커널 (리눅스 등)
   U-mode (User)      최저 권한    ← 일반 응용 프로그램
   권한 낮음 ▼
```

| 레벨 | 약자 | 누가 도나 | 할 수 있는 일 |
|---|---|---|---|
| **Machine** | M | 펌웨어/부트로더 | **모든 것** — 하드웨어 직접 제어 |
| **Supervisor** | S | OS 커널 (리눅스, 윈도우) | 가상 메모리, 프로세스 스케줄링, 디바이스 |
| **User** | U | 일반 앱 (브라우저, 게임) | 자기 계산만. 위험한 일은 OS에 "요청" |

(확장으로 **H-mode**, Hypervisor도 있음 — 가상머신 여러 개.)

**부팅 순서**: 전원 ON → **M-mode**(펌웨어) 가장 먼저 → OS 띄우고 **S-mode**로 → OS가 앱 띄우며 **U-mode**로. 권한을 점점 **내려주며** 부팅.

#### 2. 핵심 메커니즘 — "낮은 권한이 위험한 일을 하려면?"

→ **시스템 콜(system call) = 권한 상승 요청**

```text
U-mode 앱:  "파일 읽어주세요!"  ──(ecall 명령어)──►  trap 발생
                                            권한이 S-mode로 점프
S-mode OS:  요청 검사 → 안전하면 디스크 읽어서 결과 전달 → U-mode로 복귀
```

- **`ecall`**: 낮은 권한이 높은 권한에게 요청하는 명령어. 자동으로 **trap**(권한 상승 + 정해진 핸들러로 점프).
- **trap**: 권한 경계를 넘는 안전한 통로. OS가 정해놓은 진입점으로만 들어감.

> **U-mode는 절대 스스로 권한을 못 올린다.** 오직 "요청(trap)"을 통해 높은 권한 코드가 **검사한 뒤 대신 해주는** 방식. 보안의 근간.

#### 3. 무엇이 권한별로 나뉘나 — 특권 명령어 & CSR

- **특권 명령어**: 높은 권한에서만 실행 (`sret/mret`, `sfence.vma`, 인터럽트 제어...). U-mode가 실행 시도 → **illegal instruction 예외(trap)**.
- **CSR (Control and Status Register)**: CPU 설정·상태 특수 레지스터. 권한 레벨마다 접근 가능한 CSR이 다름 (`mstatus`, `satp`=가상메모리 페이지테이블 주소 등). 낮은 권한은 높은 권한 CSR 접근 불가.

> Unit 14(가상 메모리)와 직결 — 가상 메모리 설정(`satp`)은 S-mode 권한이라 앱이 마음대로 메모리 매핑을 못 바꿈.

#### 4. 왜 중요한가 — 보안과 격리

1. **프로세스 격리**: 한 앱(U-mode)이 죽거나 악성이어도 다른 앱·OS를 못 건드림.
2. **OS 보호**: 앱이 OS 커널/하드웨어를 직접 못 만짐 → 시스템 안정.
3. **공격 차단**: 악성 코드가 U-mode에 갇힘. (해커는 "권한 상승(privilege escalation)" 취약점을 노림.)

#### 🔌 DV 메모

1. **권한 경계 위반 테스트 (1순위 negative test)**: "U-mode에서 특권 명령어/CSR 접근 → 반드시 illegal instruction trap?" 안 터지면 **보안 구멍**. 모든 특권 명령어 × 낮은 권한 조합 exhaustive.
2. **권한 전이 검증**: U→(ecall)→S→(mret/sret)→U 정확성. trap 시 권한·PC·상태(CSR) 저장/복원. nested trap corner.
3. **CSR 접근 권한 매트릭스**: 각 CSR을 각 권한에서 읽기/쓰기 → 허용/거부가 스펙대로. 특권 스펙에 매트릭스 정의됨.
4. **RDMA 비유**: RDMA도 QP/MR에 권한 비트(local/remote read/write)가 있어 "권한 없는 접근은 거부+에러"를 검증. **negative/security test가 functional만큼 중요**.

> 특권 레벨 검증은 "되는 것(positive)"보다 **"안 되어야 하는 게 정말 막히나(negative)"** 가 훨씬 중요. 보안은 "차단"의 정확성.

**한 줄 요약**: 특권 레벨 = CPU의 **권한 등급 시스템**. RISC-V는 **U(앱) < S(OS) < M(펌웨어)** 3단계로, 낮은 권한은 위험한 명령어/자원을 직접 못 건드리고 **trap(ecall)으로 높은 권한에 요청**. 프로세스 격리·보안의 근간이고, DV에선 "권한 없는 접근이 차단되나"는 negative test가 핵심.

### Q5. "이건 OS에 해당하는 내용 같긴 한데, supervisor가 그냥 OS라 생각하면 되는 용어 같은 거야?"

절반은 맞고, 한 가지 중요한 구분이 있다.

> **"Supervisor 모드 = OS 커널이 *실행되는* 권한 레벨"** 은 맞다. 근데 **"Supervisor라는 단어 = OS"** 는 아니다. **하나는 하드웨어, 하나는 소프트웨어**다.

#### 1. 핵심 구분 — "방(level)"과 "거주자(OS)"는 다르다

| | **Supervisor 모드 (S-mode)** | **OS** |
|---|---|---|
| 정체 | **하드웨어가 제공하는 권한 레벨** (ISA가 정의) | **그 레벨에서 도는 소프트웨어** |
| 누가 만듦 | CPU 설계자 (RISC-V 스펙) | OS 개발자 (리눅스, 윈도우...) |
| 비유 | 건물의 "관리자 전용 층" | 그 층에 입주한 "관리 회사" |

**S-mode = 건물의 한 층(빈 방)**, **OS = 그 방에 입주한 세입자**. 방은 CPU가 제공하고 누가 입주할지는 자유. **S-mode라는 방은 OS가 없어도 존재**한다.

#### 2. 왜 "Supervisor = OS"라고 못 박으면 안 되나 — 3가지

**(1) OS는 한 레벨에만 있지 않다**

```text
리눅스 "커널"      → S-mode  (메모리 관리, 스케줄러)
리눅스 "유저 공간" → U-mode  (셸, 데몬, 라이브러리)
```

OS의 핵심(커널)만 S-mode, 다른 부분은 U-mode.

**(2) S-mode에 OS 말고 다른 게 들어갈 수도** — 작은 임베디드는 OS 없이 펌웨어(M-mode)만 쓰기도. S-mode는 "OS가 *주로* 쓰는 방"이지 "OS 전용 방"이 아님.

**(3) 진짜 최강자는 M-mode (OS가 아님)**

```text
M-mode (최고권한) ← OS도 못 건드리는 펌웨어/부트로더 (OpenSBI 등)
   ↑ 위에 OS를 "올려놓고" 관리
S-mode           ← OS 커널 (리눅스)
U-mode           ← 앱
```

OS(S-mode)조차 어떤 일은 M-mode에 요청. **OS는 권한 계층의 *중간 한 칸*을 차지하는 입주자**일 뿐.

#### 3. 실용적으로는?

> **"S-mode ≈ OS 커널이 도는 곳"** 으로 이해해도 **90%는 맞다.**

다만 정확히는: **S-mode** = 하드웨어가 정의한 **권한 등급(메커니즘)**, **OS 커널** = 그 등급을 **활용하는 소프트웨어(정책)**. "메커니즘 vs 정책"의 구분. **CPU가 권한 레벨이라는 "도구"를 주고, OS가 그 도구를 "사용"한다.**

#### 🔌 DV 메모

- DV가 검증하는 건 **"방(메커니즘)"이지 "입주자(OS)"가 아니다.** CPU/ISA 검증 대상은 S-mode 권한 레벨이 스펙대로 동작하나(특권 명령어 접근 제어, CSR 권한, trap 전이)지 "리눅스가 잘 도나"가 아님.
- ISA 검증은 OS를 안 띄우고 **권한 레벨만 단독으로 bare-metal** 테스트. 입주자 없이 빈 방의 정확성 검증.
- RDMA 비유: 검증 대상은 HW가 제공하는 권한/보호 메커니즘(MR 권한 비트, QP 접근 제어)이지 그 위 응용(MPI, 스토리지 SW)이 아님. "메커니즘은 HW 보장, 정책은 SW 결정, DV는 메커니즘 검증" 구도 동일.

**한 줄 요약**: **Supervisor(S-mode)는 "OS 커널이 *실행되는* 하드웨어 권한 레벨"** 이지 "OS"라는 소프트웨어 자체는 아니다. 큰 그림에선 "S-mode ≈ OS 커널 자리"로 봐도 되지만, 정확히는 **CPU가 제공하는 권한 등급(메커니즘)** 이고 OS는 그걸 *쓰는* 입주자다. (OS는 S+U 여러 레벨에 걸쳐 있고, OS보다 위엔 M-mode 펌웨어가 또 있음.)

### Q6. "비트 필드는 왜 모든 format에서 같은 자리에 놓는 거야?"

RISC-V 설계의 **가장 영리한 결정** 중 하나.

> **레지스터 번호(rs1, rs2, rd)와 opcode를 항상 같은 자리에 두면, 명령어 종류를 다 해석하기 *전에* 레지스터 읽기를 미리 시작할 수 있어서 — 디코드가 빨라지고 회로가 단순해진다.**

#### 1. 무엇이 같은 자리에 고정돼 있나

```text
        31      25 24   20 19   15 14  12 11    7 6      0
R-type: │ funct7  │ rs2  │ rs1  │funct3│  rd   │ opcode │
I-type: │   imm[11:0]    │ rs1  │funct3│  rd   │ opcode │
S-type: │imm[11:5]│ rs2  │ rs1  │funct3│imm[4:0]│ opcode │
B-type: │ imm     │ rs2  │ rs1  │funct3│ imm   │ opcode │
U-type: │      imm[31:12]              │  rd   │ opcode │
J-type: │      imm[20:1...]            │  rd   │ opcode │
                          ↑      ↑      ↑      ↑       ↑
                         rs1   funct3   rd          opcode
                       [19:15] [14:12] [11:7]       [6:0]
                       항상     항상     항상         항상
```

| 필드 | 항상 있는 위치 | 어떤 포맷에 등장 |
|---|---|---|
| **opcode** | `[6:0]` | **전부** |
| **rd** | `[11:7]` | R, I, U, J |
| **funct3** | `[14:12]` | R, I, S, B |
| **rs1** | `[19:15]` | R, I, S, B |
| **rs2** | `[24:20]` | R, S, B |

**rs1, rs2, rd의 위치가 절대 안 변한다.** R이든 S든 B든 "첫 번째 소스 레지스터"는 무조건 [19:15].

#### 2. 결정적 이유: "타입을 몰라도 레지스터를 읽을 수 있다"

ID 단계에서 ① 명령어 해석 ② 레지스터 읽기가 **동시에** 일어난다. 레지스터 위치가 가변이면 "타입 먼저 알아야" 어디서 읽을지 정함 → 느려짐:

```text
❌ 가변이면 (순차 = 느림):
   [opcode 해석] → [타입 판별] → [rs1 위치 계산] → [레지스터 읽기]

✅ 고정이면 (병렬 = 빠름):
   [opcode 해석] ─┐
                  ├─► 동시에!  ("타입이 뭐든 rs1은 [19:15]니까 그냥 읽어")
   [레지스터 읽기]─┘
```

비트 [19:15], [24:20]을 **무조건 레지스터 파일에 던져 읽기 시작**할 수 있다. 그 명령어가 레지스터를 안 쓰면 결과를 버리면 그만 — **"일단 읽고 본다(speculative read)"**.

> 레지스터 읽기는 시간이 걸리는 작업. 타입 판별을 안 기다리고 즉시 시작하면 **클럭 주기(T_clock)를 줄일 수 있다** (Iron Law!).

#### 3. 부가 이유

**(1) opcode가 항상 [6:0]**: 명령어 받자마자 종류 판단을 시작하려면 종류 정보가 항상 같은 자리에.
**(2) 회로 단순화**: 필드 위치 고정 → 비트 뽑는 데 **MUX 거의 불필요**, 그냥 배선 직결(`rs1 = instruction[19:15]`). hardwired control이 단순해지는 것과 같은 맥락.

#### 4. ⭐ 대가(trade-off) — 그래서 immediate가 흩어진다

레지스터 자리를 고정하니 **남는 비트(immediate)는 들쑥날쑥한 자리로 밀려난다.**

```text
S-type: immediate가 [31:25]랑 [11:7] 두 조각으로 쪼개짐
        └─ rs1/rs2/funct3를 고정 자리에 양보하느라 연속 공간이 없어 두 동강
```

설계자 선택: **"immediate 재조립의 약간의 수고를 감수하더라도 레지스터 읽기를 빠르게 하는 게 훨씬 이득."** 레지스터 읽기는 모든 명령어가 자주 하고, immediate 재조립은 간단한 배선(wire shuffle)으로 공짜에 가깝다.

> immediate 비트도 아무렇게나 흩은 게 아니라 — **부호 비트(MSB)는 항상 [31]에 고정**(부호확장을 타입 판별 전 시작). "자주 쓰는 건 고정, 덜 급한 것만 재배치" 원칙.

#### 5. 통찰 — RISC 철학의 결정체

단순한 디코드(RISC) + 빠른 클럭/작은 CPI(Iron Law) + 단순한 hardwired 회로 + pipeline 친화. x86은 명령어 길이부터 가변(1~15B)이라 "필드가 어디 있는지"조차 앞바이트를 다 읽어야 알아 → 디코드 악명 높게 복잡. RISC-V는 "자주 쓰는 필드는 항상 같은 자리" 규칙 하나로 디코드를 거의 공짜로.

#### 🔌 DV 메모

1. **필드 추출 checker가 단순·통일** — 어떤 명령어든 `rs1 = instr[19:15]`. 디버깅 시 원인 분리 쉬움.
2. **immediate는 여전히 1순위 버그 지점** — 흩어진 immediate 재조립(특히 B/J 비트 셔플 + 부호확장)이 제일 자주 틀림. directed test 집중.
3. **speculative register read 검증** — "타입 모르고 일단 읽은" 값이 안 쓰는 경우(U-type엔 rs1 없음) 제대로 무시/버려지나.
4. **RDMA 비유**: 공통 필드(QP번호, opcode)는 고정 위치(BTH), 가변 부분만 뒤쪽 가변 헤더. 자주 파싱하는 공통 필드는 고정 오프셋 → 파서가 분기 없이 빠르게. RISC-V 명령어 = "고정 헤더 + 재배치된 immediate"인 패킷.

**한 줄 요약**: rs1/rs2/rd/opcode를 **모든 포맷에서 같은 자리에 고정**하는 이유는 — **타입을 다 해석하기 전에 레지스터 읽기를 즉시·병렬로 시작**할 수 있어서. 디코드↑, 회로 단순(MUX 불필요), pipeline 유리. 대가로 **immediate가 흩어지지만** 간단한 배선으로 해결되니 남는 장사. RISC 철학의 결정체.

### Q7. "왜 x0을 hardwired zero로 두는 거야? 그리고 x0이란 RISC-V의 x0라는 명령어인 거지?"

#### 오해 정정: x0은 명령어가 아니라 레지스터

> **x0은 "명령어"가 아니라 "레지스터"다.** RISC-V의 32개 레지스터(x0~x31) 중 **0번 레지스터**.

`add`, `lw`가 명령어(동작)고, `x0`~`x31`은 데이터를 넣고 빼는 **저장소(레지스터)**. (Unit 5의 rs1/rs2/rd가 가리키는 그 32개 중 0번)

#### 1. 무슨 뜻 — "x0은 영원히 0"

```text
x1 ~ x31 : 보통 레지스터. 값을 쓰면 저장됨.
x0       : 특수. 읽으면 항상 0. 쓰면 그냥 버려짐 (아무 일 안 일어남)

addi x0, x0, 99    →  x0에 99를 쓰라 해도 x0은 여전히 0. (쓰기 무시)
add  x5, x0, x6    →  x0(=0) + x6 = x6.  즉 "x6을 x5로 복사"
```

물리적으로 x0은 **저장 공간이 없다.** "읽으면 0이 나오도록 배선(hardwire)"돼 있고 "쓰기 신호는 무시". 그래서 hardwired **zero**.

#### 2. 왜 레지스터 하나를 0 전용으로? — 이득이 엄청나서

**0이라는 상수와 "버리는 곳"이 어마어마하게 자주 필요**해서, 이걸 레지스터로 제공하면 **명령어 종류를 확 줄일 수 있다.**

**이득 ① — "상수 0"을 공짜로 제공**: 0은 가장 많이 쓰는 상수. x0 읽으면 끝.

**이득 ② — 수많은 "의사명령어(pseudo-instruction)"를 공짜로 만듦**:

| 쓰고 싶은 동작 | 실제 명령어 (x0 활용) | 설명 |
|---|---|---|
| `mv x5, x6` (복사) | `addi x5, x6, 0` / `add x5, x6, x0` | x6 + 0 |
| `li x5, 0` | `addi x5, x0, 0` | 0 + 0 |
| `nop` (무동작) | `addi x0, x0, 0` | 결과를 x0에 버림 |
| `neg x5, x6` (부호 반전) | `sub x5, x0, x6` | 0 − x6 |
| `j label` (무조건 점프) | `jal x0, label` | 복귀주소를 x0에 버림 |
| `beqz x5, L` (0이면 분기) | `beq x5, x0, L` | x5 == 0 비교 |
| `ret` (함수 복귀) | `jalr x0, 0(x1)` | 복귀주소 저장 안 함 |

> RISC 철학의 결정체 — **"명령어 종류를 늘리지 말고, 기존 명령어 + x0 조합으로 해결."** 디코더에 mv/nop/neg 회로를 따로 안 만들어도 됨.

**이득 ③ — "결과를 버리는 곳"**: 부수효과만 원하고 결과값은 불필요할 때 (`jal x0, label`: 점프만, 복귀주소 버림). x0이 "쓰면 사라지는 쓰레기통".

#### 3. 왜 하필 "0"이고 "x0"인가

- **값 0**: 비교(`== 0`), 초기화, 부호반전 등에서 압도적으로 자주 쓰임.
- **0번 자리**: 레지스터 번호 `00000`(5비트 전부 0)이 회로에서 "전부 0이면 → 0 출력, 쓰기 무시"로 검출하기 쉬움.

#### 4. 통찰 — 작은 결정, 큰 효과

**손해는 레지스터 1개(31개로 충분), 이득은 상수 0 + mv/nop/neg/j/ret 등 수십 개 의사명령어 + 디코더 단순화.** 압도적으로 남는 장사라 거의 모든 RISC ISA가 이 트릭 사용.

#### 🔌 DV 메모

1. **읽기 = 항상 0 검증**: rs1=x0/rs2=x0일 때 무조건 0으로 읽히나 (`add x5, x0, x0` → x5는 반드시 0).
2. **쓰기 = 무시 검증 (제일 중요)**: rd=x0인 모든 명령어가 정말 x0을 안 바꾸나 (`addi x0, x0, 999` 후 x0이 0). 버그 나면 0이라 믿고 쓴 모든 코드가 깨져 치명적. **모든 명령어 × rd=x0** 조합.
3. **pseudo-instruction 등가성**: `mv x5, x6`가 `add x5, x6, x0`와 동일 결과? assembler/golden model의 lowering 검증.
4. **hazard corner (Unit 8 예고)**: "x0에 쓰는 명령어" 다음 "x0 읽는 명령어"에 forwarding이 **0을 forward하면 안 됨**(x0은 실제로 안 써졌으니까). forwarding 로직 검증 corner.
5. **RDMA 비유**: reserved 필드/특수 핸들(특정 QP번호, well-known address)에서 "쓰기 무시 / 읽으면 고정값" 검증과 같은 부류. **"안 변해야 하는 게 정말 안 변하나"는 negative test.**

**한 줄 요약**: **x0은 명령어가 아니라 RISC-V의 0번 레지스터**고, **읽으면 항상 0 / 쓰면 무시**되도록 고정(hardwired zero). 이유는 상수 0을 공짜로 주고, `mv·nop·neg·j·ret` 같은 **수많은 의사명령어를 회로 추가 없이** 기존 명령어+x0 조합으로 구현하기 위해서. 레지스터 1개 손해로 명령어 수십 개를 절약하는 RISC 철학의 결정체. DV에선 "읽으면 0 / 쓰면 무시"가 정말 보장되나가 핵심 corner test.
