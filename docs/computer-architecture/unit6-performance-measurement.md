# Unit 6 — '빠르다'를 재는 법 (How to Measure Performance)

> 핵심 질문: "빠른 CPU"란 정확히 뭘 말하나? 클럭? IPC? 무엇으로 재나? (latency vs throughput · CPI · Iron Law)

## 0. 가장 흔한 함정부터 — "빠르다"는 한 단어가 아니다

누가 "이 차 빠르다"고 하면 두 가지 뜻일 수 있다:

- **0→100km/h 가속이 빠르다** (한 대가 얼마나 빨리 반응하나)
- **고속도로에서 시간당 차를 더 많이 나른다** (전체 처리량)

이게 컴퓨터 성능의 두 축, **latency**와 **throughput**이다. 둘은 **다르고, 종종 트레이드오프**다. 이걸 안 나누면 성능 얘기가 전부 엉킨다.

## 1. Latency vs Throughput (지연시간 vs 처리량)

| | **Latency (지연시간)** | **Throughput (처리량)** |
|---|---|---|
| 정의 | **하나**의 작업을 끝내는 데 걸리는 시간 | **단위 시간당** 끝내는 작업 수 |
| 단위 | 초, ns, 클럭 수 | 작업/초, IPC, GB/s |
| 질문 | "이 명령어 하나 언제 끝나?" | "초당 몇 개 처리해?" |
| 비유 | 차 한 대의 통과 시간 | 도로 전체의 시간당 통행량 |

### 핵심: 둘은 독립적이고, 자주 상충한다

**Pipeline이 완벽한 예시다** (Unit 5 끝에서 본 것):

```text
명령1: IF ID EX MEM WB
명령2:    IF ID EX  MEM WB
명령3:       IF ID  EX  MEM WB
```

- **Latency**: 명령어 하나는 여전히 5단계를 다 거쳐야 함 → **줄지 않음** (오히려 단계 분리 오버헤드로 살짝 늘 수도)
- **Throughput**: 매 클럭마다 새 명령어가 완료됨 → **5배 가까이 증가**

> 즉 pipeline은 **latency는 그대로 두고 throughput을 올리는** 기법이다. "한 명령어가 빨라진 게 아니라, 동시에 여러 개를 굴려서 전체 처리율을 높인 것."

### 비유 — 세탁소

빨래 1통: 세탁(30분) → 건조(30분) → 개기(30분) = **90분 (latency)**

- 순차 처리: 빨래 4통 = 360분
- pipeline(겹침): 세탁 끝낸 1통을 건조 돌리는 동안 2통째 세탁 시작 → 4통 = 180분
- **통 하나의 latency는 여전히 90분.** 하지만 **throughput**(시간당 끝나는 통 수)은 2배.

> **DV 메모**: 성능 검증에서 이 둘을 **반드시 따로 측정**해야 한다. RDMA로 치면 — 패킷 하나의 **end-to-end latency**(WQE post부터 CQE까지)와, 링크의 **throughput**(Gbps, IOPS)은 별개 metric이고 별개 testbench 시나리오다. 하나가 좋다고 다른 게 좋은 게 아니다. burst test로 throughput을, single-shot test로 latency를 재는 식으로 분리한다.

## 2. 성능의 정의 — 무엇을 측정할 것인가

직관적으로:

```text
성능(Performance) = 1 / 실행시간(Execution Time)
```

성능이 X배 좋다 = 실행시간이 1/X로 줄었다. **결국 모든 성능 논의의 최종 진실은 "실행시간(벽시계 시간, wall-clock)"** 이다. 다른 지표(클럭, IPC...)는 다 이걸 분해한 것.

### 함정: "클럭 빠르면 빠른 거 아냐?" — NO

3GHz CPU가 2GHz CPU보다 항상 빠를까? **아니다.** 클럭은 성능의 **한 요소**일 뿐이다. 클럭이 높아도 한 작업에 명령어를 더 많이 쓰거나, 명령어당 클럭을 더 많이 쓰면 느릴 수 있다. 이 함정을 깨려고 나온 게 다음의 **Iron Law**다.

## 3. ⭐ Iron Law of Performance (성능의 철칙) — 이 유닛의 심장

CPU 실행시간을 **딱 3개 인자의 곱**으로 분해하는 공식이다. 이거 하나면 "왜 빠른가/느린가"를 거의 다 설명할 수 있다.

```text
                 명령어 수        클럭 수          시간
실행시간   =   ──────────  ×  ──────────  ×  ──────────
              (Instructions)   (Cycles)        (Clock)
   Time    =      IC        ×      CPI      ×    T_clock

           =  IC × CPI × (1 / 클럭주파수)
```

세 인자:

| 인자 | 이름 | 의미 | 누가 결정하나 |
|---|---|---|---|
| **IC** | Instruction Count | 프로그램이 실행하는 **명령어 총 개수** | 알고리즘, 컴파일러, ISA |
| **CPI** | Cycles Per Instruction | 명령어 **하나당 평균 클럭 수** | 마이크로아키텍처(pipeline, 캐시...) |
| **T** | Clock Cycle Time | 클럭 한 번의 길이 (= 1/주파수) | 회로 설계, 공정(반도체) |

### 왜 "철칙"인가

이 세 인자가 **CPU 성능을 바꾸는 유일한 손잡이**이기 때문이다. 어떤 최적화든 결국 이 셋 중 하나(이상)를 건드려서 성능을 올린다. 그리고 **셋은 서로 얽혀 있어서 하나만 좋게 만들면 다른 게 나빠지기 쉽다** — 그래서 "철칙(피할 수 없는 법칙)".

### 단위 상쇄

```text
  명령어     클럭        시간
 ──────  ×  ──────  ×  ─────  =  시간   (명령어, 클럭이 약분됨)
   1       명령어       클럭
```

## 4. Iron Law로 최적화 기법들을 해부하기

앞으로 배울 모든 기법이 Iron Law의 어느 인자를 건드리는지:

| 기법 | IC | CPI | T(클럭) | 핵심 |
|---|---|---|---|---|
| **더 좋은 알고리즘** | ⬇️ | - | - | 명령어 자체를 덜 실행 |
| **CISC→복잡한 명령어** | ⬇️ | ⬆️ | ⬆️ | 명령어 수는 줄지만 하나가 무거워짐 |
| **RISC(단순 명령어)** | ⬆️ | ⬇️ | ⬇️ | 명령어는 많아지지만 각각 빠르고 단순 |
| **Pipeline** (Unit 8) | - | ⬇️ (이상적으로 1에 근접) | ⬇️ (단계 짧아짐) | throughput↑ |
| **분기 예측** (Unit 9) | - | ⬇️ | - | 잘못된 stall 제거로 CPI↓ |
| **캐시** (Unit 11~12) | - | ⬇️ | - | 메모리 대기 줄여 CPI↓ |
| **클럭만 올리기** | - | - | ⬇️ | 단, 발열/전력 한계(Unit 15 power wall) |

> **핵심 통찰**: "클럭만 올리면 되잖아"가 안 통하는 이유가 이 표에 다 있다. 클럭을 올리면(T↓) 보통 pipeline을 더 잘게 쪼개야 하는데, 그러면 hazard가 늘어 CPI가 나빠지고, 전력이 폭증한다(Unit 15). **세 인자는 한 몸이라 따로 못 논다.**

### MIPS, FLOPS 같은 지표를 믿지 마라

"이 CPU는 1000 MIPS!"(초당 백만 명령어) 같은 지표는 **함정**이다. MIPS는 IC만 보고 "그 명령어가 무슨 일을 하는지"는 안 본다. 단순 명령어를 무더기로 실행하는 CPU가 MIPS는 높지만 실제 일은 더 느릴 수 있다. → **벤치마크(실제 프로그램 실행시간)로 비교해야 한다.**

## 5. CPI 깊이 보기 — DV가 가장 자주 만나는 인자

### 평균 CPI 계산

명령어 종류마다 클럭 수가 다르니까, **가중 평균**을 낸다:

```text
        Σ (각 명령어 종류의 CPI × 그 종류의 개수)
CPI  =  ─────────────────────────────────────────
                  전체 명령어 수
```

예시 — 어떤 프로그램:

- ALU 명령어 50%, CPI 1
- Load 20%, CPI 5 (캐시 미스 때문에 느림)
- Branch 30%, CPI 2

```text
평균 CPI = 0.5×1 + 0.2×5 + 0.3×2 = 0.5 + 1.0 + 0.6 = 2.1
```

→ 이 프로그램은 명령어당 평균 2.1 클럭. **Load가 전체의 20%인데 CPI 기여는 1.0(거의 절반)** 인 게 보인다. 이게 "어디를 최적화해야 하나"를 알려준다 — **Load(=메모리/캐시)를 잡으면 효과가 크다.** 이게 캐시(Unit 11~)가 그렇게 중요한 이유.

### IPC = 1/CPI

요즘은 CPI 대신 **IPC(Instructions Per Cycle, 클럭당 명령어 수)** 를 자주 쓴다. superscalar(Unit 10)에선 한 클럭에 여러 명령어를 완료하니까 IPC > 1이 된다. CPI < 1 보다 IPC > 1 이 더 직관적이라.

> **DV 메모**: 성능 검증에서 **CPI/IPC가 핵심 측정 대상**이다. testbench에서 "사이클 수 / 완료한 명령어(또는 트랜잭션) 수"를 카운트해서 측정하고, **목표 CPI(스펙)** 와 비교한다. RDMA로 치면 "트랜잭션당 평균 클럭 수" 또는 "초당 처리 가능한 IOPS"가 같은 역할이다. 그리고 위 예시처럼 **CPI를 명령어 종류별로 분해(breakdown)** 하는 게 성능 디버깅의 핵심 — "전체가 느리다"가 아니라 "load가 stall을 80% 차지한다"처럼 범인을 특정해야 고친다.

## 6. 평균의 함정 — 성능 비교할 때 조심

여러 벤치마크 결과를 하나로 합칠 때 **산술평균(arithmetic mean)** 을 쓰면 틀릴 수 있다. 비율(속도 향상 배수)을 합칠 땐 **기하평균(geometric mean)** 을 써야 한다.

간단 직관: A가 B보다 "어떤 건 10배 빠르고 어떤 건 0.1배(10배 느림)"면 평균이 1이어야(상쇄) 맞는데, 산술평균은 (10+0.1)/2 = 5.05로 "5배 빠름"이라 거짓말을 한다. 기하평균 √(10×0.1)=1로 정확. → **속도 비율의 평균은 기하평균.**

> **DV 메모**: regression suite에서 여러 테스트의 성능을 한 숫자로 요약할 때 이 함정에 빠지기 쉽다. "평균 성능 향상 X%"를 보고할 때 어떤 평균을 썼는지가 결론을 바꾼다.

## 핵심 정리

> 이 유닛의 진짜 메시지 — 꼭 기억할 3가지.

1. **"빠르다"는 두 개다 — latency(하나의 시간)와 throughput(시간당 개수).** 둘은 독립이고 자주 상충한다. pipeline은 latency 그대로 두고 throughput을 올린다.

2. **Iron Law: `시간 = IC × CPI × T_clock`.** CPU 성능을 바꾸는 손잡이는 이 셋뿐이고, 셋은 얽혀 있어 하나만 못 건드린다. 앞으로 배울 모든 최적화는 이 셋 중 하나를 건드리는 것.

3. **클럭(GHz)이나 MIPS만 보고 빠르다고 판단하지 마라.** 최종 진실은 실행시간(벽시계)이고, CPI를 종류별로 분해하면 진짜 병목이 보인다.

## 🔌 검증 관점

- **latency와 throughput은 별개 metric:** 별개 testbench 시나리오로 따로 측정. single-shot으로 latency, burst로 throughput. 하나가 좋다고 다른 게 좋은 게 아니다.
- **CPI/IPC가 핵심 측정 대상:** "사이클 수 / 완료 명령어(트랜잭션) 수"를 카운트해 **목표 CPI 스펙과 비교.** 그냥 "느리다"가 아니라 **종류별 breakdown**(base CPI + branch penalty + memory stall...)으로 범인을 특정해야 고친다.
- **performance counter 활용:** misprediction/flush count 등 카운터를 읽어 스펙과 비교. "기능은 맞는데 misprediction이 스펙보다 높다"가 전형적 성능 버그 리포트.
- **워크로드 다양화:** 같은 HW도 분기 비율·예측률에 따라 빠르고 느리다. 대표 워크로드 set(분기 많은/적은/예측 어려운)으로 directed + random 둘 다 돌려야 corner를 안 놓친다.
- **평균 함정:** 정규화된 성능비를 합칠 땐 **기하평균**(산술평균은 퇴보를 묻어 성능 버그를 놓침). 절대 latency·사이클 수는 산술평균/percentile.
- **개수 metric vs 유효 일 metric:** 둘 다 재라(MIPS류 ↔ goodput류). peak vs achieved 갭이 곧 utilization이고, 그 갭의 출처(stall, 의존성, HoL blocking)가 성능 디버깅의 본체.

## 📎 부록 — 이 단원에서 나온 질문들

### Q1. "MIPS, FLOPS가 뭐야?"

둘 다 **"컴퓨터가 얼마나 빠른가"를 나타내는 옛날 단위**다. 이름이 비슷해서 헷갈리는데 측정 대상이 다르다.

#### 1. MIPS — Million Instructions Per Second

**초당 실행하는 명령어 수 (백만 단위)**

```text
            명령어 실행 개수            클럭주파수
MIPS  =  ──────────────────────  =  ──────────────
          실행시간 × 1,000,000        CPI × 1,000,000
```

예: 1초에 2억 개 명령어를 실행하면 = **200 MIPS**

"명령어를 얼마나 빨리 쏟아내나"를 재는 것. Iron Law의 `IC / 시간`에 해당한다.

##### MIPS의 치명적 함정

> **명령어 개수만 세고, 그 명령어가 무슨 일을 했는지는 안 본다.**

```text
CPU A: 단순 명령어를 5개 써서 곱셈 1번 수행  →  명령어 5개 실행 (MIPS 높게 나옴)
CPU B: 곱셈 명령어 1개로 곱셈 1번 수행       →  명령어 1개 실행 (MIPS 낮게 나옴)
```

둘 다 **같은 일(곱셈 1번)** 을 했는데, MIPS는 A가 5배 높게 나온다! 마치 A가 빠른 것처럼 보이지만 실제로 한 일은 똑같거나 오히려 A가 느릴 수도 있다.

그래서 MIPS를 농담으로 **"Meaningless Indicator of Processor Speed"**(프로세서 속도의 무의미한 지표)라고 부른다. 특히 ISA가 다른 CPU끼리(RISC vs CISC) MIPS로 비교하면 완전히 헛다리다.

#### 2. FLOPS — FLoating-point Operations Per Second

**초당 부동소수점 연산 수**

```text
FLOPS = 초당 수행하는 실수(float) 덧셈/곱셈 등의 개수
```

MIPS는 "명령어 개수"를 세는데, FLOPS는 **"실수 계산 개수"** 를 센다. 차이가 핵심:

- MIPS: 명령어가 뭐든 다 셈 (메모리 이동, 분기, 정수 연산...)
- FLOPS: **오직 부동소수점(실수) 계산만** 셈

##### 왜 FLOPS가 따로 있나?

과학계산·AI·그래픽 같은 분야는 일이 **거의 다 실수 곱셈/덧셈**이다 (행렬 곱, 신경망...). 이런 워크로드에선 "정수 명령어 몇 개 실행"은 관심 없고 **"실수 계산을 초당 몇 번 하냐"** 가 진짜 성능이다. 그래서 HPC(슈퍼컴퓨터)·GPU·AI 칩은 전부 FLOPS로 성능을 말한다.

단위 스케일:

```text
KFLOPS  → MFLOPS → GFLOPS → TFLOPS → PFLOPS → EFLOPS
 10³       10⁶      10⁹      10¹²     10¹⁵     10¹⁸
```

- 요즘 GPU 하나: 수십~수백 **TFLOPS**
- 슈퍼컴퓨터: **EFLOPS**(엑사플롭스) 시대
- "이 AI 칩 1000 TOPS" 할 때 TOPS는 FLOPS의 정수(integer) 버전 — AI 추론은 정수 연산을 많이 써서.

##### FLOPS도 함정 있다

FLOPS는 보통 **이론 최대치(peak)** 로 광고된다 — "이론상 모든 연산 유닛이 100% 놀지 않으면 이만큼". 실제 프로그램에선 메모리 대기·의존성 때문에 그 절반도 못 쓰는 게 보통이다. 그래서 **실측 FLOPS(achieved)** 와 **이론 FLOPS(peak)** 를 구분해야 한다. "peak FLOPS 100%"는 마케팅 숫자고, 실제 효율(achieved/peak)이 진짜 성능이다.

#### 3. MIPS vs FLOPS 한눈에

| | **MIPS** | **FLOPS** |
|---|---|---|
| 세는 대상 | **명령어** 개수 | **부동소수점 연산** 개수 |
| 어디서 쓰나 | 범용 CPU (옛날) | HPC, GPU, AI, 과학계산 |
| 함정 | 명령어가 한 일을 무시 (ISA 다르면 무의미) | peak vs achieved 차이 |
| Iron Law 관점 | IC/시간 (Iron Law의 일부만 봄) | 일의 "양"을 직접 셈 (더 의미있음) |

#### 4. 결론

두 지표 다 **"한 인자만 보는 부분 지표"** 라 단독으로는 못 믿는다. Iron Law(`시간 = IC × CPI × T`)에서 MIPS는 사실상 IC/시간만, FLOPS는 "유용한 연산량"만 본다.

> **진짜 비교는 "실제 프로그램의 실행시간(벽시계)" 또는 표준 벤치마크(SPEC 등)로 한다.** MIPS/FLOPS는 참고용 한 줄 요약일 뿐.

#### 🔌 DV 메모

성능 검증 metric을 고를 때 "무엇을 세느냐"가 결론을 바꾼다:

- RDMA로 치면 **MIPS ≈ "초당 처리한 패킷/디스크립터 개수"**, **FLOPS ≈ "초당 옮긴 유효 데이터 바이트(goodput)"** 에 가깝다. 작은 패킷을 많이 처리하면 패킷 수(MIPS류)는 높은데 실제 옮긴 데이터(goodput)는 적을 수 있다 — MIPS 함정과 똑같은 구조.
- 그래서 성능 testbench를 짤 때 **"개수 기반 metric"과 "유효 일(work) 기반 metric"을 둘 다** 재야 한다. 하나만 보면 "패킷은 많이 처리하는데 정작 데이터는 안 나가는" 병목을 놓친다.
- **peak vs achieved 구분**도 그대로 적용된다 — 이론 대역폭(line rate)과 실측 throughput의 갭이 곧 효율(utilization)이고, 그 갭이 어디서 생기는지(stall, 의존성, head-of-line blocking)가 성능 디버깅의 본체다.

**한 줄 요약**: **MIPS** = 초당 명령어 수(명령어가 한 일은 무시해서 함정 많음), **FLOPS** = 초당 실수 연산 수(HPC/AI 표준, 하지만 peak vs 실측 구분 필요). 둘 다 부분 지표라 단독으로 믿지 말고 실제 실행시간/벤치마크로 봐야 한다.

### Q2. "산술평균 기하평균 차이를 쉽게 알려줘"

#### 1. 한 줄 정의

| | **산술평균 (Arithmetic Mean)** | **기하평균 (Geometric Mean)** |
|---|---|---|
| 계산 | **더해서** 개수로 나눔 | **곱해서** 개수만큼 제곱근 |
| 공식 | `(a + b) / 2` | `√(a × b)` |
| 묻는 것 | "**합**이 같으려면 평균 얼마?" | "**곱**이 같으려면 평균 얼마?" |
| 쓰는 곳 | 덧셈으로 쌓이는 양 (시간, 점수, 금액) | 곱셈으로 쌓이는 양 (비율, 배수, 성장률) |

#### 2. 핵심 직관: "더하는 값이냐, 곱하는 값이냐"

- **더해서 의미가 생기는 값** → 산술평균
  (예: 3시간 + 5시간 일했다 = 총 8시간. 시간은 더해짐)
- **곱해서 의미가 생기는 값** → 기하평균
  (예: 2배 빨라지고 → 다시 3배 빨라지면 = 총 6배. 배수는 곱해짐)

**배수·비율·퍼센트는 곱으로 누적되니까 기하평균.** 이게 Unit 6에서 "속도 향상 배수는 기하평균"이라고 한 이유.

#### 3. 왜 산술평균이 비율에서 거짓말을 하나 — 결정적 예제

A 컴퓨터가 B보다:

- 벤치마크1에서 **10배 빠름** (배수 = 10)
- 벤치마크2에서 **10배 느림** (배수 = 0.1)

직관적으로 "한 번 10배 빠르고 한 번 10배 느리면 → **비긴 거(1배)**" 여야 맞다.

**산술평균:**

```text
(10 + 0.1) / 2 = 5.05   →  "A가 5배 빠르다!" (거짓말)
```

한쪽이 10배 느린데(0.1) 그걸 거의 무시해버린다. "10배 빠름"의 영향이 너무 커서 결과를 끌어올린다.

**기하평균:**

```text
√(10 × 0.1) = √1 = 1   →  "비겼다" (정답)
```

빠름(10)과 느림(0.1)이 정확히 상쇄돼서 1이 나온다. **이게 직관과 맞는다.**

#### 4. 왜 이런 차이가? — "느린 쪽"을 다루는 방식

비율의 본질은 **대칭**이어야 한다:

- "2배 빠름"(2)과 "2배 느림"(0.5)은 **같은 크기의 반대 변화**다.

그런데:

```text
산술평균에서:  2 → 2만큼 위,  0.5 → 0.5만큼 아래   (비대칭! 위쪽이 훨씬 큼)
기하평균에서:  2와 0.5는 1을 기준으로 곱셈상 대칭  (×2 와 ÷2)
```

산술평균은 "빨라짐(큰 수)"을 과대평가하고 "느려짐(작은 수, 0~1 사이)"을 과소평가한다. 0.1이든 0.0001이든 산술평균엔 거의 영향 없는데(둘 다 0에 가까움), 실제로는 1000배 느림과 10000배 느림은 엄청난 차이다. 기하평균은 이걸 곱셈(로그) 척도로 봐서 공평하게 다룬다.

> **기억법**: 0과 1 사이의 작은 비율(=느려짐)을 산술평균은 "거의 0"으로 뭉개버린다. 비율은 곱셈 세계의 숫자라 곱셈 평균(기하)으로 다뤄야 공평하다.

#### 5. 일상 예제로 한 번 더 — 투자 수익률

투자가 1년차 +100%(2배), 2년차 −50%(0.5배) 났다고 하자.

```text
100만원 → (×2) → 200만원 → (×0.5) → 100만원   →  실제로 본전!
```

**산술평균 수익률:** (+100% + −50%)/2 = **+25%** → "연 25% 벌었다" (본전인데?!)
**기하평균:** √(2 × 0.5) = 1 = **0%** → "본전" (정답)

펀드 광고가 산술평균 수익률로 부풀리는 게 이 트릭이다. 실제 누적 수익은 곱으로 쌓이니까 기하평균이 진실.

#### 6. 언제 뭘 쓰나 — 판단 기준

| 상황 | 평균 |
|---|---|
| 실행시간들(초)을 평균 | 산술 (시간은 더해짐) |
| 시험 점수 평균 | 산술 |
| **속도 향상 배수(speedup)** 평균 | **기하** |
| **성장률 / 수익률 / 비율** 평균 | **기하** |
| 여러 벤치마크의 **정규화된 성능비** 평균 | **기하** (SPEC 표준) |

핵심 질문: **"이 값들을 더하면 말이 되나, 곱하면 말이 되나?"** 더하면 산술, 곱하면 기하.

#### 🔌 DV 메모

성능 regression에서 이게 실수로 자주 터지는 지점:

- 여러 테스트의 성능을 **각각 baseline 대비 배수(예: 1.2배, 0.9배, 1.5배...)** 로 정규화한 뒤 하나로 요약할 때 — **반드시 기하평균.** 산술평균 쓰면 "전체 1.3배 향상!" 같은 부풀린 거짓 결론이 나온다.
- 특히 **회귀(regression)** 가 섞였을 때 위험하다. 한 테스트가 0.5배(2배 느려짐)로 퇴보했는데, 다른 테스트들이 산술평균에서 그걸 덮어버려 "평균은 향상"이라고 보고하면 — 성능 버그를 놓치는 것. 기하평균은 퇴보(0.5)를 제대로 반영해서 경고를 띄운다.
- 반대로 **절대 latency(ns), 사이클 수** 같은 건 더해지는 양이라 산술평균(또는 percentile)이 맞다. p50/p99 latency를 볼 때 평균 대신 percentile을 쓰는 건 또 다른 얘기(꼬리 지연)다.

**한 줄 요약**: **산술평균 = 더해서 나눔(시간·점수처럼 덧셈으로 쌓이는 양)**, **기하평균 = 곱해서 제곱근(배수·비율·성장률처럼 곱셈으로 쌓이는 양)**. 속도 향상 배수를 평균낼 땐 무조건 기하평균 — 안 그러면 빠름은 부풀고 느림은 묻혀서 거짓말이 된다.

### Q3. "파이프라인을 깊게 해 주파수를 높이면 분기 패널티로 CPI가 증가할 수 있다. 관련된 예시도 하나 들어줘"

정확히 Iron Law의 핵심 트레이드오프다. `시간 = IC × CPI × T_clock` 에서 **T를 줄이려다 CPI가 올라가는** 전형적인 사례.

#### 1. 왜 "파이프라인을 깊게 하면 주파수가 오르나?"

클럭 주기(T)는 **가장 느린 파이프라인 단계 하나**가 결정한다. 한 단계의 일을 더 잘게 쪼개면 각 단계가 짧아지니까 클럭을 더 빨리 돌릴 수 있다.

```text
5단계 파이프라인:  [IF][ID][EX][MEM][WB]   각 단계 = 200ps  →  클럭 5GHz
                    ↓ 각 단계를 2개로 쪼갬
10단계 파이프라인: [IF1][IF2][ID1][ID2]...  각 단계 = 100ps  →  클럭 10GHz
```

→ 단계를 깊게(deep pipeline) 쪼개면 **T_clock ↓, 주파수 ↑.** 여기까진 이득.

> 실제 역사: Intel Pentium 4가 이 전략의 극단이었다. **31단계** 파이프라인으로 클럭을 막 올려서 한때 3.8GHz까지 갔다.

#### 2. 그런데 분기(branch)가 발목을 잡는다 — branch penalty

문제는 **분기 명령어(`if`, 반복문, 함수 호출)**. CPU는 파이프라인을 멈추지 않으려고 "다음 명령어가 이거겠지" 하고 **미리 예측해서 fetch**해 놓고 실행을 진행한다(speculation, Unit 9).

근데 예측이 **틀리면**? 이미 파이프라인에 채워 넣은 잘못된 명령어들을 **전부 버리고(flush)**, 올바른 주소부터 다시 채워야 한다. 이때 버려지는 클럭이 **branch misprediction penalty(분기 오예측 패널티)**.

##### 핵심: 패널티 크기 = 파이프라인 깊이에 비례

```text
얕은 파이프라인(5단계):  잘못 채운 게 적음  →  버리는 클럭 ≈ 2~3 클럭
깊은 파이프라인(20단계): 잘못 채운 게 많음  →  버리는 클럭 ≈ 15~20 클럭
```

파이프라인이 깊을수록 "예측 결과가 확정되기까지" 더 많은 단계를 지나야 하고, 그 사이 잘못 채운 명령어가 **단계 수만큼 많아져서** 버릴 게 많아진다. **깊게 팔수록 한 번 틀릴 때 손해가 커진다.**

#### 3. ⭐ 숫자 예제 — 깊게 했더니 오히려 느려진 경우

가정:

- 프로그램의 명령어 중 **20%가 분기** (흔한 비율)
- 분기 예측 정확도 **90%** (즉 10%는 틀림)
- 분기 빼면 모든 명령어 CPI = 1 (이상적 파이프라인)

##### 케이스 A — 얕은 파이프라인 (5단계)

- 클럭 주기 **T = 200ps** (5GHz)
- 오예측 패널티 = **3 클럭**

```text
오예측으로 추가되는 평균 클럭
 = 분기 비율 × 오예측 확률 × 패널티
 = 0.20 × 0.10 × 3
 = 0.06 클럭/명령어

CPI = 1 (기본) + 0.06 = 1.06
시간/명령어 = CPI × T = 1.06 × 200ps = 212 ps
```

##### 케이스 B — 깊은 파이프라인 (20단계)

- 클럭 주기 **T = 80ps** (12.5GHz) ← 주파수 2.5배 올림
- 오예측 패널티 = **18 클럭** ← 깊어서 패널티 폭증

```text
오예측 추가 클럭 = 0.20 × 0.10 × 18 = 0.36 클럭/명령어

CPI = 1 + 0.36 = 1.36
시간/명령어 = 1.36 × 80ps = 108.8 ps
```

##### 결과 비교

| | T_clock | CPI | **시간/명령어 (CPI×T)** |
|---|---|---|---|
| A (5단계, 5GHz) | 200ps | 1.06 | **212 ps** |
| B (20단계, 12.5GHz) | 80ps | 1.36 | **108.8 ps** |

이 경우엔 B가 빠르다(108.8 < 212). **주파수 2.5배 이득이 CPI 악화를 이겼다.** 여기까진 deep pipeline 승리.

#### 4. 그런데 — 예측이 더 나쁘거나 분기가 더 많으면 역전된다

예측 정확도 **80%**(틀림 20%)에 분기 많은(30%) 코드라고 하자.

**A (5단계, 200ps, 패널티 3):**

```text
CPI = 1 + 0.30 × 0.20 × 3 = 1 + 0.18 = 1.18
시간/명령어 = 1.18 × 200 = 236 ps
```

**B (20단계, 80ps, 패널티 18):**

```text
CPI = 1 + 0.30 × 0.20 × 18 = 1 + 1.08 = 2.08
시간/명령어 = 2.08 × 80 = 166.4 ps
```

아직 B가 빠르다(166 < 236). 더 극단으로 — **35단계, 패널티 32, 주파수는 거의 안 오름(공정 한계로 60ps)**:

```text
CPI = 1 + 0.30 × 0.20 × 32 = 1 + 1.92 = 2.92
시간/명령어 = 2.92 × 60 = 175.2 ps   ← B(20단계)보다 오히려 느려짐! (175 > 166)
```

**20단계 → 35단계로 더 깊게 팠더니 오히려 느려졌다.** 클럭 이득(80→60ps)이 미미한데 CPI 악화(2.08→2.92)가 커서 역전된 것. 이게 **"깊게 파다가 분기 패널티로 CPI가 증가해서 손해 보는"** 정확한 지점이다.

> 핵심 통찰: 파이프라인을 깊게 할수록 **클럭 이득은 점점 줄고(공정·전력 한계)**, **분기 패널티는 선형으로 커진다.** 어느 지점을 넘으면 `IC × CPI × T`의 곱이 다시 늘기 시작한다. 이게 **"최적 파이프라인 깊이"가 존재하는** 이유.

#### 5. 실제 역사 — Pentium 4의 교훈

- Intel **Pentium 4 (Prescott)**: 클럭 경쟁에서 이기려고 파이프라인을 **31단계**까지 늘림. 목표는 10GHz였다.
- 결과: 분기 오예측 한 번에 **~30 클럭**을 날림. 게다가 클럭 올리느라 **전력·발열이 폭발**(Unit 15 power wall).
- 같은 시기 AMD Athlon은 더 짧은 파이프라인 + 낮은 클럭인데 **실제로 더 빨랐다** — CPI가 훨씬 좋아서.
- 결국 Intel은 이 노선을 **폐기**하고, Core 아키텍처(파이프라인 14단계로 되돌림, 클럭은 낮추고 IPC↑)로 전환했다. 지금까지도 이 방향이다.

**"GHz 경쟁의 종말"** 이 바로 이 트레이드오프 때문이었다.

#### 🔌 DV 메모

성능 검증 관점에서 이 트레이드오프는 **measurement breakdown이 왜 필수인지** 보여준다:

1. **CPI를 분해(decompose)해서 측정해야 한다.** "CPI = 2.08"만 보면 안 되고, `base CPI 1 + branch penalty 1.08`처럼 **기여 인자별로 쪼개**야 범인이 보인다. RDMA로 치면 latency를 "순수 전송 + 재시도 stall + queue 대기"로 분해하는 것과 같다.
2. **분기 오예측률은 핵심 성능 카운터.** 실제 칩/RTL 검증엔 performance counter(misprediction count, flush count)가 박혀 있고, DV가 그걸 읽어서 **목표 CPI 스펙과 비교**한다. "기능은 맞는데 misprediction이 스펙보다 높다"가 전형적인 성능 버그 리포트다.
3. **워크로드 의존성.** 위 예제처럼 같은 하드웨어도 **분기 비율·예측률(=워크로드)** 에 따라 빠르기도 느리기도 하다. 그래서 성능 검증은 **대표 워크로드 set(분기 많은 것/적은 것/예측 어려운 것)** 으로 다양하게 돌려야 하지, 한 가지 패턴만 보면 "특정 코드에선 느려지는" corner를 놓친다. directed 성능 시나리오 + random 워크로드 둘 다 필요한 이유.

**한 줄 요약**: 파이프라인을 깊게 → 단계가 짧아져 **T_clock↓(주파수↑)** 이득. 하지만 분기 오예측 시 **버릴 단계가 많아져 패널티가 커지고 → CPI↑.** 깊이가 어느 선을 넘으면 클럭 이득보다 CPI 손해가 커져 `IC×CPI×T`가 다시 늘어난다. 실제 사례가 **Pentium 4(31단계, 10GHz 노렸다 실패)** → Core로 후퇴. 이게 GHz 경쟁이 끝난 이유다.
