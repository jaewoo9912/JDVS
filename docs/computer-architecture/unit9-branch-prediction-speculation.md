# Unit 9 — 분기 예측 & Speculation (Branch Prediction & Speculation)

> **핵심 한 문장:** 분기 결과를 기다리지(stall) 말고, 추측해서 일단 진행하자. 맞으면 공짜로 빨라지고, 틀리면 그때 되돌리면(squash) 된다.
> 이게 **prediction(예측)** = "다음에 뭘 fetch할지 추측" 과 **speculation(추측 실행)** = "그 추측한 명령어를 실제로 실행까지 진행" 이다.

분기는 코드의 **5~6개 명령어마다 하나씩** 나온다(if, for, while, 함수 호출/리턴…). 이렇게 자주 나오는 control hazard를 매번 stall로 처리하면 파이프라인 절반이 거품(bubble)으로 찬다. 그래서 현대 CPU 성능의 상당 부분이 **"분기를 얼마나 잘 맞히느냐"** 에 달려 있다. DV 관점에서는 **"speculative한 것이 절대 architectural state를 더럽히면 안 된다"** 는 검증 원칙과 직결되고, **Spectre** 같은 보안 취약점의 무대이기도 하다.

---

## 1. 왜 stall은 답이 아닌가 (control hazard 복습)

```
beq x5, x6, LABEL    IF ID EX ← 분기 방향이 EX에서야 확정
???                     IF ?? ← 그 사이 다음에 뭘 fetch하지?
```

Unit 8에서 본 선택지 3가지 중:
- **Stall(무조건 멈춤):** 분기마다 패널티. 분기가 6 명령어당 1개면 CPI가 확 나빠짐. 너무 비싸다.
- **Delayed branch:** 옛날 방식, 폐기.
- **Branch prediction:** ← 정답. 이 유닛 전체.

**핵심 통찰:** 대부분의 분기는 **패턴이 있다.** 반복문 분기는 거의 항상 taken(루프 계속), 에러 체크 분기는 거의 항상 not-taken(에러 안 남). 패턴이 있으면 추측이 매우 잘 맞는다 — 현대 예측기는 **95~99% 정확도**. 맞히면 패널티 0, 틀린 1~5%만 flush. 그래서 stall보다 압도적으로 빠르다.

> **DV 메모:** control hazard는 "PC를 결정하는 로직"이 검증 핫스팟이라는 뜻. 분기 결과 forwarding, flush 타이밍, PC redirect가 한 사이클이라도 어긋나면 잘못된 명령어를 실행 → 정확성 버그가 여기 몰린다.

---

## 2. 분기 예측이 답해야 할 두 가지 질문

```
beq x5, x6, LABEL
```
1. **방향(direction):** taken이냐 not-taken이냐? (점프할까 말까) → **BHT / 예측기**
2. **목적지(target):** taken이면 어디로 점프? (LABEL 주소) → **BTB**

둘 다 맞아야 stall 없이 진행된다. 하나라도 틀리면 stall 또는 flush.

---

## 3. 방향 예측 — Static vs Dynamic

### Static Prediction (정적 예측) — "항상 같은 추측"
컴파일/설계 시점에 고정. 실행 중 안 바뀜.
- **항상 not-taken:** 분기 무시하고 그냥 다음 줄 계속 fetch (제일 단순, 하드웨어 거의 0).
- **항상 taken:** 무조건 점프한다고 찍음(목적지 주소를 알아야 해서 약간 더 복잡).
- **BTFN (Backward Taken, Forward Not-taken):** 뒤로 가는 분기(루프)는 taken, 앞으로 가는 분기는 not-taken으로 찍음. 방향이라는 단서만으로 ~70% 적중.

장점: 하드웨어 거의 안 듦. 단점: 패턴 변화에 대응 못 함.

### Dynamic Prediction (동적 예측) — "과거를 보고 학습"
실행 중 분기의 과거 행동을 기록하고 그걸로 예측. 현대 CPU 방식. "이 분기는 지난 10번 다 taken이었으니 이번에도 taken."

---

## 4. ★ Dynamic Predictor의 진화 — 1비트 → 2비트

### 1-bit Predictor
분기마다 1비트 저장: "지난번에 taken이었나?" → 지난번과 같게 예측. 틀리면 비트 뒤집음.

**문제 — 루프 경계에서 2번 틀린다:**
```
for(i=0;i<3;i++) 의 분기 행동:  T T N | T T N | ...
실제:   T   T   N   T   T   N
예측:   T   T   T   N   T   T
        ✅  ✅  ❌  ❌  ✅  ✅
                ★   ★
```
탈출(N) 한 번이 기억을 N으로 뒤집고 → 다음 루프 첫 진입(실제 T)도 틀린다. **한 번의 예외가 2번 miss를 만든다.**

### 2-bit Saturating Counter (표준)
"한 번 틀렸다고 바로 마음 안 바꾸기." 4상태, **2번 연속 틀려야** 예측을 바꾼다(관성/hysteresis):
```
강한Taken(11) ⇄ 약한Taken(10) ⇄ 약한Not(01) ⇄ 강한Not(00)
└──── taken 예측 ────┘        └──── not-taken 예측 ────┘
taken이면 → taken 쪽(왼쪽) 한 칸, not이면 → not 쪽(오른쪽) 한 칸 (양끝 포화)
예측: 왼쪽 둘이면 taken, 오른쪽 둘이면 not-taken
```
강한Taken에서 탈출(N 1번) → "약한Taken"으로만 이동, **여전히 taken 예측** → 다음 루프 진입은 안 틀림. 1비트의 "2번 틀림"을 "1번 틀림"으로 줄임. 정확도 ~85-90%.

> **비유:** 단골 식당. 한 번 맛없다고(1번 실패) 바로 단골 안 바꾸고(약한 상태로만 이동), 두 번 연속이면 그제서야 바꾼다. 노이즈에 안 휘둘림.

---

## 5. Correlation(상관 예측) — 더 똑똑하게

분기들은 서로 영향을 준다:
```
if (x > 0) ...   // 분기 A
if (x < 5) ...   // 분기 B  ← A 결과를 알면 B를 더 잘 맞힘
```
- **GHR (Global History Register):** 최근 N개 분기의 taken/not 기록(예 `1101`).
- 이 history 패턴 + 분기 PC를 조합해 예측 테이블 인덱싱.
- 대표 기법 **gshare:** PC ⊕ GHR로 테이블 인덱스.

**핵심:** "이 분기 하나의 과거"가 아니라 "최근 분기들의 패턴 전체"를 보면 더 잘 맞는다. 현대 예측기(**TAGE**, **perceptron** 등)는 97~99% 달성.

---

## 6. 목적지 예측 — BTB & RAS

방향(taken)을 맞혀도 **"어디로"** 를 모르면 여전히 stall이다. 목적지는 보통 디코드(ID)해야 알지만, 다음 PC는 IF에서 당장 필요 → 한 박자 빈다.

### BTB (Branch Target Buffer)
"이 분기(PC)는 지난번에 어디로 점프했지?"를 PC→목적지 표(캐시)로 외워둔다.
```
┌──────────┬───────────┐
│ 분기 PC  │ 목적지    │
├──────────┼───────────┤
│ 0x108    │ 0x4000    │
│ 0x250    │ 0x1200    │
└──────────┴───────────┘

IF 단계: 현재 PC로 BTB 조회 → "분기고, 지난번 목적지 0x4000"
        → taken 예측이면 다음 PC = 0x4000 (해석 전에 즉시 fetch, stall 0)
```

### RAS (Return Address Stack)
함수 리턴(`ret`)은 BTB로 잘 안 맞는다 — 같은 함수라도 **호출한 곳마다 복귀 주소가 다르기** 때문. 그래서 작은 스택을 따로 둔다:
- `call` 시 → 복귀 주소 **push**
- `ret` 시 → **pop** 해서 그 주소로 예측
- call/return이 LIFO로 짝이 맞아 거의 100% 적중.

---

## 7. ★ Speculation — 추측을 실제 실행까지

예측한 경로의 명령어를 ID/EX까지 **실제로 실행**한다(아직 진짜 taken인지 확정 전).

> **절대 규칙:** speculative 명령어는 **commit(확정) 전까지 architectural state(레지스터/메모리)를 절대 바꾸면 안 된다. 틀리면 흔적 없이 버려져야(squash) 한다.**

### Misprediction recovery
예측이 틀렸다고 EX에서 확정되면:
1. **Squash/Flush:** 잘못된 경로로 진행 중이던 명령어 전부 무효화(pipeline register → nop).
2. **상태 복구:** speculative하게 바뀔 뻔한 것 원상복구(commit 안 했으니 버리면 됨).
3. **올바른 PC부터 재시작.**

이 전 과정이 **misprediction penalty**. 파이프라인이 깊을수록 squash할 명령어가 많아 패널티가 커진다(Unit 6의 "deep pipeline → 분기 패널티↑"의 정체).

> in-order는 단순하지만, OoO/superscalar(Unit 10)에선 **ROB(ReOrder Buffer)** 가 "commit 전 보류 → 확정 commit / 틀리면 squash"를 관리한다. speculation이 ROB로 자연스럽게 이어진다.

---

## 8. ⚠️ Spectre (보안)

**문제의 본질:** speculative 실행은 architectural state(레지스터/메모리)는 복구하지만, **마이크로아키텍처 상태(캐시)는 안 지운다.** squash해도 "캐시에 뭐가 올라왔는지"라는 흔적(side channel)은 남는다.

**공격 시나리오:**
1. 공격자가 분기 예측기를 "taken"으로 훈련시킴.
2. 실제론 not-taken이어야 할(=비밀 메모리 접근 금지) 분기를 CPU가 taken으로 speculative 실행 → **권한 체크 끝나기 전에** 비밀값을 읽음.
3. 그 비밀값으로 `probe[secret]` 같은 배열의 특정 칸을 읽어 **캐시에 올림.**
4. 예측 틀림 발각 → squash. 레지스터/메모리는 복구. **BUT 캐시 흔적(그 칸이 빨라짐)은 남음.**
5. probe 배열 256칸을 하나씩 읽으며 timing 측정 → **유독 빠른 칸 번호 = 비밀값.** 반복하면 비밀번호·암호키·남의 데이터를 한 바이트씩 통째로 유출.

**교훈:** "architectural state만 안 더럽히면 안전"이란 가정이 깨졌다. speculation이 남기는 side effect(캐시 타이밍)까지 봐야 한다.

---

## 9. DV 관점 종합

1. **(최우선) speculative한 것이 architectural state를 절대 안 더럽히나** — 모든 misprediction에서 squash 후 architectural state가 golden model과 일치하는지 lock-step 비교.
2. **예측기 버그 = 보통 성능 버그, 정확성 버그 아님** — recovery가 결과를 바로잡으니 architectural 결과는 항상 정답, CPI만 나빠짐. 검증이 둘로 갈림: 기능 검증(예측 맞든 틀리든 결과는 정답) vs 성능 검증(misprediction rate가 목표 이하인가).
3. **Recovery corner explosion** — squash 중 또 다른 분기, 중첩 speculation, RAS over/underflow, BTB 충돌. constrained-random + coverage로.
4. **RAS 특수 검증** — call/return 불균형(재귀 overflow, longjmp)에서 복구 정확성.
5. **보안 검증(현대 필수)** — speculation side channel 누출. Spectre 이후 신설 영역.

> **RDMA 비유:** speculative하게 미리 당겨온 작업이 확정 전엔 외부에 commit 안 되고, abort 시 깔끔히 롤백돼야 하는 원칙과 정확히 같다. side channel 검증이 중요해지는 것도 비슷.

---

## 10. 꼭 기억할 3가지
1. **분기는 기다리지 말고 예측해 진행** — 방향(BHT/2비트/correlation) + 목적지(BTB/RAS), 95~99% 적중, 맞으면 패널티 0.
2. **Speculation = 추측 실행하되 commit 전까지 architectural state 불변, 틀리면 squash+복구**(= misprediction penalty, deep pipeline일수록 큼).
3. **예측 틀림 = 성능 문제(복구하니까), side effect(캐시 흔적=Spectre) = 보안 문제.** DV는 정확성+성능+보안 셋 다 검증.

## Q. `beq`는 어떤 명령어야?
**`beq` = "Branch if EQual" = 두 값이 같으면 점프하라** 는 조건 분기 명령어(RISC-V/MIPS).
```
beq x5, x6, LABEL
     │   │    └ 점프할 목적지(라벨/주소)
     └───┴ 비교할 두 레지스터
```
- 읽는 법: "x5와 x6가 같으면 LABEL로 점프(taken), 다르면 다음 줄 계속(not-taken)."
- C의 `if (a==b) {...}` 가 기계어로 내려오면 `beq` 같은 분기가 된다. 즉 **고급언어의 if/for/while이 기계어에선 결국 분기 명령어.**
- 친척: `bne`(같지 않으면), `blt`(작으면), `bge`(크거나 같으면). 다 "조건 맞으면 점프, 아니면 다음 줄" 구조.
- **왜 주인공?** beq는 "점프할지 말지"가 EX 단계에서야 결정되어 그 사이 뭘 fetch할지 모르는 control hazard를 만든다 → 예측이 필요한 바로 그 상황.

## Q. static 예측이 뭔데? (쉽게)
- **static = "고정. 프로그램 돌기 전 이미 정해져 있고 실행 중 안 바뀜."** 분기가 실제로 어떻든 신경 안 쓰고 항상 같은 추측을 한다.
- 비유: **하늘 안 보고 매일 "비 안 와"라고 찍는 사람.** 고정된 답.
- 3가지 규칙: ① 항상 not-taken(분기 무시하고 아래로 계속) ② 항상 taken(무조건 점프) ③ **BTFN**(뒤로=taken, 앞으로=not-taken).
- 장점: 하드웨어 거의 공짜. 단점: 패턴 변화 대응 못 함 → 그래서 다음이 학습하는 Dynamic 예측.

## Q. BTFN의 "앞으로/뒤로"가 아예 뭔 소린지 모르겠어
- 명령어는 메모리에 **주소 순서대로** 줄 서 있고 CPU는 보통 위→아래(작은 주소→큰 주소)로 읽는다. "뒤/앞"은 **시간이 아니라 메모리 주소 방향.**
- **뒤로 점프(backward) = 위로 = 작은 주소로** = 이미 지나온 곳으로 되돌아감.
  ```
  LOOP: ←──────┐  (주소 100, 위쪽)
     ...        │
     blt ..LOOP ┘  (주소 200) → 100으로 거꾸로
  ```
  거의 **루프**다. 같은 코드를 다시 돌리려 위로 감 → 여러 바퀴 도니 **거의 taken.**
- **앞으로 점프(forward) = 아래로 = 큰 주소로** = 중간을 건너뜀.
  ```
  beq ..SKIP ┐  (주소 108)
     ...      │
  SKIP: ←─────┘  (주소 120, 아래쪽)
  ```
  거의 **if로 코드 건너뛰기**다. 에러는 잘 안 나니 보통 안 건너뜀 → **거의 not-taken.**
- 그래서 **BTFN = "위로 가는 분기는 taken, 아래로 가는 분기는 not-taken으로 찍어라."** 방향만 보고 ~70% 적중.

## Q. 루프 경계에서 2번 틀린다는 게 뭐야? (쉽게)
- `for(i<3)` 분기 행동을 쭉 적으면 `T T N | T T N | ...` (탈출에서 N). N→T로 넘어가는 지점이 "루프 경계."
- 1비트는 "지난번 결과 = 이번 예측"이라:
  ```
  실제:  T  T  N  T  T  N
  예측:  T  T  T  N  T  T
         ✅ ✅ ❌ ❌ ✅ ✅
  ```
  - **틀림#1(탈출):** 직전까지 T라 "T" 예측인데 실제 N → 틀림. 기억을 N으로 뒤집음.
  - **틀림#2(재진입):** 방금 N으로 바뀐 기억으로 "N" 예측인데 새 루프는 T → 또 틀림.
- **딱 한 번의 예외(탈출 N)가 다음 예측까지 오염시켜 2번 miss.** 2비트는 관성으로 "약한Taken"에 머물러 재진입을 살리므로 **1번**으로 줄인다.

## Q. branch뿐 아니라 저 loop도 이게 먹는 거야?
- **loop는 별개가 아니라 loop 자체가 branch로 만들어진다.** CPU엔 for/while이 없고, 아는 건 "순차 실행"과 "분기(조건 맞으면 점프)"뿐.
  ```c
  for(i=0;i<3;i++){ work(); }
  ```
  →
  ```
        i=0
  LOOP:                  (위, 작은 주소)
        work()
        i=i+1
        blt i,3,LOOP     ← for가 사라지고 분기 하나가 생김
  ```
  - `i<3`이면 LOOP로 점프(taken)=루프 계속, 아니면 아래로(not-taken)=탈출.
- 그래서 **"루프 도느냐 마느냐" = "이 분기가 taken이냐 not-taken이냐"** 와 같은 말. 루프 예측 = 그 분기 예측.
- 이걸로 앞 내용이 연결됨: "뒤로 점프=루프=거의 taken"(BTFN), "루프 경계 2번 틀림"(그 분기의 `T T N` 기록 얘기).
- 비교: `if(조건){}` = 분기로 **아래로 건너뛰기**(forward, 보통 not-taken) / `for/while` = 분기로 **위로 되돌아가기**(backward, 거의 taken).

## Q. 6번(BTB) 더 쉽게
- 예측엔 질문이 2개: 방향(점프해?)은 BHT/2비트가 답하고, **목적지(어디로?)는 BTB가** 답한다. 방향만 맞혀선 다음 주소를 몰라 여전히 stall.
- 목적지는 명령어를 해석(ID)해야 알지만 다음 PC는 IF에서 당장 필요 → 한 박자 빈다.
- **BTB = "이 PC 분기는 지난번 어디로 점프했지?"를 PC→목적지로 외운 메모장.** 같은 분기는 보통 같은 곳으로 가니까(루프는 늘 같은 LOOP), 외워두면 해석 전에 답을 꺼내 쓴다.
  ```
  IF: 현재 PC=0x108 → BTB 조회 "분기, 지난번 0x4000"
      → taken 예측이면 다음 PC=0x4000 즉시 fetch (stall 0)
  ```
- **`ret`은 BTB가 약하다** — 같은 함수라도 호출한 곳마다 복귀지가 달라(A에서 부르면 A로, B에서 부르면 B로) 매번 틀림. → **RAS(스택)** 로 따로: call 시 복귀주소 push, ret 시 pop. 거의 100% 적중.

## Q. 저 스택은 뭐야? 왜 RAS는 스택이고 BTB는 버퍼야?
- **스택(Stack)** = 쌓아 올리고 **맨 위에서만** 꺼내는 구조(접시 쌓기). push=위에 올림, pop=맨 위 꺼냄. 마지막에 넣은 게 먼저 나옴 = **LIFO.**
- **왜 리턴은 스택이 맞나:** 함수 호출이 정확히 LIFO다.
  ```
  main→foo() : push(main복귀)      [main]
     foo→bar() : push(foo복귀)      [main, foo]
        bar ret : pop → foo로        [main]
     foo ret : pop → main으로        []
  ```
  가장 최근에 부른 함수가 가장 먼저 끝남 → "다음 복귀지"가 항상 맨 위 → 스택이면 순서가 저절로 맞음. 그래서 RAS = Return Address **Stack**.
- **왜 BTB는 버퍼(표)인가:** 분기는 **아무 순서로나** 튀어나온다(0x3F0 봤다가 다음에 0x108). 맨 위/맨 아래 같은 순서가 없고, **"이 PC의 답이 뭐였지?"를 키로 콕 집어** 찾아야 한다 → 전화번호부처럼 키(PC)로 값(목적지)을 조회하는 표 = 캐시/버퍼.
- 한 줄: **데이터가 "쌓였다 풀리는 순서(LIFO)"를 가지면 스택, "순서 없이 키로 찾아야" 하면 버퍼.** 리턴은 전자, 일반 분기 목적지는 후자.

## Q. Spectre가 뭐야? (간단히)
- **추측 실행(speculation)을 악용해, 접근 권한 없는 비밀 메모리를 캐시 흔적으로 빼내는 공격.**
- 흐름: ① CPU가 분기를 추측 실행(정상 최적화) ② 공격자가 어떤 분기를 taken으로 훈련 ③ 실제론 not-taken이어야 할(비밀 접근 금지) 상황에서 CPU가 권한 체크 전에 비밀값을 speculative read ④ 그 값으로 캐시 한 줄을 건드림 ⑤ squash로 레지스터/메모리는 복구되지만 캐시 흔적은 남음 ⑥ 캐시 타이밍 측정으로 비밀값 역추론.
- 충격 포인트: "architectural state만 안 더럽히면 안전"이란 가정이 깨짐 — squash해도 캐시 타이밍이라는 side channel로 정보가 샌다.

## Q. Spectre 4·5·6 단계가 이해 안 돼 (더 쉽게)
- **깔고 갈 사실:** 캐시 = 최근 읽은 데이터를 담는 빠른 선반. 한 번 읽은 건 다음에 **빠르고**, 안 읽은 건 **느리다.** 이 빠름/느림 차이가 전부.
- **4단계 (비밀값으로 캐시를 건드림):** 공격자가 256칸 배열 `probe[0..255]`를 준비하고 처음엔 전부 캐시에서 비워둠(다 느림). speculation 중 비밀값이 `secret=7`이면 `probe[secret]` 즉 `probe[7]`을 읽음 → **probe[7] 한 칸만 캐시에 올라온다.** 비밀값이 "어느 칸을 올릴지"를 결정.
- **5단계 (취소돼도 캐시는 안 지워짐):** CPU가 예측 틀림/권한 없음을 깨닫고 squash → 레지스터의 비밀값 지움, 메모리 변경 되돌림. **그러나 probe[7]이 캐시에 올라온 사실은 안 지움**(캐시 정리는 복구 대상이 아님). 비밀이 캐시 상태에 간접적으로 새겨진 것.
- **6단계 (빠름/느림 재서 역추론):** 공격자가 probe 256칸을 하나씩 읽으며 시간 측정. probe[7]만 빠름(⚡) → "아 speculation이 probe[7]을 건드렸구나" → **비밀값 = 7.**
- **비유:** 도둑이 금고를 몰래 보고 기억은 지워졌지만(squash), 나가기 전 7번 사물함만 살짝 열어둠. 나중에 사물함을 만져보다 "7번만 따뜻하네"로 비밀이 7이었음을 알아냄.

## Q. 그거(비밀값) 알아내면 뭐가 좋은 건데?
- 핵심은 그 "비밀 메모리"가 **원래 공격자가 절대 못 읽어야 하는 영역**이라는 것. Spectre는 그 권한 벽을 우회한다.
- 거기 든 것: **비밀번호, 암호 키(디스크 암호화/SSH/HTTPS 키), 다른 프로그램의 데이터(은행 앱·메신저), OS 커널 보호 데이터.**
- **한 바이트 → 전부:** 주소를 1씩 늘리며 반복하면 `secret[0]='p', [1]='a', [2]='s'...` → `"password123"` 통째로 유출.
- **왜 특히 무서운가:** ① 벽을 안 부수고 우회(권한 체크 끝나기 전에 슬쩍 읽음) ② 레지스터/메모리는 복구되니 로그에 흔적 거의 안 남음(들키기 어려움) ③ speculation은 20년간 모든 고성능 CPU의 기본 기능 → Intel·AMD·ARM 거의 전부 취약(2018년 전 업계 패치, 성능도 일부 하락) ④ 클라우드에서 치명적(한 서버에 여러 회사 VM이 같이 도는데 옆 칸 데이터를 훔쳐볼 수 있음).
- DV로 연결: "speculation이 architectural state만 안 더럽히면 안전"이란 가정이 깨졌으니, 이제 "추측 실행이 캐시 같은 흔적으로 비밀을 흘리지 않나"까지 검증해야 함(섹션 9의 보안 검증).
