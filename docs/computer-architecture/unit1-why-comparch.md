# Unit 1 — 왜 컴퓨터 구조를 배우는가

> 핵심 질문: 소프트웨어/RTL 위에서 일하는데 왜 그 아래 하드웨어 구조를 알아야 하나?

## 0. 블랙박스의 벽

컴퓨터를 블랙박스로 써도 평소엔 된다. 그런데 이런 벽에 부딪힌다:

- 같은 알고리즘인데 한 구현이 **10배 느림** — 코드만 봐선 안 보임.
- 가속기가 스펙대로 안 빠른데 **연산 부족인지 데이터 부족인지** 모름.
- scoreboard mismatch인데 값은 맞고 **순서만** 다름 — 버그인지 정당한지 판단 불가.

→ 전부 "한 층 아래(하드웨어가 실제로 어떻게 도나)"를 알아야 풀린다. 그게 컴퓨터 구조.

## 1. 추상화는 "성능"에서 샌다 (Leaky Abstraction)

```text
고수준 언어 → ISA(하드웨어/SW 계약) → 마이크로아키텍처(파이프라인·캐시·OoO)
            → 논리 게이트/RTL → 트랜지스터
```

각 층은 윗층에게 "세부는 신경 꺼"라 약속한다. 단, 구멍이 하나:

> **정확성(correctness)은 추상화가 지켜준다. 하지만 "얼마나 빠른가"는 절대 못 숨긴다.**

- `a+b`는 어디서든 *올바른* 합 (정확성 = 보장).
- 그 값이 레지스터/캐시/먼 메모리 중 어디 있냐로 1~수백 사이클 (성능 = 안 숨겨짐).

**핵심:** 하드웨어를 몰라도 결과는 항상 옳다 — 단지 **왜 느린지 설명을 못 할 뿐.** 추상화가 새는 곳은 *정확성*이 아니라 *성능*이다.

## 2. 증거 — 같은 코드, 10배 차이

2D 배열 합산, 루프 순서만 변경 (4KB 페이지/큰 배열 가정):

```text
A: 행 우선  for i: for j: sum += A[i][j]   // 옆 칸 연속 접근
B: 열 우선  for j: for i: sum += A[i][j]   // 한 행씩 점프
```

- 연산 횟수·결과 동일. 그런데 **B가 5~10배 느림.**
- 이유: 배열은 행 단위 연속 저장 + 메모리는 한 줄(캐시 라인)을 통째로 끌어옴.
    - A = 끌어온 라인을 알뜰히 다 씀 → 대부분 hit.
    - B = 매번 멀리 점프 → 라인에서 한 칸 쓰고 버림 → 거의 매번 miss.
- **코드 리뷰로는 안 보임** → "캐시/지역성"을 알아야만 설명됨.

(둘째 예: `if (data[i]>128)` 루프에서 데이터를 **정렬**하면 분기예측기가 패턴을 잘 맞혀 몇 배 빨라짐 — 역시 코드만 봐선 미스터리.)

## 3. "공짜 점심"은 끝났다

```text
1985~2005: 클럭 매년 ↑ (16MHz→3GHz)
2005~2025: 클럭 정체 (~3-5GHz, 거의 멈춤)  ← power wall
```

옛날엔 가만히 있어도 클럭이 올라 프로그램이 저절로 빨라졌다(=공짜 점심). 클럭이 물리 벽에 막혀 멈추자, 업계 대응이 바뀜:

```text
이전:  코어 하나를 더 빠르게 (클럭↑, ILP↑)
이후:  코어를 더 많이(멀티코어) + 구조를 영리하게(캐시·예측·OoO) + 특화 칩(GPU·NPU·DSA)
```

→ **성능은 이제 기다린다고 안 온다.** 하드웨어 구조를 아는 만큼만 끌어낼 수 있다. (그리고 칩이 복잡해진 만큼 **검증의 중요성도 폭발**.)

## 4. 모든 컴퓨터의 기본 골격: von Neumann 구조

오늘날 거의 모든 범용 컴퓨터는 **von Neumann 구조(저장 프로그램 방식, stored-program)** 위에 서 있다. 핵심 발상 한 줄:

> **명령(program)도 데이터(data)처럼 똑같은 메모리에 숫자로 저장한다.**

```text
        ┌─────────────────────────────┐
        │            CPU              │
        │  ┌───────────┐ ┌─────────┐  │
        │  │ Control    │ │  ALU    │  │   ← 제어장치(명령 해석) + 연산장치(계산)
        │  │ Unit (PC)  │ │ +레지스터│  │
        │  └───────────┘ └─────────┘  │
        └──────────────┬──────────────┘
                       │  하나의 통로(bus)
        ┌──────────────┴──────────────┐
        │           Memory            │   ← 명령 + 데이터를 같은 곳에 저장
        └─────────────────────────────┘
                 ▲                  ▲
                 │                  │
              입력(Input)        출력(Output)
```

- **구성:** ① 연산장치(ALU) ② 제어장치(Control Unit, PC로 "다음 명령" 추적) ③ 메모리 ④ 입출력.
- **저장 프로그램의 위력:** 프로그램이 데이터와 같은 메모리에 사니, **소프트웨어만 바꿔 끼우면** 같은 하드웨어가 전혀 다른 일을 한다(배선을 다시 안 해도 됨). 오늘날 "프로그래밍"의 토대.
- **동작 = fetch-execute 사이클의 반복** (Unit 5에서 한 줄의 일생으로 자세히):

```text
① fetch   : PC가 가리키는 주소에서 "명령"을 메모리에서 가져온다
② decode  : 그 명령이 뭔지 해석
③ execute : ALU로 계산 / 메모리 접근
④ PC 갱신  : 다음 명령으로 → ①로 반복
```

- **대비 — Harvard 구조:** 명령과 데이터를 *물리적으로 분리된* 메모리·통로에 둠. 임베디드/DSP, 그리고 CPU 내부 L1 캐시(I-cache/D-cache 분리)가 이 방식. 범용 시스템 바깥 큰 그림은 von Neumann.

## 4-1. 그 골격의 약점: von Neumann 병목

저장 프로그램은 강력하지만 대가가 있다 — **명령도 데이터도 결국 하나의 통로로 CPU에 와야 한다.** 그런데 CPU는 빠르고 메모리는 느리다:

```text
[CPU] ◄──── 좁고 느린 통로 ────► [메모리]
 빠름                              느림·큼
```

이 격차가 **von Neumann 병목(memory wall)**. CPU가 아무리 빨라도 데이터가 통로에서 굶으면 논다. **구조의 거의 모든 기교가 이 병목과 싸우려고 태어났다:**

```text
캐시(11~13)       = 느린 메모리를 빠른 작은 메모리로 가림
파이프라인(8)      = 기다리는 동안 다른 일 겹침
분기예측(9)       = 다음에 뭘 가져올지 미리 추측
OoO/Tomasulo(10)  = 메모리 기다리는 명령 건너뛰고 딴 거 먼저
DRAM 재정렬(14)   = 통로 사용을 효율적 순서로
멀티코어(15)      = 통로를 여러 개로
가속기/DSA(17)    = 특정 작업엔 통로 구조 자체를 다르게
```

이 한 장이 사실상 과정 전체의 목차. "왜 이 기능이 칩에 있나?" → 거의 항상 "병목과 싸우려고."

## 5. 🔌 검증 관점 — 이게 1차 원리인 이유

검증하는 모든 RTL은 위의 "병목과 싸우는 구조" 위에 얹혀 있다. 캐시가 왜 있는지, 파이프라인이 왜 stall하는지, 메모리 컨트롤러가 왜 순서를 바꾸는지를 모르면 두 현상을 못 가른다:

> **"느린데(이상한데) 버그 아닌 것"  vs  "빠른데(멀쩡한데) 실제론 틀린 것."**

이게 없으면 막히는 순간:

- **① DRAM row-hit 재정렬을 mismatch로 오인** — 값 맞고 순서만 바뀐 정당한 동작인데 버그로 신고 → 헛디버깅. (Unit 14)
- **② OoO retirement 순서 vs execution 순서 혼동** — reference model이 잘못된 기대값 → 멀쩡한 DUT를 fail시키거나 진짜 버그 통과. (Unit 10)
- **③ 가속기 성능 미달이 compute-bound인지 memory-bound인지 판단 불가** → 엉뚱한 데 디버깅. (Unit 17)

→ 셋 다 본질은 "틀린 것 vs 정당한데 달라 보이는 것"을 가르는 눈. 그 눈이 컴퓨터 구조.

## 이 과정을 꿰는 멘탈 모델

> "명령 한 줄이 어떻게 실행되고, 무엇이 빠르게/느리게 만들며, 그게 DUT에 어떻게 드러나는가?"

```text
명령 한 줄(5) → 겹쳐 실행(8) → 순서 바꿈(10) → 데이터 멀면 헛수고 → 캐시 계층(11~14)
   → 한 코어로 부족 → 멀티코어(15) → 장치와 대화(16) → 한계 재기(17)
```

## 핵심 정리

- **추상화는 정확성은 지켜주지만 성능에서 샌다** → 빠르기를 이해하려면 하드웨어를 봐야 한다.
- 같은 코드도 하드웨어 매핑(캐시·분기예측)에 따라 몇 배 차이 — 코드 리뷰로는 안 보인다.
- **공짜 점심은 끝났다** — 클럭 정체 후 성능은 구조·병렬성·특화에서 나온다.
- 모든 범용 컴퓨터의 골격 = **von Neumann 구조**(명령·데이터를 같은 메모리에 저장, fetch-execute 반복). 그 대가가 **von Neumann 병목**.
- 거의 모든 구조 기교는 **von Neumann 병목**과 싸우려고 태어났다.
- **검증:** 구조 지식 = "정당한 동작(거짓 경보 거름)"과 "깨질 수 있는 지점(놓침 방지)"을 가르는 언어.
- **Golden rule:** 정확성은 추상화가 지켜주지만, **성능과 그 정당성 판단은 하드웨어를 아는 만큼** 나온다.

## 📎 부록 — 이 단원에서 나온 질문들

### Q. "느린데 버그가 아닌 것" vs "빠른데 실제로는 틀린 것" — 쉽게 설명해줘

검증 엔지니어(scoreboard)가 "통과/실패"를 판정할 때 **두 방향으로 틀릴 수 있다** = 시험 채점관의 두 가지 실수:

```text
실수 A: 맞은 답을 틀렸다고 표시 → "거짓 경보"  = ① 느린데 버그 아님
실수 B: 틀린 답을 맞았다고 통과 → "놓침"      = ② 빠른데 실제론 틀림 (더 위험)
```

**① 느린데/이상한데 버그 아님 (거짓 경보 위험)**
DUT는 정상인데 겉보기 수상함. 예: DRAM 컨트롤러가 같은 row를 묶으려고 요청 순서를 [주소1→2→3]에서 [2→1→3]으로 바꿈 → **값은 다 맞고 순서만 바뀐 정당한 동작.** 구조를 모르면 "순서 다름=버그"로 오인해 헛디버깅. 구조를 알면 "재정렬은 정당, scoreboard를 순서 무관하게 짜야"를 앎. (성능이 낮은데 파이프라인이 정당하게 stall한 것도 같은 부류 — 느리다고 다 버그 아님.)

**② 빠른데/멀쩡한데 실제론 틀림 (놓침 위험, 더 무서움)**
DUT가 겉보기 멀쩡히 통과하는데 속으론 틀림 → 버그가 실리콘까지 유출. 예: OoO 코어가 특정 hazard에서 옛 값을 써 미묘하게 틀린 값을 빠르게 냄 → 약한 checker가 "그럴듯하니 통과". 또는 캐시가 다른 코어가 방금 바꾼 값을 모르고 stale 데이터를 빠르게 반환(일관성 버그). 구조를 알면 "이 코너에서 깨질 수 있다"를 알고 그 지점을 일부러 찌르는 테스트를 만들어 잡음.

**공통 원인:** "DUT가 *왜* 그렇게 동작하나"를 모름.

- 정당한 동작의 *이유*를 모르면 → ① 거짓 경보.
- 잘못될 수 있는 *지점*을 모르면 → ② 놓침.

**한 줄 비유:** 컴퓨터 구조를 모르는 검증 = 정답지 없이 채점하는 것. 맞은 걸 틀렸다 하고(①), 틀린 걸 맞았다 한다(②). 구조를 알면 비로소 정답지를 들고 채점.
