# RTL 기초 — 조합/순차 논리 & `=` vs `<=`

> 회로는 **조합(기억 없음) / 순차(기억 있음)** 두 종류. 코드는 `assign` / `always_comb` / `always_ff`로 쓰고, **`always_ff`엔 `<=`, `always_comb`엔 `=`**.

---

## 1. 두 기준을 먼저 구분하기

"combinational vs procedural"은 비교하는 짝이 아니다. 기준이 서로 다르다.

- **조합(combinational) vs 순차(sequential)** → **회로의 종류**
- **continuous(`assign`) vs procedural(`always` 블록)** → **코드를 쓰는 방식**

| 구분 | 회로 종류 | 기억 | 값이 바뀌는 시점 | 비유 |
| --- | --- | --- | --- | --- |
| **조합 논리** | AND, OR, MUX, 덧셈기 | 없음 | 입력이 바뀌면 **바로** | 계산기 버튼 → 화면 |
| **순차 논리** | 플립플롭, 레지스터, 카운터, FSM | 있음 | **클럭 엣지에서만** | 사진기 셔터 |

두 기준을 합치면 다음과 같다.

| 코드 | 쓰는 방식 | 만드는 회로 |
| --- | --- | --- |
| `assign y = a & b;` | continuous (한 줄) | 조합 |
| `always_comb begin ... end` | procedural | 조합 |
| `always_ff @(posedge clk) ...` | procedural | 순차 |

→ procedural은 "**어떻게 쓰느냐**"일 뿐, 그걸로 조합 회로도 순차 회로도 만들 수 있다.

---

## 2. `assign` vs `always_comb`

**둘 다 조합 회로**를 만든다. 차이는 "얼마나 복잡한 조건을 쓸 수 있느냐"다.

```systemverilog
// assign — 식 하나로 선을 연결
assign y   = a & b;
assign out = sel ? d1 : d0;   // 2:1 MUX
```

```systemverilog
// always_comb — 블록 안에 문장 여러 줄
always_comb begin
  out = d3;                // 기본값 먼저
  case (sel)
    2'd0: out = d0;
    2'd1: out = d1;
    2'd2: out = d2;
  endcase
end
```

| 항목 | `assign` | `always_comb` |
| --- | --- | --- |
| **표현** | 식 하나 | `if`, `case`, 중간 변수, 여러 출력 |
| **래치 위험** | 없음 (항상 식이 연결돼 있음) | 모든 경우에 값을 안 주면 생김 |
| **언제 쓰나** | 식 하나로 끝날 때 | 조건이 여러 개거나 `case`가 필요할 때 |

## 3. 의도치 않은 Latch & 글리치(Glitch)

**래치(Latch)**는 값을 기억하는 회로다. 원래 기억이 없어야 하는 조합 회로를 만들려다 `else`/`default`를 빼먹어 실수로 "기억"이 들어간 상황이다.

```systemverilog
// ❌ 나쁜 예: sel=0일 때 y 값을 안 정함 → "이전 값 유지" → 래치 추론!
always_comb begin
  if (sel)
    y = a;
end

// ✅ 좋은 예: 맨 윗줄에 기본값을 먼저 주면 모든 경우에 값이 정해짐
always_comb begin
  y = '0;
  if (sel) y = a;
end
```

### 래치는 어디서만 생길까?

실수로 생기는 래치는 **조합 회로 블록(`always_comb`, `always @(*)`)에서만** 생긴다.

| 구문 | 조건(`else`) 누락 시 결과 | 래치 발생 여부 |
| --- | --- | --- |
| **`assign`** | 문법상 조건을 빼먹을 수 없음 (항상 식이 연결됨) | **안 생김** |
| **`always_ff @(posedge clk)`** | "이전 값을 유지하는 **정상 플립플롭**" (Enable 달린 FF: `if (en) q <= d;`) | **안 생김** (FF 생성) |
| **`always_comb`** | 클럭도 없는데 이전 값을 기억해야 해서 **래치(Latch)** 추론 | **생김 ⚠️** (의도적 래치는 `always_latch`) |

---

### 의도치 않은 래치가 위험한 4가지 이유

| # | 위험 요인 | 플립플롭 (`always_ff`) | 의도치 않은 래치 (`always_comb` 실수) |
| --- | --- | --- | --- |
| **①** | **투명성 (창문 열림)** | 클럭 엣지 순간만 찍는 **사진기 셔터** | 조건(`sel=1`) 동안 내내 열려 있는 **창문** |
| **②** | **글리치(Glitch)에 취약** | 글리치가 가라앉은 **클럭 정각**만 찍어 무시 | `sel`에 글리치가 튀면 창문이 열려 **쓰레기 값 영구 저장** |
| **③** | **타이밍 검사 (STA)** | 정각 출발 → 정각 도착이라 계산 명확 | 창문이 열린 동안 신호가 그냥 통과해 **경계가 흐려짐** |
| **④** | **시뮬레이션 은폐** | RTL과 실제 칩 동작이 일치 | RTL 시뮬(지연 `0초`)에선 글리치가 안 보여 **가짜 PASS** 후 실제 칩에서만 터짐 |

#### ① 창문이 계속 열려 있음 (투명성 문제)

- 플립플롭은 클럭이 올라가는 "찰칵" 한 순간만 문을 여는 **사진기 셔터**지만, 래치는 `sel=1`인 동안 내내 열려 있는 **창문**이다.
- `sel=1`인 동안 입력 `a`가 흔들리면 출력 `y`도 클럭과 무관하게 실시간으로 흔들리고, `sel=0`이 되는 순간 마지막 값이 그대로 갇힌다.

#### ② 글리치(Glitch, 찰나의 가짜 신호)를 삼켜서 영구 저장함

- **글리치란?** 두 개 이상의 신호가 조합 회로를 거칠 때 **선 길이(도착 시간) 차이**로 출력이 잠깐 튀는 현상이다. (단독 외길 신호에서는 안 생기고 **두 신호가 합쳐질 때만** 발생)

```text
예: sel = p & q  (p: 1→0 느린 선, q: 0→1 빠른 선으로 동시에 바뀔 때)

  p (느린 선) : ━━━━━━┓
                      ┗━━━━━━━━━━━━  (1 → 0 늦게 도착)
  q (빠른 선) : ━━━┏━━━━━━━━━━━━━━━  (0 → 1 먼저 도착)
                   ┃  ┃
  sel = p & q : ━━━┛  ┗━━━━━━━━━━━━  ← 둘 다 1인 찰나에 0 → 1 → 0 가짜 신호(Glitch) 발생!
                  (찰나!)
```

- **플립플롭**: 글리치가 다 가라앉은 뒤 **클럭 정각**만 찍으므로 글리치를 무시한다.
- **래치**: `sel` 선에 잠깐 튄 글리치(`0→1→0`)에도 창문이 열렸다가 닫히면서 **그 순간의 쓰레기 값을 영구 저장**해 버린다.

#### ③ 타이밍 검사(STA)가 어려워짐

- 플립플롭은 **정각 출발 → 정각 도착**하는 기차와 같아 "한 클럭 안에 도착하는가"를 계산(STA)하기 쉽다.
- 래치는 창문이 열려 있는 동안 아무 때나 신호가 통과해 출발선과 결승선의 경계가 흐려진다.

#### ④ RTL 시뮬레이션에선 숨어 있다가 실제 칩에서만 터짐

- 일반 RTL 시뮬레이션은 모든 선의 이동 지연을 **`0초`로 가정**하므로, 도착 시간 차이로 생기는 글리치가 아예 나타나지 않아 테스트가 **100% PASS**한다.
- 실제 칩에는 물리적 선 길이 차이가 있어 글리치가 생기고, 시뮬레이션에선 한 번도 안 열렸던 래치 창문이 열리며 버그가 터진다.

---

### 실무 방지 규칙 3가지

!!! tip "래치 & 글리치 실무 방지 3원칙"
    1. **기억 소자는 무조건 `always_ff`(플립플롭)로만** 만든다. (데이터 선의 글리치는 클럭 엣지 전에 가라앉아 안전)
    2. **`always_comb`에서는 래치가 절대 안 생기게** 맨 윗줄 기본값(`y = '0;`) 또는 `else`/`default`를 빠짐없이 채운다.
    3. **방아쇠 핀(`clk`, `rst_n`)에는 절대 두 신호를 합친 조합 회로 출력을 꽂지 않고, 외길 단독 신호(PLL/FF 직출)만 연결**한다.

```systemverilog
// ❌ 금지: 클럭에 조합 회로를 섞으면 클럭 자체에 글리치(가짜 엣지) 발생!
// (클럭을 직접 꺼야 할 땐 전용 부품인 ICG를 사용)
assign sub_clk = clk & en;

// ✅ 정석: clk는 외길 그대로 두고, en은 데이터 입구(d 쪽)에서 처리
always_ff @(posedge clk) begin
  if (en) q <= d;
end
```

## 4. 순차 논리와 `always_ff`

기본 부품은 **D 플립플롭** (입력 `d`, 클럭 `clk`, 출력 `q`).

- `clk`가 `0 → 1`로 올라가는 순간(`posedge`) `d`를 찍어서 `q`에 저장한다.
- 그 외 시간엔 `d`가 바뀌어도 `q`는 그대로 유지된다 (셔터를 누른 순간만 저장되는 사진기).

```systemverilog
// 기본 플립플롭
always_ff @(posedge clk) begin
  q <= d;
end

// 비동기 리셋 — 전원 직후 FF 값은 알 수 없으므로 시작 값을 정해줌
always_ff @(posedge clk or negedge rst_n) begin
  if (!rst_n) q <= '0;
  else        q <= d;
end
```

- "지금 몇 번째인지", "지금 어떤 상태인지"처럼 **과거를 기억해야 하는 건 전부 순차 논리**다 (카운터, 레지스터, [FSM](fsm.md)).
- 리셋을 빼먹었을 때 `X`가 퍼지는 현상은 → [X propagation & `xprop` 옵션](x-propagation.md)

## 5. `always` vs `always_ff` / `always_comb`

만들어지는 회로는 같을 수 있다. 차이는 **의도를 선언하고, 도구가 그걸 검사해 준다**는 것이다.

```verilog
// 옛 Verilog — always 하나로 FF도, 조합도, 래치도 다 만듦 → 실수해도 조용히 넘어감
always @(posedge clk) q <= d;     // 플립플롭
always @(*)           y = a & b;  // 조합 회로
```

| 블록 | 용도 | 도구가 자동으로 잡아주는 실수 |
| --- | --- | --- |
| **`always_ff`** | 플립플롭 (순차) | 클럭 엣지 누락, FF가 아닌 회로(래치/조합) 추론, 다중 블록 구동 시 에러 |
| **`always_comb`** | 조합 회로 | 감도 리스트 자동 완성, 의도치 않은 래치 추론 시 경고/에러 |
| **`always`** | 회로가 아닌 곳 | TB 클럭 생성 (`always #5 clk = ~clk;`) 등 |

## 6. `=` (blocking) vs `<=` (non-blocking)

### 개념과 비유

| 연산자 | 동작 | 비유 | 쓰는 곳 |
| --- | --- | --- | --- |
| **blocking `=`** | 값이 바뀔 때까지 다음 줄을 막고 기다림 → **다음 줄은 바뀐 값을 봄** | **요리 레시피**: 1번 줄에서 재료를 썰고(`tmp = a + b`), 2번 줄에서 바로 그 재료를 볶음(`y = tmp * 2`) | **`always_comb`** |
| **non-blocking `<=`** | 값 넣기는 나중으로 예약만 하고 바로 다음 줄로 → **다음 줄은 바뀌기 전 값을 봄** | **단체 공 넘기기**: 호루라기(클럭)가 울리면 모두 동시에 직전에 들고 있던 공을 옆 사람에게 넘김 | **`always_ff`** |

### 코드 비교 (`always_ff` 시프트 레지스터)

```systemverilog
// ✅ <= : 시프트 레지스터 (한 클럭에 한 칸씩 이동)
always_ff @(posedge clk) begin
  B <= A;
  C <= B;
end

// ❌ = : A가 B를 거쳐 C까지 한 번에 날아가 버림
always_ff @(posedge clk) begin
  B = A;
  C = B;
end
```

| 시점 | `<=` 버전 (`B`, `C`) | `=` 버전 (`B`, `C`) |
| --- | --- | --- |
| 시작 (`A=🔴, B=🔵, C=🟢`) | 🔵, 🟢 | 🔵, 🟢 |
| 1번째 클럭 직후 | **🔴, 🔵** (한 칸씩 이동 ✅) | **🔴, 🔴** (`B`가 즉시 바뀌어 `C`까지 덮어씀 ❌) |

### 시뮬레이터 안에서 `<=`의 2단계 동작

- **1단계 — 읽기 (Active)**: 클럭이 올라가면 모든 `<=`의 오른쪽 값을 먼저 읽어 메모한다 (모두 공을 꽉 쥐고 준비).
- **2단계 — 쓰기 (NBA)**: 그 시점 계산이 다 끝나면 메모한 값을 한꺼번에 왼쪽에 넣는다 (하나, 둘, 셋에 동시에 넘기기).

```systemverilog
// <= 는 다 읽고 나서 한꺼번에 쓰므로 줄 순서를 바꿔도 결과가 똑같다!
always_ff @(posedge clk) begin
  C <= B;
  B <= A;
end
```

- 반대로 `always_comb`에 `<=`를 쓰면 다음 줄이 **갱신 전 옛날 `tmp`**를 읽어 틀린 값이 나오므로, 조합 회로엔 반드시 `=`를 쓴다.

!!! warning "하지 말 것"
    한 블록 안에서 `=`와 `<=`를 **섞어 쓰지 않는다**. 언제 바뀌는지 헷갈려 버그가 생기고 리뷰도 어렵다.

    - UVM Driver / Monitor에서의 `=` vs `<=` 구분은 → [Driver / Monitor의 `=` vs `<=`](../uvm/driver-monitor-blocking-nonblocking.md)

## 7. 핵심 규칙 요약

- 조합/순차는 **회로 종류**, `assign`/procedural은 **쓰는 방식**이다.
- 식 하나면 `assign`, 조건이 많으면 `always_comb`을 쓴다.
- `always_comb`에선 **맨 윗줄 기본값 먼저** → 의도치 않은 래치 방지 (래치는 `always_comb`에서만 추론됨).
- 클럭/리셋 선에는 조합 회로를 섞지 않고 **외길 단독 신호**만 연결해 글리치를 차단한다.
- 플립플롭은 `always_ff`, 조합은 `always_comb`, 그냥 `always`는 TB용이다.
- **`always_ff`엔 `<=`, `always_comb`엔 `=`**, 한 블록에서 섞지 않는다.
