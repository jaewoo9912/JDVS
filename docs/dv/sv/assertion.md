# assertion (SVA — SystemVerilog Assertions)

> "이 조건은 **항상 참이어야 한다**"를 회로 옆 **자동 감시 카메라(CCTV)**처럼 코드로 박아두고, 깨지는 순간 시뮬레이터가 **시각·위치까지 짚어** 알려주는 기능.

---

## 1. 핵심 개념 & 기본 뼈대

- **Scoreboard vs Assertion**: Scoreboard가 최종 **결과값**을 비교한다면, Assertion은 그 사이의 **프로토콜·타이밍 규칙**(handshake, FSM 전이, 신호 안정성)을 신호 레벨에서 직접 감시한다.
- **목적**: 버그가 뒷단으로 퍼지기 전에 **발생 지점·클럭에서 즉시** 잡는다.

```systemverilog
// 기본 뼈대: 클럭마다 감시하되, 리셋 중엔 끄고, [방아쇠]가 맞으면 [결과]를 확인!
assert property (@(posedge clk) disable iff (!rst_n)
  (state == IDLE && start) |=> (state == BUSY)
) else $error("IDLE에서 start 후 BUSY 전이 실패!");
```

| 구성 요소 | 역할 |
| --- | --- |
| **`@(posedge clk)`** | 감시 카메라가 사진을 찍을 기준 클럭 |
| **`disable iff (!rst_n)`** | 리셋(`rst_n == 0`) 중에는 감시를 꺼서 가짜 에러(헛발) 방지 |
| **왼쪽 (`state == IDLE && start`)** | 언제 감시를 시작할지 (**선행조건 / 방아쇠**) |
| **오른쪽 (`state == BUSY`)** | 그때 반드시 일어나야 하는 일 (**후행결과**) |

---

## 2. 두 종류 — Immediate vs Concurrent (`property`의 유무)

비유하면 **그 순간 찍는 사진 한 장(Immediate)**이냐, **매 클럭마다 계속 찍는 CCTV 동영상(Concurrent)**이냐의 차이다. 코드에서 가장 확실한 구분 기준은 **`property` 키워드의 유무**다.

| 구분 | Immediate (`assert (...)`) | Concurrent (`assert property (...)`) |
| --- | --- | --- |
| **비유** | 그 줄을 지나는 순간 찍는 **사진 한 장** | 클럭마다 백그라운드로 계속 찍는 **CCTV 동영상** |
| **문법 구분** | **`property` 없음** (`if`문에서 `if`만 `assert`로 바꾼 모양) | **`property` 있음** (`@(posedge clk)`, `disable iff` 포함) |
| **시간 기호 (`##`, `\|->`, `\|=>`, `[*]`)** | **사용 불가** (현재 순간의 참/거짓 식만 가능) | **사용 가능** (여러 클럭에 걸친 시간 순서·반복 표현) |
| **적는 위치** | `always_comb`, `initial`, `task/function` 블록 **안** | `module`, `interface` **안** (절차 블록 바깥) |
| **글리치 영향** | 그대로 받음 (과도기 가짜 에러 가능 → `assert final`로 보완) | 안 받음 (클럭 엣지의 안정된 값만 샘플링) |

```systemverilog
// ① Immediate (property 없음) — 블록 안에서 "지금 당장 이 값이 맞나"만 체크
always_comb begin
  assert (!(a && b)) else $error("a와 b가 동시에 1임!");
end

// ② Concurrent (property 있음) — 한 줄로 쓰거나, property에 이름을 붙여 두 줄로 분리
assert property (@(posedge clk) disable iff (!rst_n)
  req |-> ##[1:5] ack
);

// (실무에서 자주 쓰는 두 줄 분리형 — assert property가 있으면 무조건 Concurrent!)
property p_handshake;
  @(posedge clk) disable iff (!rst_n)
  valid |-> ##[1:3] ready;
endproperty
a_handshake: assert property (p_handshake);
```

!!! note "왜 조합 논리 결과를 검사할 때도 `@(posedge clk)`를 쓸까?"
    조합 논리(`assign done_pulse = (state == DONE);`) 자체는 클럭과 무관하게 즉시 바뀌지만, 클럭과 클럭 사이(과도기)에는 **글리치**가 튀거나 시뮬레이터 내부 실행 순서 차이로 찰나의 불일치가 생길 수 있다.

    따라서 **"계산과 글리치가 다 가라앉아 조용해진 `posedge clk` 정각에만 사진을 찍되, 같은 사진 안에 두 조건이 함께 맞는지(`|->`) 확인하라"**는 뜻으로 `@(posedge clk)`를 쓴다.

## 3. 화살표 두 개: `|->` (0칸 이동) vs `|=>` (1칸 이동)

| 화살표 | 이름 | 보드게임 칸 이동 | 결과 확인 시점 | 주로 쓰는 곳 |
| --- | --- | --- | --- | --- |
| **`\|->`** | overlapped implication | **0칸 이동** (`\|-> ##0`과 동일) | 조건이 맞은 **바로 그 클럭** | 조합 논리 출력처럼 **즉시** 나와야 하는 결과 |
| **`\|=>`** | non-overlapped implication | **1칸 이동** (`\|-> ##1`과 동일) | 조건이 맞은 **다음 클럭** | 플립플롭(`always_ff`, `<=`)을 거쳐 **1클럭 뒤에** 나오는 결과 |

### 뒤에 `##숫자`가 붙을 때 칸 계산법 (덧셈 규칙)

**`|->`는 `0칸`**, **`|=>`는 `1칸`**으로 놓고 뒤에 붙은 `##숫자`를 그대로 더하면 몇 번째 클럭에서 확인하는지 바로 나온다.

```text
클럭 칸 :  [E1] ──1칸──> [E2] ──1칸──> [E3]
req     :   1
|-> ##1 :  (0칸) ──────> E2에서 ack 확인! (0 + 1 = 1칸 뒤)
|=> ##1 :        (|=>로 1칸) ──(##1로 1칸)──> E3에서 ack 확인! (1 + 1 = 2칸 뒤)
```

| 식 | 칸 덧셈 | 의미 |
| --- | --- | --- |
| `req \|-> ##1 ack` | `0 + 1 = 1칸 뒤` | `req |=> ack`와 완전히 동일 (다음 클럭 E2에서 확인) |
| `req \|=> ##1 ack` | `1 + 1 = 2칸 뒤` | 다다음 클럭(E3)에서 확인 |
| `req \|-> ##[1:10] ack` | `0 + (1~10)` | **1~10클럭 이내**에 `ack` 확인 (숫자가 직관적이라 실무 권장) |
| `req \|=> ##[1:10] ack` | `1 + (1~10)` | **2~11클럭 이내**에 `ack` 확인 |

## 4. SVA 시퀀스 공식 (`[*]` 연속 유지 vs `##` 시간 이동)

SVA 시퀀스는 아래 **한 가지 레고 블록 공식**이 반복된다.

> **`[신호A][몇 클럭 연속 유지할지 *]   ##[몇 클럭 뒤로 갈지]   [신호B][몇 클럭 연속 유지할지 *]`**

| 구분 | 표기 위치 | 기호 예시 | 의미 |
| --- | --- | --- | --- |
| **연속 유지 (`[*]`)** | 신호 이름 **뒤** | `A` (생략 시 `A[*1]`) | `A`가 **1클럭** 동안 참 |
| | | `A[*3]` | `A`가 쉬지 않고 **3클럭 연속** 참 (`A ##1 A ##1 A`) |
| | | `A[*1:4]` | `A`가 **1~4클럭 연속** 참 |
| | | `A[*1:$]` | `A`가 **1클럭부터 무한대(`$`)까지 연속** 참 |
| **시간 이동 (`##`)** | 다음 신호 **앞** | `##1` / `##N` | 앞 구간이 끝난 뒤 **1칸(N칸) 뒤** 클럭으로 이동 |
| | | `##[1:4]` | 앞 구간이 끝난 뒤 **1~4칸 사이 어딘가**에 한 번이라도 참이면 통과 |
| | | **`##0`** | **0칸 이동** = 앞 구간이 끝나는 **바로 그 마지막 클럭에서 동시에(겹쳐서)** 확인 |

---

### 자주 헷갈리는 문법 핵심 3가지

#### ① 왜 `busy[1:10]`이 아니라 `*`를 붙여서 `busy[*1:10]`으로 쓸까?

- `*` 없이 `busy[1:10]`이라고 쓰면 시뮬레이터가 클럭 반복이 아니라 **`busy` 신호의 1~10번 비트를 잘라낸 값(비트 슬라이싱, 예: `data[7:0]`)**으로 인식한다.
- 따라서 신호 뒤 대괄호에는 반드시 `*`를 붙여 **"비트 번호가 아니라 클럭 반복 횟수"**임을 표시해야 한다. (반면 `##[1:10]`은 앞에 `##`이 있어 비트 번호와 헷갈리지 않으므로 `*` 없이 쓴다.)

#### ② `start |=> [*3] busy`처럼 신호 앞에 `[*3]`을 쓸 수 있을까?

- **불가능(문법 에러)**. `[*3]`은 "무엇을 3번 반복할지" 대상이 앞에 있어야 하므로 반드시 **신호 이름 뒤(`busy[*3]`)**에 붙여야 한다.

#### ③ `##[1:10] busy` (신호 앞) vs `busy[*1:10]` (신호 뒤)의 차이

| 식 | 기호 위치 | 의미 | 파형 예시 (`E1 E2 E3 E4`) |
| --- | --- | --- | --- |
| **`##[1:10] busy`** | 신호 **앞** (`##`) | 1~10클럭 사이 어딘가에서 **딱 한 번만 `1`**이면 통과 (중간엔 `0`이어도 됨) | `0  0  0  1` → **통과 ✅** |
| **`busy[*1:10]`** | 신호 **뒤** (`[*]`) | 중간에 한 번도 `0`으로 안 끊기고 **연속으로 내내 `1` 유지** | `1  1  1  (done)` → **통과 ✅** |

---

### `##0` vs `##1` 완벽 비교 (택배 기사님 비유)

`$rose(valid) |-> valid[*1:$] ##0 ready` (또는 `valid until_with ready`)는 **"택배 기사님(`valid`)이 벨을 누르면, 문(`ready`)을 열어줄 때까지 떠나지 않고 계속 서 있어야 한다"**는 핸드셰이크 규칙이다.

```text
클럭                   :  E1   E2   E3   E4
ready (문 열림)        :   0    0    0    1   (E4에서 드디어 문을 열어줌!)

[✅ ##0 사용: valid[*1:$] ##0 ready]  (0칸 이동 = 마지막 칸 E4에서 겹침)
valid                  :   1 ───1 ───1 ───1   ← 문이 열리는 E4 그 순간까지 valid=1 유지! (정상 핸드셰이크)

[❌ ##1 사용: valid[*1:$] ##1 ready]  (1칸 이동 = valid 끝난 다음 칸에서 ready 체크)
valid                  :   1 ───1 ───1    0   ← E3까지만 서 있다가 문 열리기 직전(E4)에 가버려도(valid=0) 통과됨!
                                     ↘ ##1 (한 칸 뒤인 E4에서 빈 문만 열려도 합격 처리)
```

- **`##0`**: `valid`가 `1`로 유지되는 **바로 그 마지막 클럭(E4)에 `ready=1`과 동시에** 만나야 한다.
- **`##1`**: `valid` 행진이 끝난 **다음 클럭**에 `ready=1`이면 되므로, 정작 `ready=1`인 클럭에 `valid=0`으로 떨어져도 통과해 버린다.

## 5. 지난 클럭과 비교하는 함수 3총사 (`$rose`, `$fell`, `$stable`)

현재 클럭의 값만 보는 것을 넘어, **"직전 클럭과 비교해 어떻게 바뀌었는지"**를 검사하는 필수 함수 3개다.

| 함수 | 참(True)이 되는 조건 | 실무 용도 |
| --- | --- | --- |
| **`$rose(sig)`** | 지난 클럭 `0` → 이번 클럭 `1`로 **막 올라간 첫 클럭에만** 참 | 신호가 1인 내내 매 클럭 감시가 중복 시작되지 않고, **처음 켜진 순간 딱 한 번만** 감시 시작 |
| **`$fell(sig)`** | 지난 클럭 `1` → 이번 클럭 `0`으로 **막 내려간 순간에만** 참 | 작업 완료 후 신호가 정상적으로 내려가는지 확인 |
| **`$stable(sig)`** | 지난 클럭 값과 이번 클럭 값이 **바뀌지 않고 그대로 유지**되면 참 | 대기 중 주소/데이터 버스(32비트 등)가 흔들리지 않고 유지되는지 확인 |

```text
클럭         :  E1    E2    E3    E4
sig          :   0     1     1     0
────────────────────────────────────────────────────────
$rose(sig)   :   X    참!   거짓  거짓   (0 → 1 올라간 E2만 참)
$stable(sig) :   X   거짓    참!  거짓   (1 → 1 유지된 E3만 참)
$fell(sig)   :   X   거짓   거짓   참!   (1 → 0 내려간 E4만 참)
```

## 6. 실무 Assertion 해석 단어장 7개 & 5대 대표 패턴

실무 SVA 코드는 아래 **단어장 7개**만 대입해 왼쪽에서 오른쪽으로 읽으면 90% 이상 바로 해석된다.

| 번호 | 기호 | 한국어 번역 |
| --- | --- | --- |
| **1** | **`\|->`** | (왼쪽이 참이면) **바로 그 클럭에** (`0칸` 이동) |
| **2** | **`\|=>`** | (왼쪽이 참이면) **다음 클럭에** (`1칸` 이동) |
| **3** | **`##N` / `##[a:b]`** | **N클럭 뒤에** / **a~b클럭 사이 안에 한 번** (`##0`은 **끝나는 바로 그 클럭에 동시에**) |
| **4** | **`신호[*N]` / `[*a:b]`** | 신호가 안 끊기고 **N클럭(a~b클럭) 연속 1 유지** (`$`는 끝까지 쭉) |
| **5** | **`$rose(신호)`** | 신호가 **`0 → 1`로 막 올라갔을 때** |
| **6** | **`$fell(신호)`** | 신호가 **`1 → 0`으로 막 내려갔을 때** |
| **7** | **`$stable(신호)`** | 신호 값이 **지난 클럭과 똑같이 유지** |

---

### 실무 5대 대표 패턴 쪼개서 읽기

#### 패턴 1 — 기본 응답 시간 체크 (`##[a:b]` : 건너뛰어 한 번 체크)

```systemverilog
$rose(req) |-> ##[1:4] ack
```

- **쪼개 읽기**: `$rose(req)` (`req`가 0→1로 막 올라오면) + `|-> ##[1:4]` (그 클럭 기준 1~4클럭 이내에) + `ack` (`ack`가 한 번 1이어야 한다 — 중간 클럭엔 0이어도 됨).

#### 패턴 2 — 고정된 클럭 동안 신호 연속 유지 (`[*N]` : 연속 도장 찍기)

```systemverilog
$rose(err) |-> irq[*4]
```

- **쪼개 읽기**: `$rose(err)` (`err`가 막 발생하면) + `|->` (바로 그 클럭부터) + `irq[*4]` (4클럭 동안 쉬지 않고 연속으로 `irq=1`을 유지해야 한다).

#### 패턴 3 — 대기 중 값 변경 금지 (`|=>` + `$stable`)

```systemverilog
(valid && !ready) |=> valid && $stable(data)
```

- **쪼개 읽기**: `(valid && !ready)` (데이터를 내밀었는데 상대가 아직 못 받으면) + `|=>` (다음 클럭에도) + `valid && $stable(data)` (`valid`를 내리지 말고 `data` 값도 바꾸지 말아야 한다).

#### 패턴 4 — 연속 유지 후 완료 신호 체크 (`[*a:b]` + `##1`)

```systemverilog
start |=> busy[*1:8] ##1 done
```

- **쪼개 읽기**: `start |=>` (`start` 다음 클럭부터) + `busy[*1:8]` (1~8클럭 동안 `busy`가 끊기지 않고 1로 유지된 직후) + `##1 done` (그 다음 클럭에 `done=1`이 떠야 한다).

#### 패턴 5 — 끝까지 유지되다가 같은 클럭에 만나기 (`[*1:$]` + `##0`)

```systemverilog
$rose(valid) |-> valid[*1:$] ##0 ready
```

- **쪼개 읽기**: `$rose(valid) |->` (`valid`가 막 올라오면 그 클럭부터) + `valid[*1:$]` (중간에 0으로 떨어지지 않고 쭉 유지되다가) + `##0 ready` (마지막 클럭에 `ready=1`과 **동시에** 만나야 한다).

## 7. `property` 분리 문법 & `assert` / `cover` / `assume` 3총사

### 1) 한 줄 작성 vs `property` 분리 작성 (실무 표준)

실무에서는 타이밍 규칙(`property`)을 먼저 정의해 두고, 그 아래에서 용도(`assert` / `cover` / `assume`)를 정해 끼워 넣는 **2단 분리 스타일**을 많이 쓴다. 같은 규칙 하나를 `assert`와 `cover`에 동시에 재사용할 수 있기 때문이다.

```systemverilog
// 스타일 1: 한 줄로 합쳐 쓰기
// [이름]: assert property ( @[클럭] disable iff ([리셋]) [알맹이 식] );
a_req_ack: assert property (@(posedge clk) disable iff (!rst_n) req |=> ack);

// 스타일 2: property(규칙 내용물)를 먼저 정의하고, 아래에서 용도(assert/cover) 지정하기
property p_req_ack;
  @(posedge clk) disable iff (!rst_n)
  req |=> ack;
endproperty

a_req_ack: assert property (p_req_ack);   // 에러 감시용으로 사용
c_req_ack: cover  property (p_req_ack);   // 출석 체크용으로 재사용!
```

---

### 2) `assert` / `cover` / `assume` 차이 (신호등 단속 카메라 비유)

안쪽 `property` 식은 똑같고, 맨 앞 키워드로 **"이 식을 왜 적어놨는지(목적)"**만 구분한다.

| 지시어 | 비유 | 역할 | 좋은 결과 기준 |
| --- | --- | --- | --- |
| **`assert property`** | **과속·신호위반 단속 카메라** | 규칙을 어기는 순간 즉시 `$error` 출력 | **Fail `0회`**여야 좋음 |
| **`cover property`** | **교통량 체크 카운터 (출석 도장)** | 그 상황이 실제로 몇 번 일어났는지 카운트 | **Hit `1회 이상`**이어야 좋음 |
| **`assume property`** | **"운전자는 면허가 있다"는 전제** | 입력 신호가 이 규칙을 지킨다고 가정 (Formal은 입력 범위 한정, 시뮬레이션은 TB 입력 감시) | 위반 `0회` |

!!! warning "왜 `assert` 옆에 반드시 `cover`를 짝으로 달아야 할까? (Vacuous Pass 함정)"
    도로에 단속 카메라(`assert`)를 달았는데 **새벽이라 차(`req`)가 한 대도 안 지나갔다면?** 위반 건수는 `0건`으로 뜨지만, 차가 아예 안 다녔으니 신호등을 진짜로 검증한 것이 아니다(**Vacuous Pass, 가짜 통과**).

    그래서 옆에 통행량 카운터(`cover`)를 함께 달아 **`Hit 0회`면 "에러는 안 났지만 아직 이 상황을 테스트조차 안 해봤구나!"** 하고 즉시 잡아낸다.

### 3) 실제 코드 & 시뮬레이션 리포트 4가지 상황

```systemverilog
module dut_checker (
  input logic clk, rst_n,
  input logic req,   // TB가 DUT에 넣는 입력
  input logic ack    // DUT가 내보내는 출력
);
  // ① assert (단속 카메라): req가 오면 다음 클럭에 무조건 ack가 와야 함
  a_req_ack: assert property (@(posedge clk) disable iff (!rst_n)
    req |=> ack
  ) else $error("위반! req 다음 클럭에 ack 없음!");

  // ② cover (통행량 카운터): req 다음 클럭에 ack가 오는 장면이 실제로 몇 번 나왔나?
  c_req_ack: cover property (@(posedge clk) disable iff (!rst_n)
    req ##1 ack
  );

  // ③ assume (입력 전제조건): TB는 ack 전에 req를 2클럭 연속 안 보낸다고 가정
  m_no_b2b_req: assume property (@(posedge clk) disable iff (!rst_n)
    req |=> !req
  );
endmodule
```

| 시뮬레이션 상황 | `a_req_ack` (`assert`) | `c_req_ack` (`cover`) | 판정 |
| --- | --- | --- | --- |
| **① TB 고장으로 `req`를 한 번도 안 보냄** | Fail `0회` (통과처럼 보임) | **Hit `0회` 🚨** | `cover` 덕분에 `req` 미인가 즉시 발각! |
| **② `req` 10번 전송 & 10번 모두 다음 클럭 `ack` 응답** | **Fail `0회` ✅** | **Hit `10회` ✅** | 진짜로 10번 시험했고 모두 통과 확신 |
| **③ `req` 보냈는데 DUT 버그로 다음 클럭 `ack=0`** | **즉시 `$error` (Fail `1회`) 🚨** | Hit `0회` | DUT 버그 발생 즉시 검출 |
| **④ TB 실수로 `req`를 2클럭 연속(`1→1`) 전송** | — | — | `m_no_b2b_req` (`assume`)가 TB 입력 약속 위반 알림 |

## 8. 실전 코드 해석 점검 Q&A (3문제)

???+ question "Q1. `$rose` + `|->` + `##[1:3]` 해석하기"
    ```systemverilog
    property p1;
      @(posedge clk) disable iff (!rst_n)
      $rose(cmd_valid) |-> ##[1:3] cmd_ack;
    endproperty
    a1: assert property (p1);
    ```

    - **해석**: 리셋 상태가 아닐 때, `posedge clk`에서 `cmd_valid`가 `0 → 1`로 올라간 **바로 그 클럭(`|->`, 0칸)을 기준으로 1~3클럭 이내**에 `cmd_ack`가 `1`로 떠야 한다.
    - **주의**: 화살표가 `|=>`가 아니라 **`|->`**이므로 "다음 클럭부터 1~3클럭 뒤(=2~4클럭)"가 아니라 **"올라간 그 클럭 기준 1~3클럭 뒤"**다.

???+ question "Q2. 대기 중 신호·주소 유지 감시 (`|=>` + `$stable`)"
    ```systemverilog
    property p2;
      @(posedge clk) disable iff (!rst_n)
      (req && !gnt) |=> req && $stable(addr);
    endproperty
    a2: assert property (p2);
    ```

    - **해석**: 리셋이 아닐 때, 이번 클럭에 `req == 1`이고 `gnt == 0`(아직 허락 못 받음)이면, **다음 클럭(`|=>`)에도 `req`는 `1`을 유지하고 `addr`은 이전 클럭의 값과 같아야(`$stable`)** 한다.

???+ question "Q3. 연속 유지 후 완료 시나리오 출석 체크 (`[*4]` + `##1` + `cover`)"
    ```systemverilog
    property p3;
      @(posedge clk) disable iff (!rst_n)
      start |=> run[*4] ##1 done;
    endproperty
    c3: cover property (p3);
    ```

    - **해석**: `start == 1`이 된 **다음 클럭(`|=>`)부터 `run`이 4클럭 연속 `1`로 유지**되고, 그 **바로 다음 클럭(`##1`)에 `done == 1`**이 발생해야 통과한다.
    - **왜 `cover`인가?**: 에러를 잡으려는 것이 아니라, **이 시나리오가 시뮬레이션 중 실제로 최소 1번 이상 일어났는지(출석 도장)** 확인하기 위해서다.

---

- **어디에 적나**: 포트 신호는 주로 **`interface`** 안에 적고, 포트로 나와 있지 않은 DUT 내부 신호(FSM `state`, Arbiter `req`/`gnt` 등)는 원본 수정 없이 **[`bind`로 외부에서 꽂아 넣어 감시](bind.md)**한다.
