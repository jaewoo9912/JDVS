## Q1. 픽셀·샘플·패킷은 addr가 필요 없다는데 어떤 식으로 쓰이는 거야? (픽셀로 쉽게)

좋은 질문이에요. "주소가 없는데 받는 쪽이 어떻게 어느 픽셀인지 알아?" — 여기가 핵심이에요. 픽셀로 갑니다.

### 핵심 한 방: 주소를 안 보낸다, **순서가 곧 주소**다

스트림의 트릭은 이거예요:

```text
"이 픽셀은 (x=2, y=1) 위치야" 라고 주소를 붙여 보내는 게 아니라,
픽셀을 정해진 순서(왼→오, 위→아래)로 그냥 흘려보낸다.
받는 쪽은 "몇 번째로 들어왔나"를 세서 위치를 스스로 복원한다.
```

순서가 약속돼 있으니(라스터 스캔), **위치는 보낼 필요가 없다 — 세면 되니까.**

### 비교: 메모리맵(AXI) vs 스트림(AXIS)

3×2 짜리 작은 이미지로 봅시다:

```text
이미지 (가로 3 × 세로 2):
   row0:  P00  P01  P02
   row1:  P10  P11  P12
```

**AXI(주소 방식)라면** — 픽셀마다 "어디에 쓸지" 주소를 계산해 붙여야 해요:

```text
P00 → 주소 0x1000 에 써라
P01 → 주소 0x1004 에 써라      주소 = base + (y×가로 + x)×픽셀크기
P02 → 주소 0x1008 에 써라      매 픽셀이 자기 목적지를 들고 다님
...                            (배선·대역폭의 절반이 '주소' 나르는 데 낭비)
```

**AXI-Stream(스트림 방식)이라면** — 그냥 순서대로 토해냅니다. 주소 없음:

```text
        ┌───── 라스터 스캔 순서로 그냥 흘림 ─────┐
전송:    P00  P01  P02  P10  P11  P12
SOF :     1    0    0    0    0    0     ← TUSER: "프레임 시작" (첫 픽셀)
EOL :     0    0    1    0    0    1     ← TLAST: "이 줄 끝"
TVALID:   1    1    1    1    1    1
```

여기서 **주소는 단 하나도 안 실렸어요.** 대신 두 개의 표식만:
- `TUSER`의 SOF(Start of Frame) = "여기서 새 프레임 시작" (첫 픽셀에 1)
- `TLAST`의 EOL(End of Line) = "이 줄(row) 끝" (각 줄 마지막 픽셀에 1)

### 받는 쪽은 위치를 어떻게 복원하나

받는 블록은 "가로 = 3"이라는 것만 알면, 들어오는 픽셀을 세면서 위치를 스스로 찍어요:

```text
들어온 픽셀  표식       받는 쪽이 찍는 위치
─────────────────────────────────────────
P00        SOF=1   →  "프레임 시작! 여기는 (x=0, y=0)"
P01                →  (x=1, y=0)
P02        EOL=1   →  (x=2, y=0) ... "줄 끝! x를 0으로, y를 +1"
P10                →  (x=0, y=1)
P11                →  (x=1, y=1)
P12        EOL=1   →  (x=2, y=1) ... "줄 끝"
```

→ **(x, y) 좌표는 한 번도 전송되지 않았어요.** 받는 쪽이 "몇 번째냐 + 줄 끝 신호"로 계산해낸 겁니다. 이게 "주소가 필요 없다"의 진짜 의미예요.

### 왜 이게 더 나은가 (픽셀 파이프라인 관점)

비디오는 보통 블록을 **줄줄이 연결**해서 처리해요:

```text
카메라 ──► [밝기 보정] ──► [색 변환] ──► [크기 조절] ──► HDMI
        픽셀이 흘러가는 대로 각 블록이 처리만 하고 다음으로 넘김
```

이 블록들은 **메모리에 랜덤하게 접근하지 않아요.** "지금 지나가는 픽셀"만 처리하면 됩니다. 그러니:

- 주소가 필요 없다 (어차피 순서대로 흐르니까).
- 주소를 안 보내니 배선·대역폭 절약.
- 순서는 프로토콜이 보장(in-order)하니, **순서 = 위치가 공짜로 성립.**

### 컨베이어 벨트 비유

```text
AXI(주소)      = 택배. 픽셀마다 "○○동 ○○호" 주소를 적어 부친다.
                 (정확한 위치에 꽂을 수 있지만, 모든 상자에 주소 라벨 필요)

AXI-Stream     = 공장 컨베이어 벨트. 부품이 정해진 순서로 지나간다.
                 5번째로 지나간 부품이 5번 부품인 걸 다들 안다 — 라벨이 필요 없다.
                 "줄 바뀜(EOL)", "새 배치 시작(SOF)" 표시만 벨트에 붙여둠.
```

벨트 위 부품에 일일이 "너는 3번 자리"라고 안 쓰죠. 순서가 자리를 말해주니까. 스트림이 딱 그거예요.

### 그럼 결국 메모리(프레임버퍼)에 저장할 땐?

언젠가 이 픽셀들을 DRAM에 모아둬야 할 때가 오죠(화면 버퍼). 그때 **주소가 다시 등장**하는데, 파이프라인 내내가 아니라 **메모리 경계에서 딱 한 번** 만들어집니다:

```text
[픽셀 스트림] ──AXIS(주소 없음)──► [DMA 엔진] ──AXI(주소 있음)──► DRAM 프레임버퍼
                                    └ 카운터로 주소 생성:
                                      addr = base + (세어둔 픽셀 번호)×픽셀크기
```

DMA가 "몇 번째 픽셀인지" 세서 `addr = base + count×크기`로 주소를 *만들어냅니다.* 즉 **순서(스트림) → 주소(메모리)** 변환을 경계에서 한 번 해주는 거예요. 파이프라인 블록들은 끝까지 주소를 몰라도 됩니다.

> **한 줄:** 스트림은 픽셀에 "위치(주소)"를 붙여 보내지 않는다. **정해진 순서(라스터 스캔)로 흘리고, 받는 쪽이 개수를 세서 (x,y)를 복원**한다 — 순서가 곧 주소다. `TUSER`=프레임 시작(SOF), `TLAST`=줄 끝(EOL) 두 표식만으로 2D 영상을 1D 흐름으로 보냈다 받는 게 가능해진다. 주소는 메모리에 실제로 쌓을 때 DMA가 카운터로 한 번 만들어줄 뿐.

오디오 샘플도 똑같아요(시간 순서대로 샘플 흘림, 주소 없음), 네트워크 패킷도 똑같고요(byte 순서가 곧 위치, `TLAST`가 패킷 끝). 픽셀이 제일 직관적이라 이걸로 잡으면 나머지는 자동입니다.

## Q2. 2-3에서 AXI는 왜 transaction 단위 확인이 필요해? 그것도 BRESP만 해당 아니야? read는 transfer마다 resp 올라오잖아

정확히 짚었어요. §2-3에서 제가 "트랜잭션 단위 확인"이라고 뭉뚱그린 게 **write 중심이라 부정확**했어요. Unit 2 Q2에서 이미 판 그대로, read는 beat마다죠. 바로잡습니다.

### 먼저 정정 — AXI 응답의 단위는 read/write가 다르다

```text
write: BRESP — 버스트당 딱 1번 (트랜잭션 단위, B 채널)
read : RRESP — beat마다     (transfer 단위, R 채널에 데이터와 같이 실려옴)
```

당신 말이 맞아요. "transaction 단위 확인"은 **BRESP(write)에만** 정확하고, read는 **beat마다 RRESP**가 올라옵니다. (Unit 2 Q2의 "방향" 논리 그대로 — read 데이터는 S→M으로 word별로 돌아오니 검증 도장이 word마다, write는 반대 방향이라 끝나고 요약 한 번.)

### 진짜 질문 — 그럼 AXI는 왜 "응답"이 필요한가?

여기서 두 가지를 분리해야 해요. 버스가 처리하는 일은 사실 **두 종류**거든요:

```text
① flow control  : "너 받을 수 있어?"            → VALID/READY 가 처리
② 접근의 결과    : "그 주소 접근이 됐어? 유효해?"  → 응답(BRESP / RRESP)이 처리
```

AXI에 ②(응답)가 있는 이유는 **주소 있는 접근은 실패하거나 무효일 수 있어서**예요:

```text
DECERR : 그 주소에 slave가 아예 없음
SLVERR : 권한 위반 등 slave 내부 실패
→ master는 "내가 쓴 게 진짜 메모리에 박혔나 / 읽은 word가 진짜 값인가 에러인가"를
  알아야 정합성을 지킨다. (실패했는데 성공한 줄 알고 진행하면 버그)
```

즉 AXI의 응답은 "데이터 받았다는 확인"이 아니라 **"주소 접근의 결과(성공/실패/유효)"** 예요. write는 그 결과가 버스트당 하나면 충분(BRESP), read는 word마다 유효성을 붙여야 함(RRESP).

### AXI-Stream은 왜 ① ② 둘 다 응답이 없나

```text
① flow control  : TREADY 가 이미 다 함 (backpressure). → 별도 응답 불필요
② 접근의 결과    : 주소가 없다 → "주소 접근"이라는 게 아예 없다
                  → 실패할 접근도, 무효일 location도 없음
                  → 보고할 "결과"가 존재하지 않음 → 응답 채널 자체가 불필요
```

핵심은 이거예요 — **AXI-Stream엔 "성공/실패할 주소 접근"이 없다.** source는 데이터가 있으면 `TVALID`로 내밀고, sink는 받을 수 있으면 `TREADY`로 받는다. 그게 전부. DECERR("그런 주소 없음")도 SLVERR("권한 없음")도 *개념적으로 성립이 안 됨* — 주소가 없으니까.

그럼 스트림에서 진짜 에러(CRC 깨짐, 잘린 패킷)는? → **프로토콜 응답이 아니라 `TUSER` 사이드밴드**에 앱이 정의해서 실어 보냅니다. "이 패킷 CRC 틀림" 같은 플래그를 TUSER 비트로. 프로토콜 차원의 응답 채널이 아니에요.

### 정리 표

| | AXI write | AXI read | AXI-Stream |
|---|---|---|---|
| flow control | AW/W READY | AR/R READY | `TREADY` |
| 접근 결과 응답 | `BRESP` (버스트당 1) | `RRESP` (**beat마다**) | **없음** |
| 왜 응답? | 쓰기가 실패/무효일 수 있음 | 읽은 word가 에러일 수 있음 | 주소 접근이 없음 → 결과랄 게 없음 |
| 에러 통보 | BRESP=SLVERR/DECERR | RRESP=SLVERR/DECERR | `TUSER`(앱 정의) |

> **한 줄(정정 포함):** "트랜잭션 단위 확인"은 **write의 BRESP에만** 맞다 — read는 **beat마다 RRESP**다. AXI가 응답을 두는 진짜 이유는 "데이터 받음 확인"이 아니라 **"주소 접근의 결과(성공/실패/유효)를 master에게 알리기"** 위해서고, 그래서 주소 접근이 실패·무효일 수 있는 한 응답이 필요하다. AXI-Stream은 **주소 접근 자체가 없어** 보고할 결과가 없으니 응답 채널이 통째로 빠졌고, flow control은 `TREADY`가, 앱 레벨 에러는 `TUSER`가 대신한다.

## Q3. data interleave는 하나의 packet 단위로? 예를 들어 TID=0, TID=1, TID=0, TID=1 이런 식?

좋은 질문이고, 사실 여기에 미묘한 함정이 있어요. **두 가지 스케일**을 구분해야 합니다 — "packet 단위 전환"과 "beat 단위 interleave". 그리고 둘을 가르는 건 **TID**예요.

### 규칙은 TID로 갈린다

```text
같은 TID  : 한 packet은 TLAST까지 연속이어야 함 → 전환은 packet 경계에서만 (interleave 금지)
다른 TID  : beat 단위로 섞어도 됨 → sink가 TID로 분리·재조립 (interleave 허용)
```

그래서 당신 예시 **`TID=0, 1, 0, 1`** 은 — *서로 다른 TID끼리 beat 단위로 번갈아* 보내는 거라 **허용되는 케이스**예요. 즉 "interleave가 꼭 packet 단위로만 일어난다"는 아니에요. **다른 TID끼리는 beat 단위로 섞을 수 있습니다.**

### 케이스별 파형

**✅ 허용 — 다른 TID끼리 beat interleave (당신 예시)**

```text
        T1   T2   T3   T4   T5
TID      0    1    0    1    0
TDATA   A0   B0   A1   B1   A2
TLAST    0    0    0    1    1
         │    │              └ A packet 끝
         │    └ B packet (B0,B1) — T4에서 TLAST
         └ A packet (A0,A1,A2)

sink: TID로 분리 → A0·A1·A2 재조립,  B0·B1 재조립
      (TID가 다르니 누가 누구 건지 명확)
```

A의 beat와 B의 beat가 한 알씩 번갈아도, **TID가 다르니** sink가 두 packet을 따로 모아 재조립할 수 있어요. 합법.

**❌ 불법 — 같은 TID인데 두 packet을 섞기**

```text
TID      0    0    0    0
TDATA   A0   C0   A1   C1    ← A packet과 C packet 둘 다 TID=0인데 섞임
TLAST    0    0    ?    ?

문제: sink는 "TID=0 스트림은 TLAST 나올 때까지 한 packet"이라고 봄
      → A 중간에 들어온 C0를 A의 일부로 오인 → packet 오염
```

같은 TID 안에서는 **한 packet이 TLAST까지 끊기면 안 돼요.** 그래서 같은 TID끼리는 전환이 **packet 경계(TLAST)에서만** 일어나죠 — 이게 §8-3에서 말한 "한 packet은 TLAST까지 연속".

**🏭 실무 — 대부분은 그냥 packet 단위로 스위칭**

```text
TID      0    0    0    1    1
TDATA   A0   A1   A2   B0   B1
TLAST    0    0    1    0    1
         └─── A 통째로 ───┘  └─ B 통째로 ─┘
```

beat interleave(다른 TID)가 *허용*되긴 하지만, 그러려면 **sink가 TID별로 재조립 버퍼**를 들고 있어야 해요(A 모으는 버퍼, B 모으는 버퍼…). 비싸죠. 그래서 현실의 stream 인터커넥트 대부분은 **packet 단위로 arbitration** — 한 packet을 TLAST까지 통째로 보낸 뒤 다음 스트림으로 전환합니다. beat interleave는 가능하지만 드물어요.

### 정리

| 상황 | beat 단위 interleave? | 왜 |
|---|---|---|
| 같은 TID, 두 packet | ❌ 금지 | sink가 packet 경계 못 가림 (오염) |
| 다른 TID, 두 packet | ✅ 허용 | TID로 분리·재조립 가능 |
| 실무 인터커넥트 | 주로 packet 단위 전환 | beat interleave는 재조립 버퍼 비용 큼 |

> **한 줄:** interleave가 "항상 packet 단위"는 아니다. **같은 TID 안에서는 packet이 TLAST까지 연속**이라 전환이 packet 경계에서만 일어나지만, **다른 TID끼리는 beat 단위로 섞어도 된다**(당신 예시 `0,1,0,1`이 그 케이스 — sink가 TID로 분리). 다만 그러려면 sink에 TID별 재조립 버퍼가 필요해서, 실제 인터커넥트는 비용 때문에 보통 packet 단위로 스위칭한다.

⚠️ 참고: §8-3에서도 깔았듯, beat-interleave 허용 범위는 AXI4-Stream 스펙 판본·인터커넥트 구현에 따라 뉘앙스가 있어요. 안전한 기본 원칙은 여전히 **"같은 TID packet은 연속, 섞을 거면 TID를 다르게"** 입니다.

## Q4. in-order는 master가 보낸 순서대로 slave가 받는 거고, out-of-order는 interconnect가 마음대로 바꾸는 거지?

핵심을 거의 맞게 잡았는데, **AXI-Stream에는 out-of-order가 아예 없다**는 게 함정이에요. 거길 정확히 가르죠.

### in-order 부분 — 맞아요 (단, "한 스트림 안에서")

```text
같은 스트림(같은 TID/TDEST) 안:
  master 보낸 순서  =  slave 받는 순서   ← 항상. 인터커넥트가 못 바꿈.

master 보냄:  P0  P1  P2  P3   (TID=0, TDEST=1)
slave 받음:   P0  P1  P2  P3   ← 무조건 이 순서
```

맞습니다. 한 스트림 안에서는 보낸 순서 그대로 받아요. **인터커넥트가 이걸 재정렬하는 건 금지**예요.

### out-of-order 부분 — 여기가 틀렸어요

AXI-Stream에는 **out-of-order라는 게 없어요.** 인터커넥트가 한 스트림을 마음대로 재정렬하는 일은 **절대 일어나지 않습니다.**

그럼 §8-1에서 말한 "다른 TID/TDEST끼리는 순서 보장 없음"은 뭐냐? 그건 **재정렬이 아니라 "독립"** 이에요. 차이가 중요합니다:

```text
재정렬(reorder): 하나의 스트림 P0 P1 P2 를 → P2 P0 P1 로 뒤섞음  ← AXI-Stream엔 없음 ❌

독립(independent): 서로 다른 스트림 A와 B는 애초에 별개라
                   "A와 B 중 뭐가 먼저냐"는 정의 자체가 안 됨    ← 이게 진짜 의미
```

```text
A0 A1 (TID=0 → dst1),   B0 B1 (TID=1 → dst2)

dst1: A0 A1  (A 순서 유지)
dst2: B0 B1  (B 순서 유지)
A와 B의 상대 순서? → 서로 다른 곳으로 가는 별개 스트림이라 비교가 무의미
                    (인터커넥트가 B를 먼저 처리하든 A를 먼저 처리하든,
                     각 스트림 내부 순서는 그대로 — 한 스트림을 "뒤집은" 게 아님)
```

→ "인터커넥트가 마음대로 순서를 바꾼다"가 아니라, **별개의 두 스트림은 원래 순서 관계가 없다**가 정확한 표현이에요.

### "out-of-order = 인터커넥트가 재정렬"은 사실 AXI(memory-mapped) 얘기

당신이 말한 그 out-of-order 개념은 **Unit 2의 AXI**에 있던 거예요. 거기선 진짜로 재정렬이 일어나죠:

```text
AXI read:  ARID=5(느린 DRAM) 먼저 요청,  ARID=6(빠른 SRAM) 나중 요청
응답:      RID=6 데이터가 먼저 옴  →  RID=5 나중      ← 진짜 재정렬 (out-of-order)

단, 같은 ID로 두 개 보내면 → 무조건 보낸 순서대로 (재정렬 불가, in-order)
```

즉 AXI의 out-of-order는 "마음대로"가 아니라 **ID 규칙 안에서**예요 — 같은 ID는 못 바꾸고, 다른 ID만 추월 허용. AXI-Stream은 AXI에서 **in-order만 물려받고 out-of-order는 안 가져왔어요.**

### 표로 정리

| | 같은 스트림/같은 ID | 다른 스트림/다른 ID |
|---|---|---|
| **AXI-Stream** | 항상 in-order (재정렬 ❌) | 별개 스트림 — **순서 관계 없음(독립)**. 재정렬이 아님 |
| **AXI (참고)** | in-order (같은 AxID) | **out-of-order 허용** (다른 AxID, 진짜 재정렬) |

> **한 줄(정정):** in-order = "**한 스트림(같은 TID/TDEST) 안**에서 master 보낸 순서 = slave 받는 순서", 맞다 — 인터커넥트가 이걸 못 바꾼다. 하지만 AXI-Stream엔 **out-of-order가 없다.** "다른 TID/TDEST끼리 순서 보장 없음"은 인터커넥트가 재정렬하는 게 아니라 **두 스트림이 애초에 독립**이라 상대 순서가 정의 안 되는 것. 당신이 말한 "인터커넥트가 마음대로 재정렬"은 **AXI(memory-mapped)의 out-of-order** 얘기이고, 그것조차 ID 규칙(같은 ID는 in-order) 안에서만 허용된다.

## Q5. (Q4 후속) 개념적으로 물어본 거야.

아, 개념 자체를 물은 거군요. 그럼 **정확히 맞아요.**

```text
in-order      : 받는 순서 = 보낸 순서      (순서 보존)
out-of-order  : 받는 순서 ≠ 보낸 순서 가능  (순서가 바뀔 수 있음)
```

- **in-order** = master가 0→1→2→3 보내면 slave도 0→1→2→3으로 받음. ✓
- **out-of-order** = 그 순서가 뒤바뀌어 도착할 수 있음 (예: 2가 0보다 먼저). ✓

개념으로는 그게 다예요. 딱 하나만 덧붙이면 — out-of-order의 "바꾼다"는 보통 **"아무렇게나"가 아니라 "바꿔도 된다(허용)"** 에 가까워요:

- **이유가 있어서** 바꿈 (빠른 응답 먼저 받아 latency 숨기기 등)
- 대개 **규칙 안에서** 바꿈 (예: "같은 그룹은 순서 유지, 다른 그룹만 추월 허용")

근데 이건 디테일이고, **"in-order = 순서 그대로, out-of-order = 순서 바뀔 수 있음"** 이라는 개념은 정확합니다. 👍

## Q6. TKEEP과 TSTRB 차이가 뭐야? 헷갈려

헷갈리는 게 당연해요 — 둘 다 "이 byte 유효해?"처럼 들리거든요. 근데 **서로 다른 질문**을 해요.

### 두 신호는 다른 질문을 한다

```text
TKEEP : "이 byte를 버려도 돼?"        → 1 = 유지(버리면 안 됨)   0 = 버려도 됨
TSTRB : "이 byte에 값이 있어?"        → 1 = 데이터(값 있음)      0 = 위치만(값 없음)
```

- `TKEEP`은 **존재** 여부 (스트림에 남길 byte냐, 그냥 버릴 쓰레기냐)
- `TSTRB`는 그 남긴 byte가 **값이 있냐, 자리만 차지하냐**

층이 달라요. `TKEEP`이 바깥 관문(남길래 버릴래), `TSTRB`가 그 안의 구분(값이냐 빈자리냐).

### 그래서 byte는 3종류

| `TKEEP` | `TSTRB` | byte 종류 | 한마디로 |
|:---:|:---:|---|---|
| 1 | 1 | **Data** | 진짜 값. 보존 O |
| 1 | 0 | **Position** | 값은 없지만 **자리는 보존해야 함** (구멍) |
| 0 | 0 | **Null** | 그냥 쓰레기. **버려도 됨** |
| 0 | 1 | ❌ | 불법 — "버려도 되는데 값이 있다" = 모순 |

### 핵심은 Null vs Position 차이 (이게 TSTRB가 하는 일)

`TKEEP`만으로는 "남길 byte / 버릴 byte" 2가지밖에 표현 못 해요. 근데 스트림엔 **3번째**가 필요해요 — "값은 없지만 버리면 안 되는 빈자리". 그래서 `TSTRB`가 추가됩니다.

```text
Null byte    (TKEEP=0)        : 인터커넥트가 빼버려도 됨. 빼도 의미 안 변함.
Position byte (TKEEP=1,TSTRB=0): 빼면 안 됨! 빼면 뒤가 당겨져서 정렬이 깨짐.
```

이 둘은 "값이 없다"는 점은 같지만, **하나는 지워도 되고(null) 하나는 지우면 안 돼요(position).** 그 차이를 못 박는 게 `TSTRB`예요.

### 언제 쓰이나 (구체)

```text
① 거의 대부분: 전부 data byte → TKEEP=1, TSTRB=1 다 켜짐 → 신경 안 써도 됨

② 패킷 끝 자투리 (Null):
   10 byte 패킷을 4 byte 버스로 → 마지막 transfer에 2 byte만 진짜, 2 lane은 남음
        lane:  3 2 1 0
        TKEEP: 0 0 1 1   ← lane3,2는 그냥 빈 lane, 버려도 됨 (null)
        TSTRB: 0 0 1 1

③ 듬성듬성 데이터 (Position):
   값 사이에 "여긴 구멍"을 보존해야 할 때
        TKEEP: 1 1 1 1   ← 다 유지
        TSTRB: 1 0 1 1   ← lane2는 값 없는 구멍인데, 자리는 지켜야 함 (position)
```

②의 lane3,2는 "버스가 데이터보다 넓어서 남은 빈칸" → 버려도 됨 → **null**.
③의 lane2는 "데이터 한가운데 의도된 구멍" → 빼면 정렬 깨짐 → **position**.

### 책장 비유

```text
TKEEP=1, TSTRB=1 : 책이 꽂혀 있음            (데이터)
TKEEP=1, TSTRB=0 : 일부러 비워둔 칸 (예약석)  (position — 채우면 안 되고 비운 채 유지)
TKEEP=0          : 책장 끝에 남는 여분 공간    (null — 잘라내도 그만)
```

> **한 줄:** `TKEEP` = "이 byte 버려도 돼?"(존재/유지), `TSTRB` = "값이 있어?"(데이터/빈자리). 합치면 **Data(11) / Position(10, 값없는 보존 구멍) / Null(00, 버릴 빈칸)** 3종. byte 하나로는 못 하는 "지워도 되는 빈칸(null) vs 지우면 안 되는 구멍(position)" 구분을 위해 신호가 둘인 것. 대부분 설계는 둘 다 전부 1이라 안 봐도 되고, **자투리(null)·구멍(position)** 에서만 갈린다.
