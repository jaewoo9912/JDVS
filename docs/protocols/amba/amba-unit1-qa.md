## Q1. backbone이 뭐야?

**Backbone(백본)** = 칩 안에서 주요 블록들을 잇는 **중심 간선 버스**, 즉 데이터가 가장 많이 흐르는 "대동맥"을 말한다. 네트워크에서 백본망(주요 도시들을 잇는 굵은 간선)이라고 부르는 것과 같은 비유.

```text
        ┌─────────── backbone (간선, 고속) ───────────┐
 CPU ──┤   메모리   DMA   GPU/가속기                   │  ← 대역폭 큰 트래픽이 여기로
        └────────────────┬─────────────────────────────┘
                         │ [Bridge]
                         ▼
        ┌───────── 가지(branch, 저속) ─────────────────┐
        │   UART   GPIO   Timer   I2C                   │  ← 가끔, 조금씩 흐르는 트래픽
        └──────────────────────────────────────────────┘
```

- **backbone(간선):** CPU↔메모리, DMA처럼 **대역폭이 큰 핵심 트래픽**이 지나는 굵은 버스. 그래서 빠른 프로토콜(AHB, 요즘은 AXI)을 쓴다.
- **거기서 갈라져 나온 가지:** UART·GPIO 같은 저속 주변장치는 backbone에 직접 안 붙이고, Bridge를 거쳐 느린 APB로 내린다.

**왜 이렇게 부르나** — 도시 도로망을 떠올리면 된다:

- **고속도로(backbone)** = 차가 많이 다니는 큰길 → 넓고 빠르게.
- **동네 골목(APB 가지)** = 차가 가끔 다님 → 좁고 단순해도 충분.

모든 길을 고속도로로 깔면 낭비고, 모든 길을 골목으로 깔면 막힌다. 그래서 **굵은 간선(backbone) + 가는 가지**로 계층화한다.

> 한 줄: **backbone = 칩 안 버스 계층에서 가장 트래픽이 많은 중심 간선 버스.** (요즘 SoC에선 AXI 인터커넥트가 그 역할을 맡는다.)

## Q2. CSR 블록과 GPIO가 뭐야?

둘 다 **APB에 붙는 대표적인 저속 주변장치**다.

### CSR 블록 (Control/Status Register)

> **소프트웨어가 하드웨어를 제어/조회하는 "레지스터 묶음".**

- **Control 레지스터:** SW가 HW에게 명령 ("이 IP 켜라", "이 모드로 동작해").
- **Status 레지스터:** HW가 SW에게 상태 보고 ("나 지금 busy", "에러 났음", "done").

거의 모든 IP가 이런 레지스터 한 뭉치를 갖고, CPU가 그 주소에 read/write 해서 IP를 조종한다. 예:

```text
0x00  CTRL   [bit0=enable, bit1=start, ...]   ← SW가 write
0x04  STATUS [bit0=busy,   bit1=done,  ...]   ← SW가 read
0x08  CONFIG [동작 파라미터]
```

CPU: `CTRL` 주소에 `0x1` write → IP 켜짐 → `STATUS` 주소 read 해서 `done` 뜰 때까지 폴링. 이런 단순 레지스터 접근이라 **고속 버스가 필요 없어서 APB**에 붙인다.

### GPIO (General-Purpose Input/Output)

> **칩의 "범용 핀"을 SW로 직접 읽고 쓰는 블록.**

칩 바깥으로 나가는 핀 하나하나를 소프트웨어가 0/1로 제어하거나 읽는다.

- **Output:** 핀을 HIGH/LOW로 → LED 켜기, 다른 칩에 신호 주기.
- **Input:** 핀 전압 읽기 → 버튼 눌렸나 감지.

이것도 결국 레지스터 접근이다:

```text
0x00  DIR   [핀별 방향: 0=입력, 1=출력]
0x04  OUT   [출력 핀 값]       ← write 하면 핀이 그 값으로
0x08  IN    [입력 핀 값]       ← read 하면 핀 현재 상태
```

1초에 몇 번 깜빡이는 정도라 대역폭이 거의 필요 없어서 역시 **APB**에 붙는다.

> **한 줄 정리:** CSR = "IP를 조종하는 제어/상태 레지스터 묶음", GPIO = "칩 핀을 SW로 직접 읽고 쓰는 블록". 둘 다 단순·저속이라 **APB의 대표 고객**.

## Q3. APB 신호로 한 번의 핸드셰이킹을 예로 설명해줘

APB의 "핸드셰이크"는 **마스터가 `PSEL`/`PENABLE`로 "이거 처리해줘"라고 내밀고, slave가 `PREADY`로 "받았어"라고 답하는** 한 쌍의 대화다. 구체적인 write 한 번으로 따라가 보자.

**상황 설정** — CPU가 UART의 설정 레지스터(`0x40`)에 `0xAB`를 **쓰는** 예. slave(UART)가 좀 느려서 1클럭 늦게 응답한다고 하자.

**핵심 신호 3개 (핸드셰이크의 주인공)**

| 신호 | 누가 | 의미 |
|---|---|---|
| `PSEL` | 마스터→slave | "**너** 지목한다" (이 slave 선택) |
| `PENABLE` | 마스터→slave | "이제 **진짜 전송**이다" (둘째 박자) |
| `PREADY` | slave→마스터 | "**받았어/준비됐어**" (응답) |

나머지(`PADDR`, `PWRITE`, `PWDATA`)는 "무엇을" 전달할지 실어주는 데이터선.

**사이클 단위 추적**

```text
        T0        T1          T2          T3        T4
        IDLE      SETUP       ACCESS      ACCESS    IDLE
                              (wait)      (완료)

PCLK    ‾|_       ‾|_         ‾|_         ‾|_       ‾|_

PSEL     0    ____/‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾\____
PENABLE  0    0        ____/‾‾‾‾‾‾‾‾‾‾‾‾‾‾\____
PWRITE   -    <───────── 1 (write) ──────────>
PADDR    -    <───────── 0x40 ───────────────>
PWDATA   -    <───────── 0xAB ───────────────>
PREADY   -    -          0           1        -
                                     ↑여기! 핸드셰이크 성립
```

**박자별 대화로 풀면**

**T1 — SETUP phase ("너한테 이거 줄게")**
- 마스터: `PSEL=1` 올림 → "UART 너 지목."
- 동시에 `PADDR=0x40`, `PWRITE=1`, `PWDATA=0xAB` 깔아둠 → "주소 0x40에, 0xAB를, 쓸 거야."
- `PENABLE=0` → "아직 셋업 중. 한 박자 줄게."
- **이 phase는 항상 정확히 1클럭.**

**T2 — ACCESS phase 시작 ("자, 지금 처리해")**
- 마스터: `PENABLE=1` 올림 → "셋업 끝. **지금 전송한다.** 받아."
- slave(UART): 아직 준비가 덜 됨 → `PREADY=0` → "**잠깐만**, 아직."
- → 이게 **wait state**. 마스터는 주소·데이터를 **그대로 유지**한 채 기다림.

**T3 — 핸드셰이크 성립 ("받았어!")**
- slave: `PREADY=1` → "**OK, 받았다.**"
- **`PSEL=1 & PENABLE=1 & PREADY=1`이 동시에 참인 이 클럭의 상승 에지에서 write가 실제로 일어남** → UART 레지스터에 0xAB 기록 완료.
- 이 세 신호가 동시에 1이 되는 순간이 바로 **"악수가 맞은(handshake)"** 시점.

**T4 — 종료**
- 마스터: `PSEL=0`, `PENABLE=0` 내림 → 버스 IDLE로. (다음 전송 있으면 IDLE 대신 바로 SETUP)

> **한 줄 요약:** 마스터가 **`PSEL`(지목) → `PENABLE`(전송 개시)** 로 두 박자에 걸쳐 요청을 내밀고, slave가 **`PREADY`(완료)** 로 답한다. **세 신호가 동시에 1이 되는 클럭**에서 데이터가 오가고 — 그게 APB의 한 번의 핸드셰이크.
>
> 만약 slave가 빨라서 T2에 바로 `PREADY=1`이면 wait 없이 **딱 2클럭**(SETUP+ACCESS)에 끝난다. 느릴 때만 `PREADY=0`으로 ACCESS가 늘어난다.

## Q4. 글리치가 뭐야?

**글리치(glitch)** = 신호가 안정되기 전에 잠깐 **삐끗 튀는, 의도치 않은 짧은 펄스**다. 회로에서 여러 입력이 동시에 안 바뀌고 미세한 시간차로 바뀔 때 출력이 순간적으로 잘못된 값을 냈다가 제자리를 찾는 현상.

**왜 생기나** — 신호마다 게이트를 지나는 시간이 조금씩 달라서, 바뀌는 "찰나"에 출력이 잠깐 엉뚱한 값이 된다.

```text
주소가  0x3F → 0x40 으로 바뀌는 순간 (비트가 동시에 안 바뀜):

       0011_1111 (0x3F)
   →   0100_0000 (0x40)

비트들이 미세한 시간차로 뒤집히면 중간에 잠깐
       0111_1111 (0x7F) 같은 "있지도 않은 주소"가 스쳐 지나감  ← 글리치!
```

**왜 문제가 되나** — 이 순간의 잘못된 주소를 디코더가 덜컥 받아들이면, **엉뚱한 slave가 잠깐 선택**되는 사고가 날 수 있다.

**APB에서 어떻게 피하나** — 그래서 APB가 **2박자(SETUP→ACCESS)** 로 동작한다:

```text
SETUP  (1클럭): 주소를 깔아두고 PENABLE=0  ← 이 동안 글리치가 가라앉음(안정화)
ACCESS:        한 박자 늦게 PENABLE=1      ← 안정된 뒤에야 "전송!"
```

주소를 깐 직후 바로 전송하지 않고 **한 박자 기다렸다가** `PENABLE`을 올리니, 주소가 튀는 찰나는 이미 지나가 있다.

> **한 줄:** 글리치 = 신호가 안정되기 직전 잠깐 튀는 가짜 펄스.
>
> ※ 단, 이 "SETUP이 글리치를 없앤다"는 설명은 교과서적 단순화다. 더 정확한 그림은 Q5·Q8에서 보정한다.

## Q5. AXI에선 글리치가 왜 발생하지 않아?

여기서 한 가지를 바로잡아야 한다. **AXI라고 글리치가 "안 생기는" 게 아니다.** 글리치는 조합 논리(combinational logic)가 있는 한 어느 버스에서든 배선 위에 생긴다. 핵심은 **"생기느냐"가 아니라 "그게 문제가 되느냐"** 다.

### 진짜 원리 — 동기 회로는 클럭 에지에서만 본다

디지털 칩은 **동기식(synchronous)** 이다. 플립플롭이 신호를 **클럭 상승 에지 그 순간에만 샘플링**한다. 에지와 에지 사이에 신호가 아무리 삐끗 튀어도(글리치), **그 순간엔 아무도 안 보고 있으니** 무해하다.

```text
              글리치(여기서 튐) ↓
신호:  ___/‾‾\__/‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾  ← 에지 사이엔 튀어도 됨
클럭:  __________________/‾\______
                          ↑ 여기서만 샘플링
                        이때쯤엔 이미 안정(settled)돼 있음
```

타이밍 설계(STA, setup/hold 시간 보장)가 하는 일이 바로 이거다: **다음 클럭 에지가 오기 전까지 모든 신호가 안정되도록** 보장. 그래서 글리치는 "에지 전에 가라앉기만 하면" 그냥 사라지는 셈.

### 그럼 APB의 SETUP 박자는 뭐였나 (Q4 보정)

Q4에서 "글리치 없는 디코딩"이라고 한 건 **교과서적 단순화**였다. 더 정확히는:

- APB의 2박자(SETUP→ACCESS)는 `PENABLE`을 **깨끗한 1클럭짜리 strobe**로 만들어, "정확히 이 클럭이 전송"이라고 명확히 못 박는 단순한 설계 장치다.
- 즉 글리치를 "물리적으로 없애는" 게 아니라, **단순한 FSM으로 타이밍을 명확하게** 하려는 목적이 크다.

### AXI는 어떻게 처리하나 — VALID/READY 핸드셰이크

AXI도 똑같이 동기식이라 같은 원리를 쓴다. 다만 SETUP 박자 대신 **VALID/READY 핸드셰이크**로 "언제가 유효한 전송인가"를 정한다.

```text
전송이 "성립"하는 조건:
  클럭 상승 에지에서  VALID=1 AND READY=1  → 그 순간의 값만 유효
```

- 에지에서 `VALID`와 `READY`가 둘 다 1일 때만 그 클럭의 주소·데이터가 "진짜"로 인정된다.
- 그 사이 배선이 글리치로 튀든 말든, **에지에서 샘플링한 안정된 값만** 받아들이니 영향이 없다.
- 게다가 AXI 신호는 보통 **플립플롭에서 바로 나오는(registered) 깨끗한 신호**라, 애초에 글리치가 적기도 하다.

| | 글리치 발생? | 왜 무해한가 |
|---|---|---|
| APB | 생김 (조합 논리에) | 동기 샘플링 + 2박자 strobe(`PENABLE`)로 전송 시점 명확화 |
| AXI | 생김 (마찬가지) | 동기 샘플링 + **VALID/READY 둘 다 1인 에지**에서만 값 인정 |

> **한 줄:** AXI에서 글리치가 "안 생기는" 게 아니라, **동기 회로라 클럭 에지에서만 값을 보고, AXI는 그 에지에서 `VALID&READY`가 맞을 때만 전송으로 인정**하기 때문에 에지 사이의 글리치가 애초에 의미가 없는 것. 글리치를 피하는 건 APB의 SETUP 박자가 아니라, **모든 동기 버스가 공유하는 "에지 샘플링"** 이라는 더 근본적인 성질이다.

## Q6. APB도 VALID 쓰면 되잖아, 굳이 왜 2스텝으로 PSEL→PENABLE을 써?

핵심을 정확히 짚었다. **사실 맞는 직관이다 — ARM도 나중에 "VALID/READY로 하는 게 낫겠다" 싶어서 APB 역할을 대체하는 AXI4-Lite를 만들었다.** APB의 2-step은 상당 부분 **시대적·단순성 이유**다.

### 1. 역사적 이유 — VALID/READY 관용구가 없던 시절

- APB는 **1990년대 후반(AMBA 1/2)** 산물이고, VALID/READY 핸드셰이크를 대중화한 **AXI는 2003년**이다. APB가 더 먼저다.
- 당시 주변장치 버스의 표준 관용구는 **"chip-select 먼저 → strobe 나중"** 이었다 (옛날 8080/68000 같은 마이크로프로세서 버스: `CS` 깔고 → `RD`/`WR` strobe). `PSEL`(선택) → `PENABLE`(strobe)는 바로 그 익숙한 패턴을 그대로 가져온 것.

> 즉, 그 시절엔 "VALID를 쓰면 되잖아"라는 선택지 자체가 아직 보편화되지 않았다.

### 2. 원래 APB엔 `PREADY`조차 없었다 (중요)

이게 핵심 포인트다. **최초 APB는 핸드셰이크가 아예 없었다.** `PREADY`는 한참 뒤 **APB3(2003)에서 추가**된 것.

```text
원래 APB: 모든 전송이 "무조건 2클럭 고정"
  SETUP(1) → ACCESS(1) → 끝.  slave는 기다리게 할 방법이 없었음.
```

- slave 입장에서 구현해야 할 핸드셰이크 로직이 **0**. "`PSEL & PENABLE`이면 지금 접근 중"이라는 것만 알면 끝.
- VALID/READY를 쓰려면 slave가 **READY를 언제 올릴지 판단하는 상태 로직**이 필요하다. 타이머·GPIO 레지스터 하나에 그걸 넣는 건 과잉이었다.

→ APB의 존재 이유가 "주변장치를 **극단적으로 단순하게**"인데, 그 목표엔 고정 2클럭이 딱 맞았다.

### 3. PENABLE은 사실 VALID와 역할이 다르다

여기서 흔한 오해가 풀린다. APB를 VALID/READY에 억지로 매핑하면:

```text
PSEL    ≈ "너 선택 + 내 주소/데이터 유효"   ← 이게 VALID에 가까운 부분
PENABLE = "그리고 지금이 commit(둘째) 사이클" ← VALID가 아니라 "phase 표시 strobe"
```

즉 **APB도 이미 VALID 비슷한 신호(`PSEL`)는 갖고 있다.** 질문의 진짜 핵심은 *"왜 굳이 `PENABLE`이라는 둘째 phase를 더 뒀나"* 인데, 그 이유는:

- **셋업 시간 보장:** SETUP 사이클 동안 주소·제어·write 데이터가 **안정될 한 박자**를 주고, 그게 안정된 뒤에야 `PENABLE`로 "지금 실행"이라고 strobe를 침. → slave가 조합 논리로 단순하게 디코딩해도 안전.
- **깨끗한 1클럭 strobe:** `PENABLE`은 정확히 한 클럭 폭의 깔끔한 read/write strobe가 됨. 레지스터 write enable으로 바로 쓰기 좋음.

### 4. 그래서 현대엔? — VALID/READY로 갔다

ARM이 "레지스터 접근도 VALID/READY로 하면 더 유연하고 throughput도 낫겠다"고 판단해서 만든 게 **AXI4-Lite**다. 실제로 요즘 새 IP의 CSR 블록은 APB 대신 AXI4-Lite를 쓰는 경우가 많다. APB는 "이미 깔려 있고 충분히 단순해서" 레거시로 남아 있는 것.

| 질문 | 답 |
|---|---|
| 왜 VALID 안 쓰고 PSEL→PENABLE? | ① APB가 AXI보다 먼저 나옴 (VALID/READY 관용구 이전 시대) ② 원래 APB는 READY조차 없는 **고정 2클럭** — slave 핸드셰이크 로직 0이 목표 ③ `PENABLE`은 VALID가 아니라 **셋업 보장 + 깨끗한 strobe**용 둘째 phase |
| 당신 직관이 맞나? | **맞다.** ARM도 결국 VALID/READY 방식의 **AXI4-Lite**로 APB 역할을 대체함 |

> **한 줄:** APB의 2-step은 "VALID를 몰라서"가 아니라, **VALID/READY가 보편화되기 전 시대에, slave를 최대한 단순하게(핸드셰이크 로직 0, 고정 2클럭) 만들려던 설계**다. 더 유연하게 하고 싶어지자 ARM은 정확히 그 직관대로 VALID/READY 기반 **AXI4-Lite**로 갈아탔다.

## Q7. PSEL 이후 여러 사이클 후에 PENABLE을 보내도 되는 거지?

**아니다, 안 된다.** 이게 APB의 중요한 규칙이다. **SETUP phase는 항상 정확히 1클럭**이고, `PSEL`을 올린 **바로 다음 클럭에 반드시 `PENABLE`이 올라가야** 한다. 늘릴 수 없다.

**규칙**

```text
PSEL=1 올린 클럭         → 무조건 SETUP (1클럭만)
그 다음 클럭            → 무조건 PENABLE=1 (ACCESS 진입)
```

```text
틀린 동작 (이렇게 못 함):
        T1      T2      T3      T4
PSEL    __/‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾
PENABLE __________________/‾‾‾‾    ← PSEL 후 여러 클럭 뒤 PENABLE? ❌ 위반!
```

```text
올바른 동작:
        T1      T2      T3
PSEL    __/‾‾‾‾‾‾‾‾‾‾‾‾‾‾
PENABLE ________/‾‾‾‾‾‾‾       ← PSEL 다음 클럭에 바로 PENABLE ✅
        SETUP   ACCESS
```

**그럼 "기다리게" 하려면?** — 지연이 필요하면 **SETUP을 늘리는 게 아니라, ACCESS에서 `PREADY`로 늘린다.** 방향이 정반대다.

```text
        T1      T2          T3          T4
        SETUP   ACCESS      ACCESS      ACCESS
                (wait)      (wait)      (완료)
PSEL    __/‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾
PENABLE ________/‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾   ← PENABLE은 제때 올라감
PREADY          0           0           1     ← 여기서 wait를 늘림
                └─ slave가 PREADY=0으로 ACCESS를 늘림 ─┘
```

- **SETUP**: 항상 1클럭. **마스터**가 결정, 못 늘림.
- **ACCESS**: `PREADY=0`인 동안 계속 유지. **slave**가 결정, 얼마든지 늘림.

**왜 이렇게?** — `PENABLE`이 "`PSEL` 다음 클럭"으로 **위치가 고정**돼 있어야, slave가 "지금이 ACCESS다"를 **상태 추적 없이 단순하게** 판단할 수 있기 때문. 만약 `PENABLE`이 임의의 클럭에 올 수 있으면 slave가 SETUP을 몇 클럭째인지 세고 있어야 해서 단순함이 깨진다.

> **한 줄:** SETUP은 **항상 1클럭 고정** — `PSEL` 다음 클럭에 무조건 `PENABLE`. 지연은 SETUP을 늘려서가 아니라 **ACCESS에서 slave가 `PREADY=0`** 으로 만든다. (단, 원래 APB엔 `PREADY`도 없어서 무조건 2클럭이었고, `PREADY`는 APB3부터다.)

## Q8. SETUP에서 안정시켜도 PENABLE 시에 글리치가 생길 수 있잖아?

정확한 지적이다. 그리고 이 질문이 Q4 설명의 약점을 정확히 찔렀다. **솔직히 말하면, 맞다 — `PENABLE` 올라가는 순간에도 글리치는 생길 수 있다.** 그런데 **그래도 상관이 없다.** Q4에서 "SETUP이 글리치를 없앤다"고 한 건 교과서적 단순화였고, 사실 그게 SETUP의 진짜 목적이 아니다.

### 왜 PENABLE 순간 글리치가 생겨도 괜찮은가

이유는 두 개다.

**① 어차피 클럭 에지에서만 본다 (근본 이유)**

slave는 `PSEL`/`PENABLE`/주소/데이터를 **클럭 상승 에지 그 순간에만** 샘플링한다. 에지 직후 신호들이 잠깐 튀어도(글리치), **다음 에지가 올 때쯤엔 다 안정**돼 있다(STA가 보장하는 setup time). 글리치는 에지 사이에서 일어나고, 그땐 아무도 안 본다.

```text
            글리치(여기서 튐)
PENABLE ___/‾\__/‾‾‾‾‾‾‾‾‾‾‾‾
클럭    ________________/‾\___
                         ↑ slave는 여기서만 샘플 → 이미 안정됨
```

→ 이건 APB든 AXI든 **모든 동기 버스가 공유하는 성질**이다.

**② 게다가 PENABLE은 플립플롭에서 나온다 → 원래 글리치가 없다**

`PENABLE`, `PSEL`은 마스터의 **레지스터(플립플롭) 출력**이다. 플립플롭 출력은 에지에서 한 번 바뀌고 **한 클럭 내내 안정**돼 있다 — 조합 논리처럼 중간에 튀지 않는다. 글리치는 주로 **조합 논리로 즉석에서 만든 신호**(예: 주소를 디코딩한 `PSEL` 같은)에서 생기는데, 그것조차 다음 에지 전에 가라앉는다.

### 그럼 SETUP phase의 진짜 목적은?

Q4 설명을 정직하게 보정하면 — SETUP은 **글리치를 없애려는 게 아니다.** 진짜 이유는:

| 목적 | 설명 |
|---|---|
| **결정적 타이밍** | 모든 전송이 "SETUP 1 + ACCESS ≥1"로 모양이 고정 → slave가 상태 추적 없이 단순 |
| **주소 디코드와 전송 strobe 분리** | `PSEL`(주소 디코드 결과)과 `PENABLE`(실제 실행 strobe)을 한 박자 떼어, 디코드가 안정될 시간 확보 |
| **깨끗한 1클럭 strobe** | `PENABLE`이 정확히 한 클럭 폭의 write/read enable이 됨 |

여기서 "디코드가 안정될 시간"이 글리치 얘기처럼 들리지만, 더 정확히는 **타이밍 마진(setup time 여유)** 확보지 "글리치 제거"가 아니다. 글리치 자체는 에지 샘플링이 알아서 무시한다.

> **당신 말이 맞다.** `PENABLE` 순간에도 글리치는 생길 수 있다. 하지만:
> 1. slave는 **클럭 에지에서만** 보고, 그땐 다 안정돼 있어서 무관.
> 2. `PENABLE`은 **플립플롭 출력**이라 애초에 글리치가 없음.
>
> SETUP의 진짜 역할은 글리치 제거가 아니라 **"결정적 타이밍 + 깨끗한 strobe + 단순한 slave"** 다. 글리치가 무해한 건 SETUP 덕이 아니라 **동기 회로의 에지 샘플링** 덕이다 (그래서 AXI도 똑같이 안전).

## Q9. "에지에서 신호가 안정돼 있다"는 게 어떻게 보장돼? + PENABLE은 무조건 1사이클만 high야?

### Q9-1. "클럭 에지에서 신호가 안정돼 있다"는 게 어떻게 보장되나

마법이 아니라, **칩을 만들기 전에 검사해서 보장**한다. 핵심은 **setup time**이라는 규칙.

**규칙: "에지 오기 *조금 전*까지 신호가 도착해서 멈춰 있어야 한다"**

플립플롭은 "클럭 에지가 오기 직전 일정 시간(setup time) 동안 입력이 안 흔들리고 가만히 있어야 제대로 읽는다"는 조건이 있다.

```text
신호 ───변하는 중───X───── 안정 ─────  (가만히)
                        │← setup →│
클럭 ____________________________/‾\___
                                  ↑ 에지: 이때 읽음
        신호는 이 빗금 구간엔 이미 멈춰 있어야 함
```

**비유: 단체 사진**

```text
"찰칵!" (셔터) = 클럭 에지
사람들 자리잡기 = 신호가 안정되는 것

규칙: 셔터 누르기 전에 모두 자리에 서서 멈춰 있어야 한다.
```

- 가장 **느린 사람**(= 가장 긴 조합 논리 경로)도 셔터 전에 자리잡을 수 있어야 함.
- 만약 못 잡으면? → 셔터를 **더 천천히** 누르거나(클럭 느리게), 그 사람을 **더 빨리 움직이게**(회로 최적화) 고침.

**누가 검사하나 — STA (Static Timing Analysis)**

칩을 만들기 전에 **STA 도구**가 모든 신호 경로를 훑어서 계산한다:

> "이 클럭 주파수에서, 가장 느린 경로도 다음 에지 전에 안정되는가?"

- **된다** → 통과. 칩 출하.
- **안 된다(timing violation)** → 클럭을 낮추거나 경로를 고친 뒤 다시 검사.

→ 즉 **"에지에서 안정돼 있다"는 STA가 통과시켜야만 칩이 나오니까 보장되는 것**이다. 글리치가 에지 사이에 튀어도, 다음 에지 전엔 반드시 가라앉도록 클럭 속도를 정한 것. (그래서 클럭을 무한정 빠르게 못 올린다 — 신호가 안정될 시간이 필요하니까.)

> **한 줄:** "에지에서 안정"은 우연이 아니라, **setup time 규칙 + STA 검사**로 *설계 단계에서 강제*한 결과. 안 되면 클럭을 늦춰서라도 맞춘다.

### Q9-2. PENABLE은 무조건 1사이클만 high인가?

**아니다.** `PENABLE`은 **ACCESS phase 내내 high**다. ACCESS가 길어지면(wait state) 같이 길어진다.

**wait state 없을 때 → 1사이클 high (이때만 1사이클)**

```text
        T1     T2
        SETUP  ACCESS
PSEL    __/‾‾‾‾‾‾‾‾‾‾
PENABLE ________/‾‾‾‾      ← 딱 1사이클
PREADY          1         ← slave 즉시 OK
```

**wait state 있을 때 → 여러 사이클 high**

```text
        T1     T2     T3     T4
        SETUP  ACCESS ACCESS ACCESS
                (wait)  (wait)  (완료)
PSEL    __/‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾
PENABLE ________/‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾      ← 3사이클 내내 high!
PREADY          0       0       1
                └── PREADY=0 동안 PENABLE 유지 ──┘
```

**정리하면**

```text
PENABLE high 길이 = ACCESS 길이 = 1 + (wait state 개수)

SETUP   : PENABLE = 0  (항상 1사이클)
ACCESS  : PENABLE = 1  (PREADY=1 될 때까지 유지, 최소 1사이클)
끝나면  : PENABLE = 0  (IDLE이거나, 다음 전송이면 다시 SETUP에서 0)
```

> "깨끗한 1사이클 strobe"는 **wait state가 없을 때만** 맞는 말이다. 정확히는 **`PENABLE`은 ACCESS 동안 high이고, wait state가 끼면 그만큼 길어진다.** 다만 `PREADY=1`로 전송이 끝나면 반드시 내려가고, 다음 전송은 또 SETUP(PENABLE=0)부터 시작한다.
>
> **참고:** 원래 APB(APB2, `PREADY` 없음)에선 ACCESS가 무조건 1사이클이라 `PENABLE`도 항상 정확히 1사이클이었다. wait state로 길어지는 건 `PREADY`가 생긴 **APB3부터**다.

## Q10. READ일 때 APB/AHB는 RDATA를 master가 어떻게 받아? AHB는 VALID 말고 뭘 써?

핵심은 **둘 다 "전송이 완료되는 그 클럭 에지"에서 master가 RDATA를 낚아챈다**는 것. write일 때와 **완료를 알리는 신호가 똑같고**, 단지 데이터가 흐르는 방향만 S→M으로 바뀐다.

### APB read — `PENABLE` & `PREADY`로 완료 시점을 안다

write와 완전히 같은 2-phase. `PWRITE=0`이고, `PWDATA` 자리 대신 slave가 `PRDATA`를 몰아준다.

```text
        T1      T2          T3
        SETUP   ACCESS      ACCESS
                (wait)      (완료)
PADDR   < 0x40 ................... >
PWRITE  < 0 (read) ............... >
PSEL    __/‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾\__
PENABLE ________/‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾\__
PRDATA          (slave가 구동중)  < 0xAB >
PREADY          0               1
                                ↑ 여기! master가 PRDATA 샘플
```

- master는 `PSEL=1 & PENABLE=1 & PREADY=1`이 **동시에 참인 에지**에서 `PRDATA`를 읽어들인다.
- write에서 "이 에지에 데이터가 써진다"고 한 그 에지에서, read에선 "이 에지의 `PRDATA`가 유효하다"가 되는 것. **완료를 알리는 신호 조합(`PENABLE`+`PREADY`)은 동일**하다.

### AHB read — `VALID` 대신 **`HREADY`** 를 쓴다

질문의 핵심이 여기다. **AHB엔 read용 VALID가 따로 없다. `HREADY`가 그 역할을 겸한다.**

```text
        T1          T2          T3
        주소 phase
                    데이터 phase
HADDR   < 0x100 >   < ... >
HWRITE  < 0 (read) >
HTRANS  NONSEQ      IDLE
HRDATA              (slave 구동중)  < 0xDE >
HREADY  1           0               1
                                    ↑ 여기! master가 HRDATA 샘플
HRESP               OKAY            OKAY
```

- 주소 phase(T1)에 주소를 내고, **데이터 phase**에서 slave가 `HRDATA`를 몰아준다.
- master는 **`HREADY=1`인 에지**에서 `HRDATA`를 읽어들인다.
- 즉 **`HREADY`가 "데이터 phase 완료" + "지금 `HRDATA`가 유효함"을 동시에 의미**한다. wait가 있으면 `HREADY=0` 동안 master는 기다리고, `HREADY=1` 되는 에지에 캡처.
- 유효성·에러는 `HRESP`(OKAY/ERROR)로 같이 판단.

### 왜 AHB엔 VALID가 없나

AHB는 **"데이터 phase에서 master는 항상 read 데이터를 받을 준비가 돼 있다"** 고 가정한다. 그래서 slave가 "데이터 준비됐다"는 신호(`HREADY`)만 주면 충분하고, 별도의 VALID나 master-side ready가 필요 없다. **`HREADY` 하나가 양쪽 박자를 다 맞춘다.**

### 세 프로토콜 비교 (read 데이터 받는 법)

| | 완료/유효 알림 | master-side ready | 별도 데이터 채널 |
|---|---|---|---|
| **APB** | `PENABLE` & `PREADY` 동시 | 없음 | 없음 (`PRDATA`) |
| **AHB** | **`HREADY=1`** (VALID 겸함) | 없음 | 없음 (`HRDATA`) |
| **AXI** | `RVALID` & `RREADY` 핸드셰이크 | **있음 (`RREADY`)** | **있음 (R 채널 전용)** |

> **한 줄:** APB는 **`PENABLE`+`PREADY`**, AHB는 **`HREADY`** 가 "지금 read 데이터 유효, 캡처해"라는 신호다. 둘 다 VALID라는 이름은 안 쓰지만 *완료 신호가 곧 데이터 유효 신호* 역할을 겸한다. 진짜 양방향 VALID/READY 핸드셰이크(slave의 `RVALID` + master의 `RREADY`)와 **전용 read 데이터 채널**을 갖춘 건 **AXI**다 — 그래서 AXI만 read 데이터를 주소와 무관하게 따로, 여러 개 밀린 채로(outstanding) 받을 수 있다.

## Q11. AHB에서 HTRANS가 IDLE이어도 HREADY만 보고 확인하는 거야?

그렇다. 그리고 그 이유가 AHB 파이프라인의 핵심을 정확히 건드린다. **`HTRANS`와 `HRDATA`는 서로 다른(한 박자 어긋난) phase에 속하기 때문**이다.

### 왜 그런가 — HTRANS와 HRDATA는 다른 transfer 얘기다

```text
HTRANS  → "지금 이 클럭의 주소 phase" 얘기 (새 전송을 시작하나?)
HRDATA  → "한 박자 전에 주소를 낸 전송"의 데이터 phase 얘기
HREADY  → 그 데이터 phase가 끝났나(=HRDATA 유효한가)
```

한 박자 어긋나 있으니, **같은 클럭에서 `HTRANS=IDLE`이면서 동시에 이전 read의 데이터가 돌아올 수 있다.** 둘이 가리키는 transfer가 다르니까.

### 파형으로 — single read

```text
        T1          T2          T3
        주소 phase
                    데이터 phase(0x100의)
HTRANS  NONSEQ      IDLE        IDLE
HADDR   0x100       (다음 거 없음)
HWRITE  0
HRDATA              < 0x100 데이터 유효 >
HREADY  1           1
                    ↑ master가 여기서 HRDATA 캡처
                      (HTRANS는 IDLE이지만 그건 "새 전송 없음" 얘기일 뿐,
                       0x100의 read 데이터와는 무관)
```

- T1: 0x100 read의 **주소 phase**. `HTRANS=NONSEQ`.
- T2: 0x100 read의 **데이터 phase**. slave가 `HRDATA` 구동. master는 더 보낼 게 없어서 `HTRANS=IDLE`.
- T2의 `HTRANS=IDLE`은 "**다음** 전송 없음"이라는 뜻이고, 지금 돌아오는 `HRDATA`(0x100의 결과)와는 별개.
- master는 **`HREADY=1`인 에지에서 `HRDATA`를 캡처** — `HTRANS` 값과 무관.

### 단, 한 가지 단서 — master는 "내가 read를 띄웠다"를 알고 있어야

순수하게 `HREADY`만 보는 건 아니고, master는 **"내가 직전 클럭에 read 주소를 냈으니, 이번 클럭은 그 데이터 phase다"** 라는 걸 스스로 알고 있어야 한다. 그 위에서 `HREADY=1` 에지에 캡처하는 것.

```text
master 입장:
  "지난 클럭에 read 주소(0x100) 냈음 → 지금은 그 데이터 phase →
   HREADY=1 되는 에지의 HRDATA가 내 데이터다"
```

그런데 AHB는 **항상 한 번에 하나의 전송만 데이터 phase에 있어서**(single outstanding) master가 "지금 데이터 phase에 있는 게 뭔지" 헷갈릴 일이 없다. 그래서 ID 같은 것도 필요 없다.

### 여기서 AXI와의 차이가 드러남

```text
AHB:  데이터 phase에 항상 transfer 1개뿐 → "HREADY=1이면 그게 내 데이터"
      (어느 전송 데이터인지 따질 필요 없음)

AXI:  여러 read가 동시에 밀려 있을(outstanding) 수 있음 →
      돌아온 데이터가 "어느 요청 것"인지 RID로 구분해야 함
      + RVALID/RREADY로 양방향 핸드셰이크
```

> **한 줄:** 맞다 — AHB에서 read 데이터는 **`HTRANS`와 무관하게 `HREADY`(+`HRESP`)로 확인**한다. `HTRANS=IDLE`은 "새 전송 시작 안 함"일 뿐이고, 돌아오는 `HRDATA`는 한 박자 전 주소 phase의 전송 것이라 별개다. 다만 master는 "내가 read를 띄웠다"는 문맥을 알고 그 데이터 phase의 `HREADY=1` 에지에 캡처하는 것 — AHB는 한 번에 하나뿐이라 그 문맥이 항상 명확하다.

## Q12. NONSEQ vs SEQ 차이가 뭐야? (동일한 주소로 보내면?)

혼란의 원인이 명확하다. **NONSEQ/SEQ는 "주소 값"을 설명하는 게 아니라, "이 전송이 버스트에서 어떤 위치인가(처음이냐 / 이어지는 거냐)"를 설명하는 꼬리표**다. 주소 자체의 성질이 아니라 **앞 전송과의 관계**를 나타낸다.

### 1. 진짜 의미

| 타입 | 뜻 | 언제 |
|---|---|---|
| **NONSEQ** (non-sequential) | "**새로** 시작하는 전송" — 앞 전송과 무관 | 버스트의 **첫 beat**, 또는 단일 전송 |
| **SEQ** (sequential) | "앞 버스트를 **이어가는** 전송" — 주소가 앞 것에서 규칙대로 이어짐 | 버스트의 **2번째 이후 beat** |

핵심: **SEQ는 "내 주소 = 앞 주소 + 전송크기"라는 약속을 포함**한다. 즉 SEQ는 정의상 주소가 *이어지는* 전송이다.

### 2. 버스트로 보면 명확

INCR4 버스트 (`0x100`부터 word 4개):

```text
        beat0    beat1    beat2    beat3
HADDR   0x100    0x104    0x108    0x10C
HTRANS  NONSEQ   SEQ      SEQ      SEQ
        └첫 전송  └─── "앞에 이어지는 전송" ───┘
```

- **beat0 = NONSEQ**: "지금 버스트 새로 시작. 시작 주소는 0x100."
- **beat1~3 = SEQ**: "방금 거에 이어지는 거야. 주소도 규칙대로 +4씩 이어짐."

### 3. 그래서 "같은 주소로 NONSEQ vs SEQ"는?

여기가 혼란의 지점인데 — **정상적인 버스트에선 SEQ가 같은 주소를 가질 수 없다.** SEQ는 정의상 "주소가 앞에서 +전송크기만큼 이어진다"는 뜻이라서다. SEQ인데 주소가 안 변하면 **프로토콜 위반**이다.

그럼 같은 주소에 두 번 쓰고 싶으면? → **둘 다 NONSEQ** (서로 무관한 두 개의 독립 전송)로 보낸다.

```text
같은 주소 0x100에 두 번 쓰기:

HADDR   0x100    0x100
HTRANS  NONSEQ   NONSEQ      ← 둘 다 "새 전송". 서로 별개의 트랜잭션.
        쓰기A     쓰기B
```

```text
이건 틀림 (말이 안 됨):
HADDR   0x100    0x100
HTRANS  NONSEQ   SEQ         ← SEQ인데 주소가 안 이어짐? → 위반 ❌
                 "이어진다며 주소가 왜 그대로야?"
```

> 그래서 "같은 주소로 NONSEQ vs SEQ"는 비교 자체가 성립을 안 한다. **SEQ는 애초에 "주소가 이어진다"는 뜻이라 같은 주소면 SEQ가 될 수 없다.**

### 4. 그럼 왜 굳이 구분하나? (slave가 왜 알아야 하나)

주소만 보면 될 것 같은데 왜 NONSEQ/SEQ를 따로 알려줄까?

1. **"버스트가 이어지는 중"임을 slave/인터커넥트에 알림**
   - SEQ가 오면 slave는 "아, 아까 그 버스트 계속이구나" → 주소가 예측 가능하니 **미리 다음 데이터를 준비(prefetch)** 할 수 있음.
   - NONSEQ가 오면 "새 접근이네" → 처음부터 디코딩/판단.

2. **인터커넥트 arbitration**
   - 버스트(NONSEQ + SEQ들)는 **한 덩어리로 묶어** 처리해야 함. SEQ가 흐르는 동안엔 다른 마스터에게 버스를 안 뺏기게 유지. NONSEQ는 "새 덩어리 시작" 신호.

3. **컨텍스트 전달**
   - SEQ는 "`HBURST`/`HSIZE`/`HWRITE`가 앞과 동일하다"는 것도 암묵적으로 보장 → slave가 매번 다시 안 따져도 됨.

### 5. (참고) BUSY와 헷갈리지 말기

"버스트 중인데 주소가 안 변하는" 정당한 경우는 SEQ가 아니라 **BUSY**다.

```text
HTRANS  NONSEQ   SEQ     BUSY    SEQ
HADDR   0x100    0x104   0x108   0x108
                         └마스터가 잠깐 대기. 다음에 쓸 주소(0x108) 유지.
                          전송은 안 일어남. 준비되면 SEQ로 0x108 실행.
```

- **BUSY** = "나 버스트 중인데 이번 beat 데이터가 아직 준비 안 됨. 잠깐만." → 주소 유지, 전송 안 함.
- 그러다 준비되면 **SEQ**로 그 주소를 실제 전송.

> **정리:** NONSEQ = "새로 시작하는 전송", SEQ = "앞 버스트에 이어지는 전송, 주소도 규칙대로 이어짐". 둘은 **주소 값이 아니라 "앞 전송과의 관계"** 를 나타냄. 그래서 **SEQ는 같은 주소를 가질 수 없음**. 구분하는 이유: slave의 prefetch 최적화 + 인터커넥트가 버스트를 한 덩어리로 묶기 위한 문맥 정보. 버스트 중 주소 유지하며 쉬는 건 SEQ가 아니라 **BUSY**.

## Q13. 0x100-0x104-0x108에 쓸 때 전부 NONSEQ vs NONSEQ-SEQ-SEQ 차이는?

**데이터를 0x100, 0x104, 0x108에 쓰는 결과는 두 방식이 똑같다.** 메모리에 들어가는 값은 동일하다. 차이는 **"이 세 전송을 시스템이 어떻게 취급하느냐(문맥/의도)"** 에 있다.

### 두 방식의 파형

**방식 A — 전부 NONSEQ (독립된 single 3개)**

```text
        T1     T2     T3     T4
HADDR   0x100  0x104  0x108
HTRANS  NONSEQ NONSEQ NONSEQ IDLE
HBURST  SINGLE SINGLE SINGLE       ← 매번 "단일 전송"
HWDATA         D0     D1     D2

의미: "서로 무관한 쓰기 3개를 그냥 연달아 던졌다."
```

**방식 B — NONSEQ-SEQ-SEQ (버스트 1개)**

```text
        T1     T2     T3     T4
HADDR   0x100  0x104  0x108
HTRANS  NONSEQ SEQ    SEQ    IDLE
HBURST  INCR   INCR   INCR         ← "이어지는 한 덩어리(증가 버스트)"
HWDATA         D0     D1     D2

의미: "0x100부터 이어지는 하나의 버스트다."
```

> 클럭 수도, 메모리 결과도 같아 보인다. 그런데 **slave와 인터커넥트가 받아들이는 의미가 완전히 다르다.**

### 진짜 차이 3가지

**① 인터커넥트가 중간에 다른 마스터를 끼울 수 있나 (가장 중요)**

```text
방식 A (전부 NONSEQ): 각 전송이 "독립"이라, 사이에 끼어들기 허용
  0x100(나) → [다른 마스터 전송!] → 0x104(나) → [또 끼어듦] → 0x108(나)
  → 내 3개가 뿔뿔이 흩어질 수 있음

방식 B (버스트): "한 덩어리"라고 선언 → 인터커넥트가 묶어서 유지
  0x100 → 0x104 → 0x108  (중간에 안 끊김, 연속 보장)
```

여러 마스터가 버스를 두고 경쟁할 때, **방식 A는 내 전송들 사이에 남의 전송이 끼어들 수 있고, 방식 B는 버스트가 끝날 때까지 버스를 붙잡아 둔다.** (이게 둘의 가장 실질적인 차이)

**② slave가 미리 준비(prefetch/최적화)할 수 있나**

```text
방식 A: slave는 매 전송을 "새 접근"으로 봄. 다음에 뭐가 올지 모름.
        → 매번 처음부터 디코딩. 미리 준비 불가.

방식 B: SEQ + HBURST=INCR을 보면 "주소가 +4씩 이어지는 버스트구나" 앎.
        → DRAM이면 같은 row를 열어두고, 다음 데이터를 미리 준비(prefetch).
        → 결과적으로 더 빠르고 효율적.
```

특히 DRAM 컨트롤러는 버스트라는 걸 알면 row를 열어둔 채 연속 처리해서 훨씬 빠르다. 독립 single 3개로 보이면 그 최적화를 못 한다.

**③ "몇 개가 올지" 정보 전달**

```text
방식 A: HBURST=SINGLE → "이번 거 하나뿐". 다음이 있는지 매번 모름.
방식 B: HBURST가 버스트 종류를 알림.
        (정확히 4개면 INCR4, 8개면 INCR8처럼 "길이 확정" 버스트도 가능 →
         slave가 "총 몇 beat 온다"까지 미리 앎)
```

> 참고: 0x100/104/108 **3개**는 고정길이 버스트(4/8/16)에 안 맞아서 `HBURST=INCR`(길이 미정 증가 버스트)을 쓴다. 만약 4개(0x100~0x10C)였다면 `INCR4`로 "정확히 4개 온다"까지 선언할 수 있다.

### 언제 뭘 쓰나

| 상황 | 권장 | 이유 |
|---|---|---|
| 연속 주소 한 덩어리 (메모리 복사, 캐시 fill) | **방식 B (버스트)** | 끊김 없이 묶임 + slave 최적화 → 빠름 |
| 서로 무관한 레지스터들 산발적 접근 | **방식 A (single)** | 애초에 이어지지 않으니 버스트로 묶을 이유 없음 |
| 주소가 연속이 아님 (0x100, 0x200, 0x308) | **방식 A** | SEQ는 "주소가 규칙대로 이어진다"는 약속이라 못 씀 |

> **정리:** 0x100-0x104-0x108에 쓰는 결과(메모리 값)는 두 방식이 동일하다. 차이는: **방식 A**(전부 NONSEQ)는 "독립된 전송 3개"라 인터커넥트가 사이에 다른 마스터를 끼울 수 있고 slave 최적화 불가. **방식 B**(NONSEQ-SEQ-SEQ)는 "하나의 버스트"라 인터커넥트가 끊지 않고 묶어주고 slave가 prefetch 등 최적화 가능. SEQ는 "이건 앞에 이어지는 한 덩어리야"라고 시스템에 알려주는 **선언**이고, 그 선언이 버스 점유(끼어들기 방지)와 slave 최적화에서 실질적 차이를 만든다.

## Q14. 2-cycle ERROR를 좀 더 쉽게. 그리고 APB·AHB는 ID가 없는데 모두 in-order인가?

### Q14-1. 2-cycle ERROR를 쉽게

**문제 상황부터.** AHB는 파이프라인이라, slave가 "방금 그 전송 실패!"를 깨달았을 땐 **이미 다음 전송의 주소가 버스에 올라와 있다.**

```text
T1: A1 주소 phase
T2: A1 데이터 phase ← 여기서 slave가 "A1 실패!" 발견
                      그런데 master는 T2에 벌써 A2 주소를 깔아둠!
```

만약 slave가 한 클럭에 "에러 + 완료"를 동시에 때려버리면, master는 **이미 진행 중인 A2를 취소할 틈이 없다.** 그래서 AHB는 에러를 **2박자**로 나눠서, 첫 박자를 "예고"로 쓴다.

```text
        T1       T2          T3          T4
HTRANS  NONSEQ   NONSEQ(A2)  IDLE
HADDR   A1       A2          -           ← master가 A2 취소(IDLE)
HRESP   OKAY     ERROR       ERROR
HREADY  1        0           1
                 ↑1박자       ↑2박자
                 "에러야!     "에러 확정,
                  잠깐(미완료)" 이제 완료"
```

- **1박자 (HRESP=ERROR, HREADY=0):** "이 전송 실패다. 근데 아직 안 끝냈어(`HREADY=0`)." → master에게 **"뒤에 깔아둔 A2 취소할 시간 한 박자"** 를 줌. master는 T3에서 `HTRANS=IDLE`로 A2를 거둬들임.
- **2박자 (HRESP=ERROR, HREADY=1):** "에러로 공식 완료." → 이제 전송 종료.

> **쉬운 비유:** 컨베이어 벨트에서 불량품이 나왔는데, 뒤 제품이 이미 따라오고 있다. "불량!" 하고 바로 멈추면 뒤 제품이 들이박는다. 그래서 먼저 **"불량 떴다, 준비해"(1박자)** → 뒤 제품 빼낼 시간 주고 → **"불량 처리 완료"(2박자)**. 한 박자의 예고가 핵심이다.
>
> **왜 APB는 1박자면 되나?** APB는 파이프라인이 없어서 "뒤에 따라오는 전송"이 애초에 없다. 취소할 게 없으니 `PSLVERR`을 그냥 완료 시점에 한 번에 띄우면 끝.

### Q14-2. ID가 없다 → 전부 in-order, 맞다

정확하다. **APB도 AHB도 ID가 없고, 둘 다 엄격하게 in-order다.** 그리고 그 이유가 핵심인데 — **애초에 ID가 필요 없기 때문**이다.

**왜 ID 없이도 되나 — single outstanding**

```text
APB/AHB: 한 번에 진행 중인 전송이 "딱 하나" (single outstanding)
  요청 → (완료될 때까지 다음 요청 못 띄움) → 완료 → 다음 요청 → ...

→ 항상 하나뿐이니, 돌아온 응답/데이터가 "어느 요청 것"인지 헷갈릴 일이 없음
→ 순서가 자동으로 보장됨 (먼저 낸 게 먼저 끝남)
→ 그래서 ID도, out-of-order도 개념 자체가 없음
```

- read든 write든 같은 채널을 쓰니, **read/write 사이 순서도 엄격하게 지켜진다.**
- "구분할 게 하나뿐이라 이름표(ID)가 필요 없다"가 정확한 직관이다.

**AXI는 왜 ID가 생겼나 — 이게 대비점**

AXI는 정반대 욕심을 낸다:

```text
AXI: 응답 기다리는 동안 다음 요청을 또 던짐 (multiple outstanding)
     + 느린 응답을 기다리지 말고 빠른 것 먼저 받자 (out-of-order)

  요청0, 요청1, 요청2 ... 다 띄워놓음
  → 응답이 0,1,2 순서로 안 올 수 있음 (slave가 빠른 것부터 응답)
  → "이 응답이 어느 요청 것?"을 구분할 이름표가 필요 → 그게 ID
```

| | outstanding | out-of-order | ID | 순서 |
|---|---|---|---|---|
| **APB** | 1개 | ✗ | 없음 | 엄격 in-order |
| **AHB** | 1개 | ✗ | 없음 | 엄격 in-order |
| **AXI** | 여러 개 | ✓ | **있음** | 같은 ID는 in-order, 다른 ID는 순서 보장 없음 |

> **한 줄:** 맞다 — APB·AHB는 **한 번에 하나만 처리(single outstanding)** 하니 순서가 저절로 지켜져서 **전부 in-order이고 ID가 필요 없다.** ID는 "여러 개를 동시에 띄우고(outstanding), 빠른 것부터 순서 바꿔 받겠다(out-of-order)"는 **AXI에서 비로소 필요해지는 이름표**다.

## Q15. 그냥 첫 박자에 아무것도 안 하고 둘째 박자에 ERR 띄워도 결국 똑같은 거 아니야? 첫 박자에 err 띄워도 HREADY가 0이잖아. 그럼 마스터는 애초에 모르는데?

아주 날카로운 반론인데, 여기에 **핵심 오해가 하나** 있다. **`HREADY=0`이라고 master가 눈을 감고 있는 게 아니다.** master는 **매 클럭 에지마다 `HRESP`를 샘플링**한다. `HREADY=0`은 "아직 이 전송 안 끝났어"라는 뜻이지, "아무 신호도 보지 마"가 아니다.

### 그래서 첫 박자가 의미가 있다

master는 첫 에러 박자가 끝나는 에지에서 **`HRESP=ERROR`를 분명히 본다.** 그게 바로 "에러 예고"를 받는 순간이다. `HREADY=0`인데 `HRESP=ERROR`다 → master는 "아, 에러 온다. 근데 아직 완료(`HREADY=1`)는 아니네 → 지금 뒤에 깔아둔 A2 취소하자"라고 판단한다.

### 두 방식을 나란히 비교하면 결정적

핵심은 **"master가 에러를 *언제* 아느냐 vs 다음 전송이 *언제* commit 되느냐"** 의 타이밍이다. commit은 `HREADY=1` 에지에서 일어난다.

**✅ 올바른 2-cycle (에러를 첫 박자에)**

```text
        T2          T3
HTRANS  A2(NONSEQ)  IDLE          ← master가 A2 취소!
HRESP   ERROR       ERROR
HREADY  0           1
        ↑여기서 master가          ↑전송 완료. 그런데 이 에지에서
         ERROR 샘플 (HREADY=0)     commit되는 주소phase는 이미 IDLE → A2 안 나감 ✅

흐름: T2 끝에 에러 알아챔 → T3에 HTRANS=IDLE로 A2 거둬들임
     → T3의 HREADY=1 에지엔 'IDLE'이 latch됨 → A2 취소 성공
```

**❌ 당신 방식 (첫 박자 가만, 둘째 박자에 에러)**

```text
        T2          T3
HTRANS  A2(NONSEQ)  A2(그대로!)    ← 취소 못 함
HRESP   OKAY        ERROR
HREADY  0           1
        ↑master는 OKAY만 봄.      ↑ERROR를 보는 바로 그 에지에서
         예고 없음 → 안심하고      동시에 A2가 commit됨(HREADY=1)
         A2 유지                   → A2가 그냥 실행돼 버림. 너무 늦음 ❌
```

### 무슨 차이냐면

```text
2-cycle:    에러를 [HREADY=0 박자]에 미리 알림
            → master가 다음 commit(HREADY=1) "전에" A2 취소 가능

당신 방식:  에러를 [HREADY=1 박자]에 알림
            → master가 에러를 아는 에지 = A2가 commit되는 에지 (동시)
            → 취소할 틈이 0. A2가 실행돼 버림
```

> **즉 `HREADY=0` 박자는 "master가 못 보는 죽은 시간"이 아니라, 오히려 "commit 없이 에러만 전달하는 안전한 한 박자"** 다. master는 그 박자에 `HRESP`를 읽고, 다음 박자(`HREADY=1`, commit 시점)가 오기 전에 뒤 전송을 IDLE로 거둬들이는 것.

**정리**

- `HREADY=0` ≠ master가 눈 감음. master는 **매 에지 `HRESP`를 본다.**
- 다음 전송이 실제로 commit되는 건 **`HREADY=1` 에지**.
- **에러를 첫 박자(`HREADY=0`)에 띄워야**, master가 commit 전에 다음 전송을 취소할 한 박자를 번다.
- 당신 방식(둘째 박자에만 에러)은 **"에러 인지 = 다음 전송 commit"이 같은 에지**가 돼서 취소가 불가능 → 그래서 안 됨.

> 한 줄: 2박자의 본질은 **"commit(HREADY=1)보다 한 박자 먼저 에러를 알려, 파이프라인에 딸려온 다음 전송을 취소할 시간을 주는 것"** 이다. `HREADY=0` 박자가 바로 그 "미리 알림" 박자다.

## Q16. A2를 취소한다는 거야? 왜 취소해? A3는 그대로 가는 거야? (쉽게 다시)

처음부터 천천히 — 왜 "취소"라는 말이 나오는지부터 그림을 다시 그리자. (A2, A3를 맥락 없이 던져서 헷갈렸던 부분)

### 먼저 상황을 제대로 깔자 — 버스트

master가 **연속된 4곳에 버스트로 쓰기** 중이라고 하자. (A1→A2→A3→A4)

```text
master 의도: "A1, A2, A3, A4 네 군데에 쭉 쓸 거야"
```

AHB는 파이프라인이라 **한 박자씩 미리** 주소를 던진다:

```text
        T1     T2     T3     T4     T5
HADDR   A1     A2     A3     A4
HWDATA         D1     D2     D3     D4
              (A1쓰는중)(A2쓰는중)...
```

→ A1을 쓰는 동안 이미 A2 주소가 나가 있고, 그 다음 A3, A4가 줄줄이 따라온다.

### 이제 문제 — A1이 실패하면?

A1을 쓰려는데 slave가 **"A1 실패!"**(예: 거기 쓰기 금지 구역, 주소 디코드 에러)라고 한다.

이때 master 입장:
> "A1이 실패했네. 이 영역이 문제인 것 같으니 **나머지 A2, A3, A4도 그만 쓸래.**"

에러가 나면 보통 **하던 작업(버스트)을 통째로 포기**하는 게 자연스럽다. (주소 영역이 잘못됐는데 나머지를 계속 쓸 이유가 없다.)

### 그런데 문제 — A2가 이미 나가 있다

파이프라인이라, slave가 "A1 실패"라고 말하는 시점엔 **A2 주소가 이미 버스에 올라가 있다.** 그냥 두면 A2까지 써져 버린다. master는 **"A2 취소!"** 라고 해야 한다.

```text
"취소한다" = A2 주소를 거둬들이고 HTRANS=IDLE로 바꿔서
            → A2 쓰기가 일어나지 않게 막는 것
```

### A3, A4는?

**A3, A4는 아직 버스에 안 나갔다.** master가 A2를 취소하고 멈추면, A3·A4는 **그냥 안 보내면 끝.** 따로 취소할 것도 없다.

```text
취소해야 하는 건 = "이미 나가버린" A2 (1개)
A3, A4         = 아직 안 보냈으니 그냥 발사 중단
```

→ 결국 **버스트 전체가 A1 에러로 중단**된다.

### 그럼 2박자 에러가 왜 필요했나 (이제 연결)

A2가 "이미 나가 있다"고 했다. AHB 규칙상 **다음 주소가 실제로 확정(commit)되는 건 `HREADY=1`인 에지**다. 그러니 master는 그 commit 에지가 오기 **전에** "A2 취소(IDLE)"를 해야 한다.

```text
        T2          T3
HTRANS  A2          IDLE          ← master가 A2를 IDLE로 → 취소!
HRESP   ERROR       ERROR
HREADY  0           1
        ↑1박자:      ↑2박자:
        "A1 실패!    "A1 에러 완료"
         (아직 미완료)" 이 에지에 commit되는 주소는
                       이미 IDLE이라 A2 안 써짐 ✅
```

- **1박자 (`HREADY=0`, ERROR):** slave가 "A1 실패" 알림. master가 이걸 보고 **"A2 취소해야겠다"** 결심.
- **2박자 (`HREADY=1`, ERROR):** A1 에러로 마무리. 이 에지에 commit되는 주소는 이미 master가 IDLE로 바꿔놨으니 **A2가 안 써지고 무사히 취소됨.**

만약 1박자 없이 한 방에 끝냈으면, master가 에러를 아는 순간 = A2가 써지는 순간이 **겹쳐서** 취소할 틈이 없었던 것. 그래서 한 박자 먼저 알려주는 것.

> **한 줄 정리:**
> - AHB는 파이프라인이라 A1을 쓰는 동안 **다음 A2가 이미 나가 있다.**
> - A1이 에러나면 master는 보통 **나머지를 포기** → 이미 나간 **A2를 취소**(IDLE로)해야 하고, **A3·A4는 아직 안 보냈으니 그냥 안 보내면 끝.**
> - 2박자 에러는 **"A2가 실제로 써지기(commit) 전에 취소할 한 박자"** 를 주려고 있는 것.
>
> 즉 "취소"는 *A1 에러 때문에 버스트를 중단하는데, 파이프라인 때문에 미리 튀어나간 다음 전송 하나(A2)를 거둬들이는 것*이다. A3는 애초에 출발도 안 했다.

## Q17. 5-5 또 다른 예제(WRAP)가 잘 이해 안 돼

5-5는 본문에서 든 **WRAP 버스트 두 번째 예제**다. WRAP 개념부터 아주 쉬운 비유로 다시 깔고 두 예제를 나란히 보자.

### WRAP을 쉽게 — "운동장 트랙 돌기"

WRAP 버스트는 **정해진 구역(블록) 안에서만 주소가 돈다**고 생각하면 된다. 트랙을 돌다가 끝에 닿으면 **출발선으로 되돌아오는** 것처럼.

```text
블록 크기 = 한 칸 크기(전송크기) × 칸 개수(beat 수)
블록은 그 크기로 "딱 떨어지게" 정렬돼 있음
주소가 블록 끝에 닿으면 → 블록 맨 앞으로 되돌아옴(wrap)
```

왜 이런 게 필요하냐면 — 캐시는 "라인"이라는 고정 블록 단위로 채우는데, **정작 CPU가 당장 필요한 데이터는 라인 한가운데** 있을 수 있다. 그래서 **필요한 곳부터 받고, 라인 끝에 닿으면 앞으로 돌아와** 나머지를 채운다.

### 예제 A (5-4) — 블록 *중간*에서 출발 → 진짜로 wrap 일어남

```text
조건: WRAP4, 한 칸 = 4바이트, 출발 = 0x34

블록 크기 = 4바이트 × 4칸 = 16바이트(0x10)
블록 범위 = 0x30 ~ 0x3F   (0x34를 16 단위로 내림 → 0x30이 시작)

       0x30  0x34  0x38  0x3C │ 0x40...
        │     ●─────●─────●    │
        │     출발  2번  3번    경계!
        └──────────────────┘
              ↑ 4번째에서 0x40이 되려는데 블록 밖! → 0x30으로 되돌아옴

순서:  0x34 → 0x38 → 0x3C → 0x30
       (출발이 중간이라 끝에 닿고 앞으로 점프) ← wrap 발생!
```

### 예제 B (5-5) — 블록 *시작*에서 출발 → wrap이 안 일어남

```text
조건: WRAP8, 한 칸 = 4바이트, 출발 = 0x1000

블록 크기 = 4바이트 × 8칸 = 32바이트(0x20)
블록 범위 = 0x1000 ~ 0x101F   (0x1000은 이미 32 단위로 딱 정렬됨)

0x1000 0x1004 ... 0x101C │ 0x1020
  ●──────●──────────●     │
  출발               8번째  여기서 버스트 끝
  └───────────────────┘
  8칸이 블록을 정확히 채움 → 끝에 닿는 순간이 곧 버스트 끝

순서:  0x1000 → 0x1004 → 0x1008 → ... → 0x101C
       (출발이 블록 맨 앞이라 되돌아올 일이 없음) ← wrap 안 일어남!
```

### 5-5의 진짜 포인트

> **출발 주소가 블록 경계에 딱 맞으면(aligned), WRAP을 써도 INCR(그냥 증가)과 결과가 똑같아 보인다.** 8칸이 블록을 정확히 채우고 끝나버리니, "되돌아오는" 동작이 나올 일이 없다.

| | 출발 위치 | wrap 일어나나? | 순서 |
|---|---|---|---|
| 예제 A (5-4) | 블록 **중간**(0x34) | **예** | 0x34→0x38→0x3C→**0x30** (점프) |
| 예제 B (5-5) | 블록 **시작**(0x1000) | **아니오** | 0x1000→…→0x101C (그냥 증가) |

> **결론:** WRAP의 "되돌아옴"은 **출발 주소가 블록 한가운데일 때만** 나타난다. 블록 맨 앞에서 출발하면 트랙을 한 바퀴 돌 일 없이 끝나서 INCR과 구별이 안 된다. 5-5는 바로 그걸 보여주는 대조 예제 — "정렬된 출발이면 wrap이 사실상 안 보인다."

## Q18. AXI뿐 아니라 APB·AHB를 쓰는 이유를 trade-off 관점에서

"AXI가 제일 강력한데 왜 APB·AHB를 아직도 쓰나?"는 결국 **"강력함은 공짜가 아니다"** 라는 trade-off 얘기다.

> **핵심:** 버스는 "성능"을 얻는 대신 "면적·전력·복잡도·검증비용"을 낸다. GPIO 하나에 AXI를 붙이는 건, 편지 한 장 부치려고 화물 트레일러를 모는 격. **트래픽에 맞는 최소한의 버스**를 쓰는 게 정답이라서 세 개가 공존한다.

### 1. trade-off 축 — 무엇을 주고받나

성능을 올리는 모든 기능에는 대가가 붙는다.

| 성능 기능 | 얻는 것 | 내는 비용 |
|---|---|---|
| 채널 분리 (AXI 5채널) | 동시성, throughput | **배선 수 폭발**, 면적 |
| Outstanding/ID | 응답 안 기다리고 연속 발행 | 추적 버퍼, 상태 로직, 면적 |
| Out-of-order | 빠른 응답 먼저 받기 | reorder 로직, ID 매칭 |
| 버스트/파이프라인 (AHB) | 연속 접근 빠름 | FSM 복잡, `HREADY`/2-cycle error 같은 규칙 |
| 단순 2-phase (APB) | 회로 극소, 검증 쉬움 | 느림 (전송당 2클럭) |

### 2. 4가지 비용 축으로 본 세 프로토콜

**① 면적 / 게이트 수 (배선 포함)**

```text
APB:  신호 십수 개. slave FSM 몇 줄. 거의 공짜.
AHB:  중간. 파이프라인 레지스터 + HREADY 로직.
AXI:  5채널 × (주소·데이터·응답) → 신호 수백 개.
      + outstanding 추적 버퍼 + ID 매칭 + reorder.
      32비트 AXI 한 포트가 APB 수십 개 맞먹는 배선/면적.
```

→ GPIO·타이머처럼 **수백 개** 붙는 저속 블록에 AXI를 쓰면 칩이 배선으로 터진다. APB면 거의 공짜.

**② 전력**

```text
게이트가 적게 토글 = 동적 전력 적음.
APB: 토글 거의 없음 + 클럭 게이팅 단순 → 저전력에 최적.
AXI: 항상 돌아가는 채널·버퍼가 많아 idle 전력도 큼.
```

→ 배터리/저전력 SoC의 주변부일수록 APB가 유리.

**③ 검증 비용 (DV 관점)**

```text
APB:  체크할 프로토콜 규칙 한 줌 (FSM 위반 정도). VIP 가벼움.
AHB:  중간 (2-cycle error, 파이프라인 정렬, 버스트 경계).
AXI:  체크 항목 수백 개 — ordering, outstanding, interleaving,
      ID 충돌, 4KB 경계, exclusive... protocol checker가 거대.
```

→ 단순 레지스터 블록에 AXI를 붙이면, 정작 그 블록은 register write 하나 하는데 **AXI ordering/outstanding 검증을 통째로** 떠안아야 함. 낭비.

**④ 지연(latency)과 예측가능성**

```text
APB: 단일 접근이 "항상 2클럭"으로 단순·예측가능.
AXI: 단일 접근에도 여러 채널 핸드셰이크가 끼어 오히려 latency가 더 길 수 있음.
     AXI의 강점은 "많은 양을 동시에"이지 "하나를 빨리"가 아님.
```

→ 어쩌다 한 번 레지스터 읽는 데는 APB의 단순·예측가능한 2클럭이 충분하고 오히려 깔끔.

### 3. 그래서 "어디에 뭘" — 트래픽에 맞춘 선택

| | APB | AHB | AXI |
|---|---|---|---|
| 대역폭 요구 | 거의 없음 | 중간 | 높음 |
| 면적/배선 | 극소 | 중간 | 큼 |
| 전력 | 최소 | 중간 | 큼 |
| 검증 비용 | 낮음 | 중간 | 높음 |
| outstanding | ✗ | ✗(1개) | ✓(다중) |
| 대표 고객 | GPIO, 타이머, CSR | ROM/SRAM, MCU backbone, 단순 마스터 | CPU↔메모리, DMA, 가속기, NoC |

**의사결정 흐름**

```text
이 블록이 1초에 얼마나 많은 데이터를 옮기나?
   │
   ├─ 거의 안 옮김 (레지스터 깔짝) ──────────► APB
   │     "굳이 비싼 버스 쓸 이유 없음"
   │
   ├─ 적당히 (연속 접근 좀 있음, 마스터 단순) ─► AHB
   │     "버스트·파이프라인은 필요하지만
   │      다중 outstanding까진 과함"
   │
   └─ 많이 (높은 대역폭, 동시 다발) ──────────► AXI
         "면적·검증비용 내고 throughput 산다"
```

### 4. 왜 셋이 "공존"하나 — 계층화의 묘

핵심은 **한 칩에 셋을 섞어 쓰는** 것이다. 비싼 자원(AXI)은 꼭 필요한 곳에만 쓰고, 나머지는 싼 버스로 내린다.

```text
        ┌──── AXI (고속 backbone/NoC) ────┐  ← 비싸지만 필수인 곳에만
 CPU ──┤   메모리   DMA   가속기            │
        └──────────────┬──────────────────┘
                       │ [AXI→AHB bridge]
                       ▼
        ┌──── AHB (중속) ────┐
        │   SRAM   ROM        │
        └─────────┬───────────┘
                  │ [AHB→APB bridge]
                  ▼
        ┌──── APB (저속, 수십 개) ────┐  ← 싸게 대량으로
        │  UART GPIO Timer I2C ...    │
        └─────────────────────────────┘
```

→ "고속 도로 + 국도 + 골목길"을 섞듯, **트래픽 등급에 맞는 버스를 계층으로** 깔아 면적·전력·검증비용을 최소화하면서 필요한 성능을 낸다.

> **핵심 정리:**
> - 성능(채널 분리·outstanding·OoO)은 면적·전력·배선·검증비용으로 산다. 공짜 강력함은 없다.
> - **APB:** 거의 공짜 회로 + 저전력 + 쉬운 검증. 대신 느림. → 저속 주변장치(GPIO/CSR)에 대량으로 깔 때 최적.
> - **AHB:** 중간. 파이프라인·버스트는 되지만 다중 outstanding은 없음. → 중속 backbone, 단순 마스터, MCU에 적당.
> - **AXI:** 최고 throughput. 대신 면적·전력·검증비용 큼. → 진짜 대역폭이 필요한 CPU/DMA/가속기에만.
> - **Golden rule:** 트래픽에 맞는 최소한의 버스를 골라 계층으로 섞는다. AXI가 제일 세다고 다 AXI로 깔면 면적·전력·검증으로 손해. 그래서 셋이 공존한다.
