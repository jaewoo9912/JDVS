# Unit 5 — 보호(Protection)와 무효화(Invalidation)

## 왜 필요한가

번역만으론 부족하다. ① 코드 영역에 버그/해커가 쓰면 자기 파괴 → "써도 되는가?"를 검사해야 함(보호).
② TLB가 캐싱한 매핑을 OS가 바꾸거나 메모리를 해제하면, TLB의 옛 사본은 거짓말이 됨 → 무효화 필요.

## 파트 A — 보호 (Protection)

각 페이지 매핑에는 PFN뿐 아니라 **권한 비트**가 함께 있다:

| 비트 | 의미 | 위반 시 |
|---|---|---|
| Valid/Present | 매핑 유효? RAM에 있나? | page fault (Unit 1 swap) |
| R (Read) | 읽기 허용? | fault |
| W (Write) | 쓰기 허용? | 읽기전용에 쓰면 fault |
| X (Execute) | 코드 실행 허용? | 데이터 실행 시 fault (보안, NX비트) |
| U/S | 사용자/커널 | 사용자가 커널 페이지 접근 시 fault |

- MMU는 매 접근마다 **2가지 동시 검사**: ①주소 번역(VPN→PFN) ②접근 권한.
- 둘 중 하나라도 실패 → **fault** (그 유명한 Segmentation Fault).
- **번역 성공 ≠ 접근 허용**: 주소는 찾아도 권한 없으면 막힘.
- Unit 1의 "보호 문제"가 실제로 구현되는 메커니즘. NX비트 = 데이터에 코드 심어 실행하는 공격 방어.

## 파트 B — 무효화 (Invalidation)

TLB는 페이지테이블의 **사본(캐시)**. 원본이 바뀌면 사본은 거짓말이 됨.
(매핑 변경 / 메모리 해제 / MR deregister 등 → 옛 TLB 엔트리는 위험)
→ TLB가 옛 사본으로 HIT하면 **이미 남의 것이 된 물리주소에 조용히 접근** = 데이터 손상/유출.

### 무효화 방법

| 방법 | 설명 | 비유 |
|---|---|---|
| 단일 무효화 (INVLPG) | 바뀐 엔트리 1개만 즉시 제거 (자리 비움) | 직원 1명 카드 비활성화 |
| 전체 flush | TLB 전체 비움 | 즐겨찾기 통째로 |
| Generation ID | 엔트리에 세대 도장, 세대 +1로 옛 세대 전부 동시 무효 (lazy) | "2024년 카드 전부 무효" 선언 |

### Generation ID 트릭 (우리 프로젝트가 사용, 16비트)

- 무효화 순간 = **카운터 +1 (O(1), 엔트리 안 건드림)**.
- 검사 = 별도 스캔 아님. **어차피 하는 lookup에 gen 비교 1건 묻어서** 판정. 접근하는 엔트리 1개만 봄.
- 옛 세대 엔트리 = 물리적으론 남되 gen 불일치로 miss 취급(무시) → 새 fill 때 덮어써서 자연 소멸.
- 대가: 옛 엔트리가 잠깐 자리 차지 / 카운터 한 바퀴(65536) 돌면 그때만 전체 flush 1회.

## 핵심 takeaway

- 번역 성공 ≠ 접근 허용. 권한 비트로 페이지 단위 보호 집행.
- 캐시(TLB)는 원본(페이지테이블)이 바뀌면 반드시 무효화. 안 하면 "성공처럼 보이는 조용한 사고".
- 단일 무효화(메스, 소수 변경) vs Generation ID(마스터 스위치, 대량 변경) — 변경 규모로 선택.
- DV 관점: "dereg 후 TLB가 정말 무효화됐나"를 반드시 테스트해야 함 (vtlb_dereg 환경).

## 📎 부록 — 이 단원에서 나온 질문들

### Q1. PFN이 뭐고, 그 권한비트 표는 TLB 엔트리인가 일반 page entry(L1/2/3)인가?

- **PFN** = Physical Frame Number = 번역의 최종 답(물리 프레임 번호). VPN→PFN + offset = 물리주소.
- 권한 정보의 **원본은 페이지 테이블**, **TLB는 그 사본**. (TLB miss 시 PTW가 페이지테이블에서 PFN+권한을 읽어 TLB에 복사)
- 레벨별 역할이 다름: **중간 레벨(L1,L2)** 엔트리 = "다음 표 위치"를 가리키는 이정표. **마지막 레벨(L3=leaf, 우리 프로젝트 PD0)** 엔트리 = 진짜 PFN + 권한비트.
- TLB는 walk의 최종 결과(VPN→PFN+권한)를 캐싱 → hit이면 중간 레벨 전부 건너뜀.

### Q2. L3 entry가 메모리가 가장 크겠네? L3에도 없으면 새로 뒤져 L3에 올리고 TLB update?

- 엔트리 **한 칸 크기는 레벨 무관하게 동일**(보통 8B). 단 나무 구조라 **L3(잎) 레벨은 표 개수가 가장 많아 총 메모리는 가장 큼** → 직관 맞음(개수가 많은 것).
- "없다"는 **두 종류**: ① **TLB miss(흔함)** — L3엔 이미 있음, PTW가 읽어서 TLB fill(만드는 게 아니라 읽기). ② **Page fault(드뭄)** — L3에조차 유효 매핑 없음 → OS가 프레임 할당/디스크 로드로 L3 엔트리를 새로 채움 → 재시도 → TLB update.
- 학습자가 말한 "L3에도 없으면 새로 채우고 TLB update" = ②번 page fault 경로와 정확히 일치(단, "뒤지는" 게 아니라 OS가 "할당/로드").

### Q3. Generation ID 무효화도 결국 generation field를 다 뒤져야 하는 것 아닌가? 똑같지 않나?

- **무효화 순간엔 아무것도 안 뒤짐**. "현재 세대 +1" 카운터 증가만(O(1)).
- gen 검사는 **별도 전체 스캔이 아니라**, 어차피 하는 lookup에서 VPN 비교할 때 **gen 비교 1건을 HW가 동시에**(사실상 공짜). 접근하는 엔트리 1개만 봄.
- 비유(우유 유통기한): 냉장고 100개를 지금 다 뒤져 버리는 게 아니라(=naive O(N)), 도장 날짜만 찍어두고 **마실 때 꺼낸 1개의 날짜만** 확인.
- 비용: 무효화 O(1) vs naive O(N). 대가는 옛 엔트리 잠깐 잔존 + 카운터 한 바퀴 돌 때만 전체 flush.

### Q4. 이게 단일 무효화랑 뭐가 다른가?

- **단일 무효화** = 메스: 바뀐 엔트리 **1개만 즉시 제거**(자리 비움). 소수 변경에 최적. 단, N개 바뀌면 N번 반복 → O(N).
- **Generation ID** = 마스터 스위치: 카운터 +1 **한 번으로 대량을 동시 무효**(개수 무관 O(1)). 대량 변경에 최적, lazy.
- 비유: 직원 1명 퇴사→그 카드만(단일) vs 1만 명 카드 전부 무효→"발급연도 무효 선언"(generation).
- 우리 프로젝트가 16비트 gen을 둔 이유: RDMA에서 MR 통째 무효화(많은 페이지 동시 사망)가 잦아 단일로 하면 너무 느림.

### Q5. 옛 엔트리는 남아있되 절대 안 보는 거지? 새로 채울 때 옛 generation 위에 덮어쓰는 거고?

- 정밀하게는: lookup 때 VPN으로 **찾아지긴 하지만 gen 불일치로 miss 취급되어 무시**됨(기능적으론 "안 보는" 것과 같음).
- 새 번역 fill 시 옛 세대(무효) 엔트리는 "잃어도 손해 없는 자리"라 **덮어쓰기 1순위 후보** → 자연 소멸.
- 즉 무효화는 "선언"만, 실제 청소(자리 회수)는 어차피 하는 fill에 공짜로 묻어서 일어남.
