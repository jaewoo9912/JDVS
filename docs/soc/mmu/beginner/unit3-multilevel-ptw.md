# Unit 3 — 다단계(Multi-level) 페이지 테이블 & PTW

## 왜 필요한가

단일 표는 4GB÷4KB = 약 100만 줄(≈4MB)을 **쓰든 안 쓰든 항상** 만들어야 함. 게다가 프로그램마다 하나씩.
현실의 주소공간은 대부분 **텅 빈 황무지(sparse)** → "안 쓰는 영역은 표도 만들지 말자"가 핵심 아이디어.

## 핵심 개념 — 표를 "책의 목차"처럼 계층화

- **목차(1단계 표)** → **장의 페이지목록(2단계 표)** → **실제 페이지(프레임)** → **줄(offset)**
- 안 쓴 장(章)은 목차에 "없음(null)" 한 줄로만 표시 → 거대한 하위표를 통째로 생략.

## VPN을 여러 조각으로 자른다

```text
   가상 주소
   ┌──────────┬──────────┬──────────────┐
   │ L1 인덱스  │ L2 인덱스  │   offset      │
   │ "몇 장?"   │ "몇 페이지?"│  "몇 번째 줄?"  │
   └──────────┴──────────┴──────────────┘
      목차 인덱스   하위표 인덱스    그대로 통과
```

## PTW (Page Table Walker)

표가 여러 단계라 번역 한 번에 표를 차례로 따라가야 함 = **page table walk**. 이걸 하는 하드웨어가 **PTW**.

```text
   ① 루트 레지스터(x86=CR3) → 1단계 표를 L1 인덱스로 읽음
   ② 2단계 표 주소 획득 → L2 인덱스로 읽음
   ③ PFN 획득 → offset 붙여 물리주소 완성
```

- 단계마다 메모리 1번씩 읽음. 2단계 = 표 2번 + 데이터 1번 = 총 3번. (4단계면 표 4번 + 1번 = 5번)
- 루트 레지스터는 **프로그램마다 다름** → 프로그램 전환 시 이것만 바꾸면 전체 매핑 교체.

## 메모리 절약 (예시)

- 단일 표: 항상 ≈4MB 고정.
- 2단계 표(3개 영역만 사용): 목차 1개 + 하위표 3개 ≈ 16KB → **약 250배 절약.**

## 트레이드오프

| | 단일 표 | 다단계 표 |
|---|---|---|
| 표 메모리 | 큼(낭비 많음) | 작음(쓴 만큼만) ✅ |
| walk 시 표 읽기 | 1번 | 단계 수만큼 ❌ (느림) |

→ "메모리 ↔ 속도"를 맞바꾼 것. 느린 walk는 Unit 4의 TLB로 만회.

## 핵심 takeaway

- VPN을 쪼개 나무 구조 표를 만들고, 안 쓰는 가지는 생략 → sparse한 현실에서 메모리 대폭 절약.
- 번역은 단계 수만큼 메모리를 읽어야 하므로 느림 → PTW가 자동화, TLB가 캐싱.
- 우리 프로젝트의 RDMA MMU = 3단계 Page Directory (PD2→PD1→PD0), PTW가 TLB miss 시 이 3단계를 walk.

## 📎 부록 — 이 단원에서 나온 질문들

### Q1. multi-level은 유리하지만 결국 page walk를 해야 해서 느려진다 — 이게 핵심인가?

- **맞다.** 다단계의 본질적 트레이드오프 = **메모리(표 크기)는 아끼지만, 번역 시 walk를 단계 수만큼 해야 해서 느려진다.**
- 단일 표: walk 시 표 읽기 1번 / 다단계: 단계 수만큼(2단계=2번, 우리 프로젝트 3단계=3번, 64비트는 4번).
- 그래서 다단계는 "메모리 ↔ 속도"를 맞바꾼 설계이고, 느린 walk는 TLB(Unit 4)가 결과를 캐싱해 만회한다.

### Q2. 단일표든 4단계든 결국 다 만들어야 하는 것 아닌가? 4단계도 새 주소 접근하면 표가 계속 추가되잖아?

- **핵심은 "안 쓰는 영역"**: 현실 프로그램은 4GB 중 극히 일부(0.0x%)만 쓰고 나머지는 영원히 안 건드림.
- **단일 표**는 거대한 1차원 배열이라 `표[VPN]`로 바로 점프하려면 모든 칸이 물리적으로 존재해야 함 → 안 쓰는 칸까지 100만 줄을 무조건 다 만듦(빈 칸도 자리 차지).
- **다단계 표**는 배열을 가지로 쪼개, 안 쓰는 가지는 "없음(null)" 한 줄로 끝내고 하위표를 **아예 안 만듦.**
- **"계속 추가된다"는 맞다** — 새 영역을 건드릴 때 OS가 그때그때 하위표를 만듦(lazy allocation). 하지만 **건드린 영역에 대해서만** 추가되고, 안 건드리는 황무지엔 절대 안 생김. 그래서 "쓴 만큼만" 자란다.
- **솔직한 반전**: 주소공간을 빈틈없이 꽉(dense) 채워 쓰면 다단계도 모든 하위표를 만들게 되고, 상위 표 오버헤드 때문에 오히려 단일 표보다 약간 더 씀. 다단계의 승리는 "현실 주소공간은 sparse하다"는 가정 덕분.
