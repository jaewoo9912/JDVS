# [심화 Unit 3] PTW & Walk Cache — miss를 견디는 법

> 핵심 질문: walk는 메모리를 여러 번 읽어야 해서 느린데, 하드웨어는 이 비용을 어떻게 견디고 숨기는가?

## 왜 필요한가

TLB miss 1건 = 트리 깊이만큼 **순차** 메모리 read. 단순히 "walk가 느리다"로 끝나지 않고, miss가 쏟아질 때 이 비용을 *짧게* + *겹쳐서* 견디는 마이크로아키텍처가 필요하다.

## 1. Page Table은 "다단계 트리"다 — 왜?

- 64비트 주소공간을 단일 배열로 만들면 엔트리가 수천조 개 → 페타바이트 → 불가능.
- 주소공간은 거대하나 **실제 쓰는 영역은 띄엄띄엄(sparse)** → "쓰는 가지만 만드는" 다단계 트리.

```text
VPN = [ L2 인덱스 | L1 인덱스 | L0 인덱스 ]

   루트 ─(L2)─► L2 테이블 ─(L1)─► L1 테이블 ─(L0)─► L0 테이블 ─► PFN
```

- 각 레벨 엔트리 = "다음 레벨 테이블 위치" 포인터. 안 쓰는 가지는 안 만들어 메모리 절약.

## 2. Walk = "포인터 따라 트리 내려가기" (비쌈)

레벨마다 메모리 read 1번:

```text
주소 [L2=5 | L1=2 | L0=9]
 ① 루트 5번 칸 → "L1은 A"   (read 1)
 ② A의 2번 칸  → "L0은 B"   (read 2)
 ③ B의 9번 칸  → "PFN=0x300"(read 3) ← 정답
```

- TLB miss 1건 = 메모리 read N번(트리 깊이), 순차적(앞 결과 필요).
- 이 walk 수행 HW = **PTW(Page Table Walker)**. miss 시 자동 walk → TLB 채움(SW 아닌 HW → 빠름).

> 도서관 비유: "층 안내판 → 구역 → 책장 → 칸" 단계마다 걸어가 확인. 각 걸음 = 메모리 접근.

## 3. 비싼 walk를 견디는 3가지 무기

### 무기 1 — Huge Page

페이지를 크게(2MB/1GB) → 트리를 끝까지 안 내려감:

```text
4KB: 루트→L2→L1→L0 (read 3)
2MB: 루트→L2→L1    (read 2)
1GB: 루트→L2        (read 1)
```

+ TLB 한 칸이 더 넓은 영역 커버 (64칸: 4KB=256KB vs 2MB=128MB, 512배).
**Trade-off:** 내부 단편화(메모리 낭비), 연속 물리 메모리 필요, swap/관리 부담. (속도 ↔ 공간)

### 무기 2 — Walk Cache ★

- 인접 주소는 **상위 레벨(루트/L2/L1) 공유**, L0만 다름.
- **TLB = 최종 답(VPN→PFN) 저장** → hit이면 walk 없음(read 0).
- **Walk cache = 중간 길(다음 레벨 주소) 저장** → hit이어도 **마지막 레벨 read는 남음**.

```text
Walk cache: [루트,5]→"L1=A" / [A,2]→"L0=B"   (PFN은 없음, PFN은 TLB에)
```

### 무기 3 — 동시 다발 처리 (non-blocking / latency hiding) ★

```text
blocking:     miss1(대기)→끝→miss2(대기)→끝   ← 다 더해짐
non-blocking: miss1·miss2·miss3 동시 진행      ← 대기 겹침, 처리량↑
```

- "처리 중 miss"를 장부(**MSHR, Miss Status Holding Register**)에 기록, 동시에 여러 건 in-flight.
- 같은 페이지 동시 miss는 walk 1회 + 결과 공유(중복 제거).
- 지연을 throughput 뒤에 숨김 = **latency hiding**.

## 4. TLB vs Walk Cache 핵심 구분

| | 저장 대상 | hit 시 | 단계 |
|---|---|---|---|
| **TLB** | 완성된 변환 (VPN→PFN) | walk 없음 (read 0) | 1차 방어 |
| **Walk Cache** | walk 중간 길 | 마지막 레벨만 read | 2차 완충 |

```text
요청 ─ TLB hit ─────► read 0
     ─ TLB miss → walk cache hit ─► 마지막만 read
     ─ 둘 다 miss ─► 풀 walk
```

## 5. 숫자로 보는 효과 (연속 512페이지, 전부 TLB miss, 3단계)

| 구성 | miss당 read | 총 read |
|---|---|---|
| walk cache 없음 | 3 | 1536 |
| walk cache 있음 | 첫 3, 이후 1 | 514 |
| + MSHR 8 | 8겹 중첩 | 벽시계 ≈ 1/8 |

→ walk cache(트래픽 ~3배↓) × MSHR(지연 ~8배 은닉). **곱셈으로 작동.**

## 핵심 takeaway

- Walk는 비싸다: TLB miss 1건 = 순차 메모리 read N번.
- Huge page: 변환 단위↑ → walk 깊이↓ + TLB 커버리지↑ (대가: 메모리 낭비).
- Walk cache: 공유되는 상위 길 캐싱 → walk 짧게 (마지막 레벨은 항상 read).
- MSHR: 여러 walk를 겹쳐 latency를 throughput 뒤에 숨김.
- **Golden rule**: HW는 walk를 *빠르게*가 아니라, *캐싱으로 짧게* + *동시 처리로 겹쳐서* 견딘다.

# 부록 A — 선행 논의: 가상화 · 하이퍼바이저 · 2단계 변환

> Unit 3 도중 곁가지로 다룬 내용. Unit 4(IOMMU & 가상화)의 토대.

### Q. 게스트(Guest)는 뭐야?

- **VM(가상 머신)** = 소프트웨어로 만든 "진짜 컴퓨터인 척하는 가짜 컴퓨터".
- **게스트(Guest) OS** = 그 가짜 컴퓨터 안에서 도는 운영체제. 자기가 진짜 하드웨어 위에 있다고 *착각*함.
- **하이퍼바이저** = 진짜 하드웨어를 쥐고 가짜 컴퓨터들을 만들어 굴리는 "집주인".
- 비유: 하이퍼바이저=건물 주인(진짜 방번호 소유), 게스트 OS=한 층 빌린 회사(건물 전체가 내 거라 착각), 프로세스=그 회사 직원.

### Q. 게스트 OS 말고 기본적으로 존재하는 OS도 있어?

하이퍼바이저 종류에 따라 다름.

- **Type 2 (호스트형, 예: VirtualBox)**: 밑에 평범한 **호스트 OS**(윈도우/맥)가 있고, 하이퍼바이저가 그 위 앱처럼 돎. → 기본 OS 있음.
- **Type 1 (베어메탈, 예: ESXi/Xen/Hyper-V)**: 하이퍼바이저 자체가 하드웨어 위 최하단. 별도 범용 OS 없음. (KVM은 리눅스 커널에 하이퍼바이저 기능이 들어가 Type 1에 가깝게 분류)

### Q. 하이퍼바이저 = Virtual Machine Manager(VMM)?

사실상 동의어. VM을 생성/실행하고 여러 VM이 하드웨어를 안전하게 나눠 쓰게 중재하는 SW 계층. "OS의 OS". Type 1(bare-metal) / Type 2(hosted) 두 종류.

### Q. MMU 배우는 이유가 하이퍼바이저 일을 덜어주려는 거였지?

절반만 맞음. MMU의 *원래* 목적은 **OS**를 도와 프로세스 격리·가상 메모리를 제공하는 것(가상화보다 수십 년 먼저). 가상화 시대에 추가된 **2단계 변환(stage-2)+VMID**가 바로 하이퍼바이저 부담을 더는 기능. (옛날엔 HW 지원이 없어 하이퍼바이저가 SW로 **shadow page table**을 유지 → 느림. HW 2단계 변환=Intel EPT/AMD NPT/ARM stage-2로 offload.)

### Q. 2단계 변환이 VA→PA 말하는 거지?

최종 입출력은 VA→PA가 맞지만, 핵심은 중간을 거쳐 **두 번에 나눠** 한다는 것:

```text
VA ─(stage1: 게스트 OS)─► IPA ─(stage2: 하이퍼바이저)─► PA
```

주의 — "단계(stage)" ≠ "레벨(level)":

- **Level**: 한 번의 변환 안에서 트리를 내려가는 깊이 (PD2→PD1→PD0).
- **Stage**: 독립된 변환을 몇 번 거치나 (게스트·하이퍼바이저, 주인 수).

2단계에선 stage1의 각 레벨 주소도 IPA라 stage2 walk가 또 필요 → 최악 시 메모리 read가 3×3≈수십 번으로 폭발 → 그래서 TLB·walk cache가 더 중요.

### Q. IPA로 변환하는 이유는? 게스트는 VA 쓰면 되잖아?

게스트 *프로세스*는 VA를 쓰지만, 그 VA를 변환하는 **게스트 OS의 page table이 내놓는 "물리주소"가 곧 IPA**다(게스트는 진짜 메모리 주인이 아니므로 그 출력은 가짜 물리=IPA). 또한 게스트 OS 커널 자체가 VA 밖에서 "물리주소"를 직접 다룸(page table base 레지스터, PTE 안의 프레임 번호 등) → 그 "물리"가 IPA. VA→PA를 한 테이블로 합치면: 게스트가 소유하면 격리 붕괴(아무 PA나 지정), 하이퍼바이저가 소유하면 shadow page table 지옥. → 테이블을 둘로 쪼개 **stage1=게스트 소유(VA→IPA), stage2=하이퍼바이저 소유(IPA→PA)**, 그 인계 지점이 IPA. IPA 덕에 격리·재배치·오버커밋·페이지 공유·라이브 마이그레이션이 게스트 몰래 가능.

### Q. 하이퍼바이저랑 MMU 차이는?

- **하이퍼바이저 = 소프트웨어**: 변환 규칙(page table)을 *만들어 둠*. 가끔(VM 생성/매핑 변경 시) 동작. "지도 제작자".
- **MMU = 하드웨어**: 그 규칙으로 *매 메모리 접근마다* 실제 변환. 초당 수십억 번. "지도 읽어 길 안내하는 내비 칩".
- 협업: SW가 page table 작성 → MMU가 매 접근마다 자동 실행 → 규칙에 없는 접근만 fault로 SW를 깨움. 평소엔 HW가 다 처리(그래서 빠름).

### Q. CPU MMU / IOMMU가 있는데, page table 만드는 게 하이퍼바이저고 실행하는 게 MMU?

방향 맞음, 한 군데만 보정: page table 작성자는 **계층마다 다름**.

- **OS**: stage1(VA→IPA, 또는 가상화 없으면 VA→PA) 작성.
- **하이퍼바이저**: stage2(IPA→PA, 격리) 작성.
- **실행 HW**: CPU 접근은 **CPU MMU**, 장치 DMA는 **IOMMU**가 매 접근마다 변환.

즉 "*모든* 테이블을 하이퍼바이저가"가 아니라 "stage1=OS, stage2=하이퍼바이저, 실행=MMU/IOMMU".

# 부록 B — 이 단원에서 나온 질문들

### Q1. "Walk cache는 미완성(중간 가지)을 들고 있어 hit이어도 하위 walk는 해야 한다" 무슨 소리야?

TLB는 **최종 답(VPN→PFN)**을 외워 hit이면 read 0번. walk cache는 PFN이 아니라 **중간 결과(다음 레벨 테이블 위치)**만 외움 → hit해도 "L0 테이블이 B에 있다"까지만 알아 **마지막 레벨(B) read는 반드시** 해야 함. 인접 주소는 상위 경로(L2·L1)가 같아 그 부분만 재사용 → read 3→1번(0번 아님). TLB hit=walk 없음(1차), TLB miss여도 walk cache가 walk 단축(2차). 둘은 외우는 대상·막는 단계가 다른 보완 관계.

### Q2. huge page는 어떤 개념이야?

기본 4KB보다 큰 페이지(2MB/1GB)를 한 덩어리로 매핑. 이득 ① walk 짧아짐(leaf가 위 레벨 → read↓), ② TLB 적중률 폭증(한 칸이 512배 영역 커버). 대가: 내부 단편화(낭비), 연속 물리 메모리 필요, swap/관리 부담. 큰 메모리 집약 워크로드(DB/ML/HPC)엔 유리.

### Q3. huge page는 "TLB + page walk가 다루는 page 크기가 커진다"는 의미?

방향 맞음. 정확히는 "한 번에 더 많이 *읽는다*"가 아니라 **"변환 1건이 커버하는 단위(페이지)가 커진다"**. 결과로 TLB 한 칸이 더 넓은 영역을 가리켜 적중률↑, walk는 leaf가 위에 있어 read↓. 단위를 키운 한 변화가 양쪽에서 이득.

### Q4. walk cache 있을 때 실제 동작을 자세한 예시로?

page table 내용을 실제로 적어두고 따라가 보자.

**무대 (3단계 트리, 각 테이블 내용):**

```text
[루트 테이블] (주소 R)
   5번 칸 → 0xA000        (L1 테이블이 0xA000에 있다)

[L1 테이블] (주소 0xA000)
   2번 칸 → 0xB000        (L0 테이블이 0xB000에 있다)
   3번 칸 → 0xC000        (다른 L0 테이블)

[L0 테이블] (주소 0xB000)  ← 진짜 PFN들
   9번 칸 → PFN 0x300 / 10번 칸 → PFN 0x301 / 11번 칸 → PFN 0x302
```

변환할 주소(`[L2칸|L1칸|L0칸]`, 전부 TLB miss 가정): ① `[5|2|9]` ② `[5|2|10]` ③ `[5|2|11]`
walk cache = "(테이블, 칸) → 다음 테이블 주소"를 담는 작은 표. 처음엔 빔.

**주소 ① [5|2|9] — walk cache 비어서 풀 walk (read 3):**

```text
단계1 "루트의 5번 칸?"   → walk cache miss → 메모리 read 루트[5]=0xA000  📥 read1
                          → walk cache 저장: (루트,5)→0xA000
단계2 "0xA000의 2번 칸?" → walk cache miss → 메모리 read L1[2]=0xB000    📥 read2
                          → walk cache 저장: (0xA000,2)→0xB000
단계3 "0xB000의 9번 칸?" → 메모리 read L0[9]=PFN 0x300                   📥 read3
                          → 정답! PFN은 TLB에 저장 (walk cache 아님)

walk cache 상태:  (루트,5)→0xA000 / (0xA000,2)→0xB000   (PFN은 없음)
```

**주소 ② [5|2|10] — 상위 2단계 hit → read 1:**

```text
TLB 조회 [5|2|10] → miss → walk 시작
단계1 "루트의 5번 칸?"   → (루트,5)=0xA000 HIT ⚡   (read 0)
단계2 "0xA000의 2번 칸?" → (0xA000,2)=0xB000 HIT ⚡ (read 0)
단계3 "0xB000의 10번 칸?"→ walk cache엔 L0 내용 없음 → 메모리 read L0[10]=0x301  📥 read1
                          → 정답, TLB 저장
```

상위 2단계를 통째로 건너뜀이 핵심. (walk cache 추가 없음)

**주소 ③ [5|2|11] — 똑같이 read 1:**

```text
단계1 (루트,5) HIT ⚡ / 단계2 (0xA000,2) HIT ⚡ / 단계3 0xB000[11] 메모리 read=0x302 📥 read1
```

**여기까지 합계:**

```text
            상위2단계      L0        총 read
주소 ①:     read 2(새길)   read 1    3
주소 ②:     hit (0)        read 1    1
주소 ③:     hit (0)        read 1    1
walk cache 없음 9 → 있음 5
```

**보너스 — 경로가 조금 다른 주소(부분 hit):**

```text
주소 ④ [5|3|0]  ← L2칸은 5로 같고, L1칸이 2→3 으로 다름
단계1 "루트의 5번 칸?"   → (루트,5)=0xA000 HIT ⚡  (read 0)   ← 이 부분 공유!
단계2 "0xA000의 3번 칸?" → walk cache엔 (0xA000,2)뿐, 3번은 없음 → miss
                          → 메모리 read L1[3]=0xC000  📥 read1, walk cache에 (0xA000,3)→0xC000 추가
단계3 "0xC000의 0번 칸?" → 메모리 read → PFN  📥 read2
→ read 2번 (풀 walk 3보다 적음)
```

→ **공유되는 만큼만 이득**. 위쪽 레벨일수록 더 많은 주소가 공유하므로 **상위 레벨 캐싱일수록 적중률↑** (그래서 walk cache는 보통 레벨별로 따로 둔다).

**한 문장 정리:** Walk cache는 walk 도중의 **(테이블,칸)→다음 테이블 주소** 쌍을 저장한다. 첫 접근이 상위 경로를 닦아두면, 그 경로를 공유하는 후속 주소들은 **공유 구간만큼 단계를 건너뛰고** 안 닦인 마지막 부분만 메모리에서 읽는다. 주소가 가까울수록(공유가 많을수록) 절약이 크다.
