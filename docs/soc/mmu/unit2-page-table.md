# Unit 2 — 페이지(Page)와 페이지 테이블(Page Table)

## 왜 필요한가

가상주소 1바이트마다 물리주소 1바이트를 적으면, 4GB 주소공간엔 표가 약 43억 줄 필요 → 비현실적.
→ 메모리는 "근처 것끼리 뭉쳐" 쓰이므로, **고정 크기 블록(페이지) 단위로 통째 매핑**하면 표가 확 줄어든다.

## 핵심 용어

- **페이지(Page)**: 가상 메모리를 자르는 고정 크기 블록 (보통 4KB = 0x1000)
- **프레임(Frame)**: 물리 메모리의 같은 크기 블록 (페이지의 물리 버전)
- **페이지 테이블(Page Table)**: "VPN(페이지 번호) → PFN(프레임 번호)" 변환 장부

## 주소를 두 토막으로 자른다

```text
   가상 주소
   ┌─────────────────┬──────────────┐
   │  페이지 번호(VPN)  │  오프셋(Offset) │
   │  "몇 번 페이지냐"   │ "페이지 안 어디냐"│
   └─────────────────┴──────────────┘
        ▲ 이것만 번역         ▲ 그대로 통과(복사)
```

- **Offset**: 페이지 안에서의 위치. 4KB면 하위 12비트 = 16진수 하위 3자리. **번역 안 함.**
- **VPN**: 페이지 번호. 나머지 상위 비트. **이것만** 표로 번역.

## 변환 공식

```text
물리주소(PA) = ( 페이지테이블[VPN] << 12 ) + offset
            = PFN을 앞에 붙이고 + offset 그대로
```

## 왜 offset은 번역하지 않나 (사물함 비유)

사물함 "한 줄(=페이지)"을 통째로 다른 곳으로 옮기면, **줄 번호만 바뀌고 줄 안의 칸 번호(=offset)는 그대로**다.
페이지는 블록째 옮겨지므로 그 안의 상대 위치는 보존된다. offset까지 바꾸면 블록으로 묶은 의미가 사라진다.

## 예제 (페이지테이블: 0x0→0x5, 0x1→0x9, 0x2→0x7, 0x3→0x2)

```text
   가상주소 0x2ABC
     VPN=0x2, offset=0xABC
   ① 표에서 VPN 0x2 → PFN 0x7
   ② offset 0xABC 그대로
   ③ 합치기 → 물리주소 0x7ABC
   (앞자리 2→7만 바뀌고 뒤 3자리 ABC는 그대로!)
```

## 핵심 takeaway

- 주소 = [VPN | offset]. VPN만 번역, offset은 복사.
- 같은 VPN을 가진 주소들(한 페이지)은 같은 PFN으로 번역되고 권한도 동일 → 페이지가 관리의 최소 단위.
- 페이지가 크면(huge page) 표↓·TLB효율↑, 대신 메모리 낭비↑ (트레이드오프).

!!! tip "One more thing — huge page 트레이드오프"
    페이지 크기가 크면(예: 2MB, 1GB "huge page") offset 비트가 늘어나 표 줄 수가 더 줄고 TLB 효율↑, 대신 메모리 낭비(내부 단편화)↑. 이 트레이드오프가 우리 프로젝트의 1GB/2MB/4KB 세 가지 페이지 크기(Unit 6) 설계 이유입니다.

## 📎 부록 — 이 단원에서 나온 질문들

### Q. offset은 왜 번역하지 않고 그냥 통과하나? (쉽게)

- **사물함 줄 비유:** 사물함 한 줄(0~9칸)을 통째로 "2번 줄 → 7번 줄"로 옮기면, "3번 칸에 둔 가방"은 옮긴 뒤 "7번 줄의 3번 칸"에 있다. **줄 번호(VPN)만 바뀌고 칸 번호(offset)는 그대로.**
- 페이지는 **통째로** 옮겨지기 때문에 그 안의 위치(offset)는 절대 안 변한다. 바뀌는 건 "어느 줄/페이지냐"(VPN)뿐.
- 만약 offset까지 바꾸면 = 줄을 옮기며 칸 안 물건을 뒤섞는 것 → 아무도 못 찾음. 그래서 offset은 건드리지 않고 그대로 통과시킨다.
